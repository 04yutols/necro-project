## 1. 目的と位置づけ

Agent A（生成）/ B（監査修正）/ E（シミュレータ）は**数値・参照の正しさ**を扱う。
ストーリーは性質が異なる — **正しさ（構造・参照）と良さ（物語の質）が分離している。**

- **構造・参照**: scene type・trigger・speaker・expression・stage 参照など → **決定論的に検証可能**。
- **物語の質**: キャラの口調・前後シーンの繋がり・固有名詞の一貫性・場面のトーン → **数値ゲートでは測れない。人間が選ぶ**。

> **Agent C の設計原則（doc100 §3.4 と一致）**:
> 1. **構造は決定論ゲートで担保**（speaker が存在するか、trigger の stageId が実在するか…）。
> 2. **物語の質は「複数案を生成 → 人間が選択」**（dialogue を 3 案出す）。LLM に良し悪しを判定させない。
> 3. **キャラの口調・世界観は豊富なコンテキストで担保**（キャラバイブル + 前後シーン + 固有名詞集）。
> 4. 永続化は既存 `saveStoryScene()` のみ。エージェントは書き込まない。

## 3. アーキテクチャ

```
[/admin/story の シーン編集 or 新規]
  「AI初稿」（新規シーン）/「AI補完」（既存シーンの lines を埋める/磨く）
      │
      ▼
Server Action: generateStorySceneAction / completeSceneLinesAction
      │  キャラバイブル(doc22) + 前後シーン + 固有名詞集 + trigger位置 を収集
      ▼
LangGraph Story Graph（N 案生成）
  ┌──────────────────────────────────────────────┐
  │ generateCandidates  LLM: 文脈に沿った台詞を **3案** 生成     │
  │     ▼                                          │
  │ validateEach  各案を storyValidator（構造・参照）で検証      │
  │     ▼  構造 FAIL の案を除外。有効案が 0 & 試行<max → 再生成  │
  │     ▼  有効案 >=1 or 試行上限 → END             │
  └──────────────────────────────────────────────┘
      │  構造的に妥当な候補 [1..3] + 各案の検証結果
      ▼
UI: **候補を並べて表示 → 人間が1案選択 → フォームに反映** → 既存 saveStoryScene
```

**ポイント**: 構造ゲートは「壊れた案を弾く」用途（再生成のトリガー）。
良し悪しの最終判断は**人間の選択**であり、LLM にも決定論ゲートにも委ねない。

## 4. 詳細設計

### 4.1 決定論的構造バリデータ（`story/storyValidator.ts`）

```ts
type StoryValidationContext = {
  characters: Record<string, StoryCharacter>; // speaker/expression 参照
  stageIds: Set<string>;                       // trigger.stageId / navigateTo
  areaIds: Set<string>;                        // areaId / unlockArea
  existingSceneIds: Set<string>;               // id 重複（対象自身は除外）
};
validateScene(scene: unknown, ctx): { ok, findings: {level, field, message}[] }
```
§2.1 の規則を機械検証。Agent A 系バリデータと同型（PASS/WARN/FAIL）。

### 4.2 物語コンテキスト（`story/storyContext.ts`）

LLM に渡す「世界観の土台」を組む（数値ではなく文章）:

1. **キャラバイブル**: characters.json（名前/表情）+ **設計書22 から各キャラの口調・性格・一人称・背景**を抽出。
   - 例: アルド=喪失を抱えた元・勇者の相棒、一人称「俺」、抑制的で時に皮肉。リン=…。
2. **前後シーン**: 挿入位置の前 N シーン・後 1 シーンの lines を要約して渡す（流れの連続性）。
3. **固有名詞集**: 王都/亡国/魔王/ネクロマンス 等の表記ゆれ防止用グロッサリ。
4. **trigger 位置の状況**: どのステージ後/章のどこか（緊張感・トーンの指針）。

> キャラの口調が崩れないかは**この文脈の質**で担保する。バリデータは口調を測らない。

### 4.3 エージェント 2 モード（`storyAgent.ts`）

- **新規シーン（AI初稿）**: 短い指示（「アルドが廃城前で友を思い出すモノローグ」）+ type/trigger 指定 →
  シーン全体（lines 含む）を **3 案**生成。各案を構造検証し、妥当案を返す。
- **lines 補完（AI補完）**: 既存シーンの骨子（id/type/trigger/speaker 列）を維持し、**lines の text/textEn を 3 案**埋める。
  構造（speaker/expression/参照）は既存を尊重しつつ検証。

ループ: 全案が構造 FAIL のときのみ再生成（最大 maxAttempts）。1 案でも妥当なら採用候補にする。

### 4.4 多案 → 人間選択

- 出力は `candidates: { scene, validation }[]`（最大3）。
- UI に 3 案を**並べて**表示。各案に検証バッジ（構造 PASS/WARN）。
- 人間が 1 案を選び「フォームに反映」→ 既存フォームの保存ボタン（`saveStoryScene`）で確定。
- WARN（例 textEn 欠落）は表示するが選択を妨げない。

## 6. プロンプト設計（generateCandidates）

```
あなたは Necromance Brave のシナリオライターです。世界観とキャラの口調を厳守し、
指定の場面の台詞を作成してください。良し悪しの選択は人間が行うため、雰囲気の異なる候補を3案出してください。

# 場面
type: {type} / trigger: {trigger} / 章: {chapter}（{archiveTitle}）
指示: {brief}

# キャラバイブル（口調・性格・一人称・背景）
{characters voice from doc22}

# 直前の流れ（連続性を保つ）
{前Nシーンの要約}

# 固有名詞（表記を統一）
{glossary}

# 出力（JSONのみ。3案）
{ "candidates": [
  { "lines": [ { "speaker": "characters.jsonのキー or null", "text": "日本語台詞", "textEn": "English", "expression": "そのキャラのexpressionsのいずれか" } ] }

# 厳守
- speaker は characters.json のキーか null（ナレーション）。
- expression はそのキャラの expressions に含まれる値のみ。
- 固有名詞の表記を統一。前シーンと矛盾しない。
- 3案はトーン/言い回しを変える（同じ内容の焼き直しにしない）。
```

## 7. UI 設計（/admin/story 拡張）

- **AI初稿**（新規シーン作成画面）: type/trigger と短い指示を入れて生成 → 3 案カード。
- **AI補完**（既存シーン編集）: 現在の骨子を文脈に、lines を 3 案生成。
- `AIStorySceneCandidates`: 3 案を横並び。各案に「構造 PASS/WARN」バッジ + lines プレビュー。
  「この案を反映」で既存フォーム（DialogueScene 編集）へ流し込み → 保存ボタンで確定。
- 構造 FAIL の案は表示しない（再生成で補充）。

## 8. 安全性

| リスク | 対策 |
|---|---|
| 存在しない speaker / expression / stage を参照 | storyValidator が FAIL → 候補から除外・再生成 |
| キャラの口調崩れ・世界観矛盾 | キャラバイブル+前後シーン+固有名詞集の文脈で抑制。最終は人間選択 |
| LLM が「良い」と誤判定 | 良し悪しを LLM に判定させない（多案→人間選択）|
| 破壊的上書き | 反映は候補選択のみ。保存は既存 saveStoryScene のユーザー操作 |
| 開発環境外実行 | `assertDev()` 踏襲 |

## 11. 他エージェントとの関係（単一の真実）

| エージェント | 検証の性質 | ゲート |
|---|---|---|
| Agent A / B | 数値・参照（静的・客観） | per-content バリデータ + 監査 |
| Agent E | 実戦バランス（動的・客観） | calculateBattleDamage 多シナリオ |
| **Agent C（ストーリー）** | **構造=客観 / 物語=主観** | **storyValidator（構造）+ 人間選択（物語）** |

A/B/E は「客観的に正しい数値」を、C は「客観的な構造の正しさ」＋「主観的な物語の良さ」を扱う。
C だけは**最終判断を人間に残す**点が他と異なる（doc100 §3.4 の方針）。

### 設計どおり実現できた核心

- **構造=決定論ゲート / 物語=人間選択**: storyValidator が無効 speaker/expression/参照の案を除外し、再生成。
  最終の良し悪しは人間が候補から選ぶ（LLM に判定させない）。
- **口調はデータ駆動**: キャラバイブルを既存シーンの実台詞から抽出 → ハードコードせず作品の声を反映。
- **保存は既存 saveStoryScene のみ**（候補選択でフォームに反映 → ユーザーが保存）。
