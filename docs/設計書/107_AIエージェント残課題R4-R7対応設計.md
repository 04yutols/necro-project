## 1. R-4: Server Action 層のテスト可能化

### 1.1 問題

`src/app/admin/agents/actions.ts`（'use server'）には、薄いラッパと言いつつ次の決定論ロジックが**インライン**で存在し、未テストだった:

- `buildDesignContext`（tier 帯の整形）
- `deriveElementAffinity`（耐性 → 属性傾向）
- `powerBandHint`（power 帯ヒント文）
- `buildFieldHints`（一括変更用フィールドヒント）
- `failKeyOf` / `failKeyOfFinding`（**同一実装が 2 箇所に重複**）
- sim 用の attacker / skill / targets 構築（`evaluateBalanceAction` と `evaluateSkillDraftAction` で**ほぼ同一コードが重複**）
- `restoreBulkSnapshotAction` の snapshotId → file 解析

'use server' ファイルは dev 環境 + disk 依存のため Jest から直接実行しにくい。
**ロジックを抽出してテストすれば、残るアクション本体は「入出力の配線」だけになり、R-4 の趣旨（未テストロジックの解消）を満たす。**

### 1.2 設計

新規 `src/lib/agent/actionSupport.ts`（純関数のみ・fs/LLM 非依存）:

```ts
validateRequirements(req: string): string | null      // 共通入力ガード（4文字未満はエラー文）
deriveElementAffinity(resistances: unknown): string[]  // 移設
buildEnemyDesignContext(existingEnemies, docExcerpt): string  // 移設（doc15 の fs 読みは呼び出し側）
powerBandHint(skill, tier): string                     // 移設
buildFieldHints(all): string                           // 移設
findingKey(f: {scope,id,message}): string              // failKeyOf 2 重複を統一
buildSimTargets(enemies, ids?): SimTarget[]            // 2 アクションの重複を統一
toSimSkill(src): SimSkill                              // 〃
snapshotFileOf(snapshotId): string                     // "{file}__{ts}.json" → file
clampLevel(level, fallback): number                    // 1〜100 クランプ
```

`actions.ts` は上記を import して使う（挙動は不変）。

### 1.3 テスト

`src/lib/agent/actionSupport.test.ts`（合成データのみ）:
- validateRequirements: 空 / 3文字 / 4文字 / 前後空白
- deriveElementAffinity: 正の耐性のみ抽出・非オブジェクト安全
- buildSimTargets: stats 欠落補完（hp=1/def=0）・存在しない id の除外・ids 未指定で全件
- toSimSkill: 型欠落時のデフォルト（power=1.0 / element=NONE / SINGLE）
- snapshotFileOf / findingKey / clampLevel / powerBandHint（帯内・帯外・分類不明）
- buildFieldHints: ネスト深さ・型表記
- buildEnemyDesignContext: tier 帯行が含まれる

完了条件: `actions.ts` に残る処理が「ガード → マスター読込 → lib 呼び出し → 整形済み返却」のみになること。

## 2. R-5: sim の AoE 合算サマリ

### 2.1 問題

`buildSimulationReport` は AoE（`targetType==='ALL_ENEMIES'`）でも per-target と同じ集計しかせず、
「1 回の発動で複数体に同時ヒットする」価値が energyEfficiency に現れない。
→ AoE スキルが常に「効率が悪い」と誤評定されるバイアス（doc103 §で簡略化として記載済み）。

### 2.2 設計

- WAVE の敵は最大 3 体（doc15 のウェーブ設計）。`AOE_ASSUMED_TARGETS = 3` を定数化。
- `SimulationReport.summary.aoe`（AoE のときのみ存在）:

```ts
aoe?: {
  assumedTargets: number;            // 3（想定同時ヒット数）
  totalExpectedPerCast: number;      // avgExpected × assumedTargets
  energyEfficiency: number | null;   // totalExpectedPerCast / mpCost
}
```

- `reportToText` に AoE 行を追加（LLM が合算効率で判断できるように）。
- `evaluateBalanceAction` / `evaluateSkillDraftAction` の designContext に AoE 用の目安を追加:
  単体の効率目安 20〜35 に対し、AoE は power が単体の約 6 割（doc19 §2.2）× 3 体 ≒ **1.8 倍**、
  すなわち**合算効率 36〜63 を目安**とする。

### 2.3 テスト

`simulationReport.test.ts` に追加:
- SINGLE のとき `summary.aoe` が無い
- ALL_ENEMIES のとき `totalExpectedPerCast = avgExpected × 3`、`energyEfficiency = 合算/mpCost`
- mpCost=0 のとき aoe.energyEfficiency=null
- reportToText に合算行が含まれる

## 3. R-6: gimmick.value の number 正規化

### 3.1 問題

`BossGimmick.value?: number`（game.ts）だが、EnemyForm の行状態は `value: string`。
- agent 生成の number は未編集なら保持されるが、**入力欄を触ると string で保存**される。
- 既存プレースホルダが `earthbound_grudge`（文字列 id）で、数値であるべきという仕様を誤誘導。

### 3.2 設計

入出力境界での正規化（フォーム内部は string のままで良い）:

新規 `src/components/admin/forms/shared/gimmickValue.ts`（純関数・client 非依存）:

```ts
gimmickValueToInput(v: unknown): string
  // 読込: number → String(v) / string → そのまま / null・undefined → ''
gimmickRowsToJson(rows: {trigger,effect,value}[]): {trigger,effect,value?}[]
  // 保存: trim して '' → value フィールド省略
  //        数値文字列 → Number（有限のみ）
  //        非数値文字列 → そのまま保持（データ消失防止。バリデータが WARN する領域）
```

EnemyForm 変更:
- `initForm`: gimmicks 読込を `gimmickValueToInput` 経由に（number 値を行状態の string へ）
- `formToJson`: gimmicks 出力を `gimmickRowsToJson` 経由に
- value 入力欄のプレースホルダを `1`（数値）へ修正

### 3.3 テスト

`gimmickValue.test.ts`:
- number 1 → '1' → 保存で 1（往復不変）
- '0.5' → 0.5、' 2 ' → 2
- '' → value 省略
- 'abc' → 'abc' のまま保持（消失しない）
- 'Infinity' / 'NaN' → 数値化しない（文字列のまま）

## 4. R-7: enemy 草案のバランス評価（E-5 拡張）

### 4.1 問題

E-5（生成直後のバランス評価）は skill 草案のみ。enemy 草案は「攻撃側を決めないと評価できない」ため未対応だった。
106 §2 の推奨どおり **「代表スキル数種 vs この敵」** の形で実装する。

### 4.2 設計（決定論パート）

新規 `src/lib/agent/sim/enemyDraftReport.ts`（純関数）:

```ts
selectRepresentativeSkills(skills, maxPerClass=1): RepresentativeSkill[]
  // 4 分類（PHYS_SINGLE/PHYS_AOE/MAGIC_SINGLE/MAGIC_AOE）ごとに
  // power 中央値のスキルを決定論的に選抜（同値は id 昇順で安定）
medianAttacker(attackers: {atk,critRate,critDmg}[]): SimAttacker
  // 全職業の level 時点ステータスの中央値 = 「代表アタッカー」
buildEnemyDraftReport(attacker, repSkills, target): EnemyDraftReport
  // 各代表スキル × この敵 1 体を evaluateAgainstTarget で評価
  // summary: avg/min/max hitsToKill・oneShot 数・弱点ヒット数・耐性ヒット数
enemyReportToText(report): string   // LLM プロンプト用整形
```

攻撃側は `getJobBaseStatsAtLevel`（実ロジック）で各職業の指定レベル値を出し、その**中央値**を採用。
特定職業に依存しない「標準的な攻撃」に対する敵の硬さを測る。レベルは UI から指定（既定 10 = 第1章想定）。

### 4.3 設計（LLM パート）

`simEvalAgent.ts` に `runEnemySimEvalAgent` を追加:
- 入力: `EnemyDraftReport` + designContext（tier 帯）+ recCheckContext.enemy
- verdict 語彙は既存と共通（TOO_STRONG=硬すぎ/脅威過剰、TOO_WEAK=脆すぎ）
- recommendations の target は `enemy.hp` / `enemy.def` のみ許可
- 帯チェックは既存 `checkRecommendations`（ctx.enemy = { tier, existingEnemies }）を再利用

### 4.4 Server Action / UI

- `evaluateEnemyDraftAction(draft, level=10, options?)`（actions.ts）:
  jobs/skills/enemies 読込 → 代表アタッカー + 代表スキル選抜 → レポート → `runEnemySimEvalAgent`。非破壊。
- `AIEnemyDraftPanel.tsx`: 草案生成後に「⚖ バランス評価」ボタン（skill パネルと同型）。
  代表スキルごとの撃破発数 + verdict + 推奨（帯外警告付き）を表示。

### 4.5 テスト

- `enemyDraftReport.test.ts`: 選抜の決定論性（中央値・安定ソート）/ medianAttacker（偶数・奇数件）/
  summary の手計算一致 / 弱点・耐性カウント / enemyReportToText の内容
- ライブ verify: `scripts/verify-enemy-eval-agent.mts`（`npm run agent:verify-enemy-eval`）
  - 硬すぎ敵（HP/DEF が BOSS 帯超）→ TOO_STRONG、紙装甲敵 → TOO_WEAK を期待
  - 非破壊（マスターデータ読み取りのみ）

### 4.6 スコープ外（DEFERRED）

demon/stage 草案の評価は「攻撃される側/構成全体」の評価軸が別設計のため対象外。
stage は WAVE 構成の TTK 合算（R-5 の延長）として将来検討。
