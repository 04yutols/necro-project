> 作成日: 2026-05-28  
> 深刻度: 🟡 Medium  
> 関連: IMPROVEMENTS.md / 「普通のWebゲームのデータ公開問題」

---

## 1. 問題の整理

### 現状の攻撃経路

```
ユーザーがブラウザコンソールで実行:
  await processStageResultAction('area1_boss', {})
  → ボスを一度も倒していないのにドロップ・EXP・クリア記録が入る
```

`processStageResultAction` は認証と stageId の存在確認しかしていない。  
「実際にバトルを開始・プレイした」という証拠を要求しないため、  
**任意のステージ報酬をAPIで直接取得できる**。

### 現状の防御ラインの評価

| チェック | 現状 | 問題 |
|---------|------|------|
| 認証（ログイン済みか） | ✅ auth() で確認 | — |
| ステージ存在確認 | ✅ mds.getStage() で確認 | — |
| ステージ解放済み確認 | ❌ **サーバーで未実施** | クライアントのみ（AreaMap） |
| バトル開始の証跡 | ❌ **なし** | コンソールから直接呼べる |
| ドロップ抽選 | ✅ サーバー側で実施 | 確率操作は不可 |

### この設計で防ぐもの・防がないもの

| シナリオ | 対策後 |
|---------|--------|
| コンソールから直接 processStageResultAction を呼ぶ | ✅ トークンなしで弾く |
| 未解放ステージの報酬を取る | ✅ 発行時に解放チェック |
| 第一発見者システムの不正取得 | ✅ バトル開始が必須になる |
| ランキングの totalDamage を偽って送る | 🔶 軽減（開始記録は残る）が完全防止ではない |
| バトルを開始してすぐ result を送る（無戦闘チート） | ❌ 防がない（サーバー再現が必要） |

「バトルを戦わずに報酬を取る」を防ぐのが目的。  
ダメージ数値の改ざんはランキング用のリスクであり、別問題として扱う。

## 2. 設計概要

### 基本フロー

```
[マップ画面]
  ↓ ステージノードをタップ → 「出撃」ボタン

[startStageAction(stageId)]  ← 新規 Server Action
  サーバー:
    1. 認証確認
    2. ステージ解放チェック（DBの clearedStages を参照）
    3. tokenId = crypto.randomUUID()
    4. Redis に保存: stage:token:{tokenId} → {userId, stageId, issuedAt}  TTL=3600s
    5. tokenId をクライアントへ返す

[BattleCanvas]
  ← tokenId を props / Zustand で受け取りメモリに保持
  ← バトル実行（変更なし）
  ↓ クリア検知

[processStageResultAction(stageId, tokenId, meta)]  ← 引数に tokenId 追加
  サーバー:
    1. 認証確認
    2. Redis から stage:token:{tokenId} を取得
    3. 検証（存在・userId一致・stageId一致）
    4. Redis からトークンを削除（使い捨て）
    5. ドロップ抽選・DB保存（既存処理）
```

## 3. 詳細設計

### 3-1. トークンのデータ構造

```typescript
// src/types/stageToken.ts （新規）
export interface StageTokenPayload {
  userId:    string;
  stageId:   string;
  issuedAt:  number;  // Date.now()
}
```

### 3-2. Redis キー設計

```
Key :  stage:token:{tokenId}
Value: JSON文字列 { userId, stageId, issuedAt }
TTL :  3600 秒（1時間）
```

TTLが切れると Redis が自動削除するため、明示的な有効期限チェックは不要。  
同一 tokenId の再利用は「削除後の再取得失敗」で自動的に弾かれる。

**既存 Redis ユーティリティとの関係:**  
`RankingService.ts` が独自の `redisGet / redisSet` を持つが、TTL 付き SET が必要なため  
共通ライブラリ `src/lib/redis.ts` を新設し両者から使う形にする（後述）。

### 3-3. startStageAction（新規）

```typescript
// src/app/actions.ts に追加
export async function startStageAction(
  stageId: string,
): Promise<{ success: true; tokenId: string } | { success: false; error: string }> {
  // 1. 認証
  const session = await auth().catch(() => null);
  if (!session?.user?.id) return { success: false, error: 'SESSION_EXPIRED' };

  // 2. ステージ存在確認
  const normalizedStageId = resolveStageId(stageId);
  const stage = MasterDataService.getInstance().getStage(normalizedStageId);
  if (!stage) return { success: false, error: 'STAGE_NOT_FOUND' };

  // 3. ステージ解放チェック（サーバー側で初めて実施）
  const char = await prisma.character.findFirst({
    where: { userId: session.user.id },
    select: { clearedStages: true },
  });
  const cleared = char?.clearedStages ?? [];
  const isUnlocked = stage.unlockRequires.every(req => cleared.includes(req));
  if (!isUnlocked) return { success: false, error: 'STAGE_LOCKED' };

  // 4. トークン発行・Redis 保存
  const tokenId = crypto.randomUUID();
  const payload: StageTokenPayload = {
    userId:   session.user.id,
    stageId:  normalizedStageId,
    issuedAt: Date.now(),
  };
  await storeStageToken(tokenId, payload);  // src/lib/redis.ts の新関数

  return { success: true, tokenId };
}
```

### 3-4. processStageResultAction の変更点

```typescript
// 変更後のシグネチャ
export async function processStageResultAction(
  stageId:  string,
  tokenId:  string | null,    // ← 追加（null = 後方互換フェーズ）
  meta:     StageResultMeta = {},
): Promise<StageResultPayload>

// 検証ロジック（processStageResultForUser 冒頭に追加）
if (tokenId) {
  const tokenData = await consumeStageToken(tokenId);  // 取得 + 削除（アトミック）
  if (!tokenData) {
    return { success: false, ..., error: 'INVALID_TOKEN' };
  }
  if (tokenData.userId !== user.id) {
    return { success: false, ..., error: 'TOKEN_USER_MISMATCH' };
  }
  if (tokenData.stageId !== normalizedStageId) {
    return { success: false, ..., error: 'TOKEN_STAGE_MISMATCH' };
  }
}
// tokenId が null の場合は後方互換として通過（rollout フェーズ）
// → 移行完了後に null を拒否するよう変更する
```

### 3-5. src/lib/redis.ts（新規共通ライブラリ）

`RankingService` の private 関数を汎用化して移動する。

```typescript
// src/lib/redis.ts
export async function redisGet<T>(key: string): Promise<T | null>
export async function redisSet(key: string, value: unknown, ttlSec?: number): Promise<void>
export async function redisDel(key: string): Promise<void>

// トークン専用ラッパー
export async function storeStageToken(tokenId: string, payload: StageTokenPayload): Promise<void>
export async function consumeStageToken(tokenId: string): Promise<StageTokenPayload | null>
// consumeStageToken は GET + DEL を逐次実行（Upstash REST で GETDEL 相当）
```

**アトミック性について:**  
Upstash REST API は `GETDEL` コマンドをサポートする。  
`GET` → `DEL` の2ステップに分けると競合状態（同一トークンの並列送信）が起きうるため、  
可能であれば `GETDEL` 1コマンドで取得＋削除する。

## 4. Redis 未設定時の挙動（フォールバック）

本番環境（Neon + Upstash）では正常動作。  
ローカル開発・テスト環境では `UPSTASH_REDIS_REST_URL` が未設定の場合がある。

```typescript
async function storeStageToken(tokenId: string, payload: StageTokenPayload): Promise<void> {
  if (!isRedisAvailable()) {
    // Redis なし → トークンをスキップ（開発環境用フォールバック）
    console.warn('[StageToken] Redis unavailable, skipping token store');
    return;
  }
  await redisSet(`stage:token:${tokenId}`, payload, 3600);
}

async function consumeStageToken(tokenId: string): Promise<StageTokenPayload | null> {
  if (!isRedisAvailable()) {
    console.warn('[StageToken] Redis unavailable, skipping token validation');
    return REDIS_UNAVAILABLE_BYPASS;  // 検証をスキップするセンチネル
  }
  // ...
}
```

`processStageResultForUser` 側で `REDIS_UNAVAILABLE_BYPASS` を受け取った場合は通過させる。  
→ 開発中はトークンなしで動作を確認できる。本番では Redis 必須として運用する。

## 5. エラーコード一覧

| エラーコード | 発生条件 | クライアント側の表示 |
|-------------|----------|-------------------|
| `STAGE_LOCKED` | startStageAction で解放条件未達 | 「このステージはまだ解放されていません」 |
| `SESSION_EXPIRED` | 未認証 | ログイン画面へリダイレクト |
| `STAGE_NOT_FOUND` | 存在しない stageId | — (通常は発生しない) |
| `INVALID_TOKEN` | Redis に存在しない・期限切れ | 「バトルセッションが切れました。もう一度出撃してください」 |
| `TOKEN_USER_MISMATCH` | 他ユーザーのトークン | 「不正なリクエストです」 |
| `TOKEN_STAGE_MISMATCH` | 別ステージのトークン | 「不正なリクエストです」 |

## 7. 副次的メリット

1. **ステージ解放チェックがサーバーで行われるようになる**  
   現在はクライアント（AreaMap）のみ。`startStageAction` で DB の `clearedStages` を参照するため、  
   クライアント改ざんによる未解放ステージへのアクセスも防げる。

2. **バトル開始ログが取れる**  
   `storeStageToken` 呼び出し時刻 = バトル開始時刻としてログを残せる。  
   将来のランキング（クリアタイム）の改ざん検知に使える。

3. **RankingService の redis 関数が共通化される**  
   コードの重複が解消される。

## 8. 移行フェーズ

| フェーズ | 内容 |
|---------|------|
| Phase 1（実装直後） | tokenId を null 許容。送られた場合のみ検証。ログで未トークンリクエストを記録 |
| Phase 2（動作確認後） | tokenId を必須化。null を MISSING_TOKEN エラーで弾く |

現時点では Phase 1 で実装し、動作確認後に Phase 2 へ移行する。

## 9. テスト方針

| テストケース | 種別 |
|-------------|------|
| `startStageAction` が有効なトークンを返す | ユニット |
| 未解放ステージで `startStageAction` が `STAGE_LOCKED` を返す | ユニット |
| 有効なトークンで `processStageResultAction` が成功する | ユニット |
| 存在しない tokenId で `INVALID_TOKEN` を返す | ユニット |
| 別ユーザーのトークンで `TOKEN_USER_MISMATCH` を返す | ユニット |
| 別ステージのトークンで `TOKEN_STAGE_MISMATCH` を返す | ユニット |
| トークン再使用（2回目の送信）で `INVALID_TOKEN` を返す | ユニット |
| Redis 未設定時にフォールバックで通過する | ユニット |
| バトル開始 → クリア → DB 保存の E2E フロー | 統合（Redis Mock 使用） |
