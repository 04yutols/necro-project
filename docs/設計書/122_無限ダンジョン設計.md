## 1. コンセプト（決定反映）

**地下1階（B1）から下り続けるエンドコンテンツ「黄泉の階層」。**

- **Ch1テーマの B1〜B20 を1セットとして制作し、Ch2 リリースに同梱**（D-1/D-12裁定）。以降はアップデートの空き期間に応じて階層を追加する
- **周回コンテンツではない**（D-20）。ストーリークリア済みユーザーの飽き防止と、ステータス厳選のやり込み誘発が目的（D-4）— 厳選は本編で行い、その力試しの場が本コンテンツ
- **1階層 = 独立した高難度ダンジョン（3WAVE）**。クリアするごとに次の階層が解放される（D-4/D-6/D-11）。潜行run・連戦・チェックポイントの概念はない
- 名称:「黄泉の階層」でほぼ決定（D-3）。「深淵」は残滓と語が衝突するため不使用

### プレイヤー体験目標

1. 「あと1階だけ下りたい」— 到達階層が伸びる快感と、深層の壁による育成動機の往復
2. 「自分の編成はどこまで通用するか」— 最深到達階層ランキングによる競争
3. 「アップデートのたびに続きが開く」— 長期のコンテンツ供給ライン

### コアループ

```
専用タブ「黄泉の階層」 → 階層選択（解放済みの最深階に挑戦）
  → 3WAVE バトル（通常ステージと同じフロー・高難度）
  → クリア → 初クリア報酬 + 次階解放 → 拠点
```

## 5. 技術設計（調査 2026-07-04 / v2 で決定反映）

### 5.1 最重要の結論: 「無限」は列挙で実現できる

`stages.json` / `areas.json` は3か所で静的 import されており（`MasterDataService.ts:6` / `AreaMap.tsx:7-8` / `BattleCanvas.tsx:9-10`）、ランタイムのステージ生成経路は存在しない。しかし本件は「アップデートごとに有限階層を追加する」モデルなので、**手続き生成（真の無限）は不要**（D-13 決定: まずは JSON 管理、必要になったら移行）:

- **各階を実ステージノードとして `stages.json` に列挙**し、`unlockRequires` で B1→B2→… と鎖状連結すれば、開始（`startStageForUser`）・戦闘（BattleCanvas）・リザルト＆報酬（`processStageResultForUser`）まで**全経路が無改造で通る**
- 独立階層方式（D-4/D-6）の決定により、これが MVP ではなく**最終形**になった — 連戦・run 管理の追加実装は不要
- 章/アップデート単位の階層追加も「JSON にノードを足すだけ」= FR-7 充足
- admin の StageForm / stageBalance / stageGraph / SimulatorClient がそのまま制作・検証・運用管理に使える（= FR-10 / D-19 充足）

### 5.2 敵スケーリング

- `EnemyScaling.ts:10` `applyEnemyStatScale` — **hp/atk/def のみ**、WAVE 単位（`StageWaveData.statScale`）。BattleEngine（`BattleEngine.ts:1007`）と BattleCanvas（`BattleCanvas.tsx:380, 2240`）の両経路に配線済み。サーバ側メトリック上限（`actions.ts:429`）でも参照
- **各階の全 WAVE に計算済み倍率を焼き込む**（エンジン改修不要）。倍率式はオーサリング時のジェネレータスクリプト側に持ち、生成後は admin で通常ステージ同様に編集可能
- 制約: spd/crit はスケール不可（`ENEMY_STAT_SCALE_KEYS` 拡張が必要 → 現状 hp/atk/def で設計）。`stageBalance.ts:74` の3倍超警告は高難度用途として許容される
- 既知の TECH_DEBT **L-3**（BattleEngine が per-wave statScale を受けない不整合）について: 本設計は「階内の全 WAVE に同一倍率を焼き込む」ため、live battle（BattleCanvas 駆動）・metric cap とも per-wave 値で一致し、L-3 の実害は本件では発生しない

### 5.3 改修が必要な範囲（v2: 大幅縮小）

独立階層 + DungeonRun 廃止の決定により、残る改修は **3点**（2026-07-04 実装ギャップ調査で1点追加）:

| 項目 | 内容 | 規模感 |
|---|---|---|
| 最深階層ランキング | `RankingType` に `DUNGEON_FLOOR` 追加 + `PlayerStats.bestDungeonFloor` 列 + `getRanking`/`recordStageClear`/`route.ts`/`invalidate` 拡張（命名は §7 を正とする） | 小 |
| 専用タブ UI | `useGameStore` の tab union に追加 + `BottomNavBar.TABS` + `page.tsx` renderMainContent + 解放ゲート（LAB の `isAbyssalResidueUnlocked` 方式 `BottomNavBar.tsx:29` 踏襲）+ 階層選択スクリーン | 中 |
| 専用エリア登録 + MAP 除外フィルタ | `areas.json` に専用エリア（`ch1_area99`）登録は**監査上必須**（未登録だと admin 監査・`data:audit`・CI が FAIL）。かつ登録すると `WorldMapSystem.buildWorldAreas` の fallback でワールドマップに出現するため、`WorldMapSystem`/`AreaMap`/`getNextAvailableStage`/`getStageLineSegments` に黄泉除外フィルタが必要 | 小〜中 |

### 5.4 注意事項

- `clearedStages` は生 ID を無制限蓄積（`actions.ts:857-859`）。20階×アップデート数なら軽微。階層進行の正は `clearedStages`+`unlockRequires`（本編と同一機構）で一本化し、`bestDungeonFloor` はランキング用の派生値とする

### 6.1 階層難易度曲線（stat別指数 + 再アンカー運用）

既存 MINION/ELITE/BOSS プールを再利用し（D-8 決定）、係数のみ階層 n で変化させる:

```
statScale_hp(n)  = 1.09 ^ (n-1)     // HP > ATK > DEF の順で速く伸ばす
statScale_atk(n) = 1.07 ^ (n-1)     // = 長く殴り合うが一撃では溶けない
statScale_def(n) = 1.045^ (n-1)
spd はスケール不可（EnemyScaling の制約）→ 対象外
```

アンカー検証（倍率 1.0 = Ch1 素体。ボス階は真ボス ossuary_wyrm_lord HP90/ATK14/DEF10 を基準テンプレに使用）:

| 階層 | HP/ATK/DEF 倍率 | ボス階テンプレ適用後 | プレイヤー想定 |
|---|---|---|---|
| B1 | 1.0 / 1.0 / 1.0 | —（B1は通常階: MINION 素体そのまま = Ch1中盤相当） | 入口。Ch1クリア編成なら余裕 |
| B10 | 2.17 / 1.84 / 1.49 | HP195 / ATK26 / DEF15 | Ch1クリア直後水準（Lv13・SR武器、ATK計≈70）で相打ち級 = **壁** |
| B20 | 5.14 / 3.62 / 2.31 | HP463 / ATK51 / DEF23 | SSR ilv90込みフル厳選（ATK≈200）でギリギリ |
| B40(参考) | 28.8 / 14.0 / 5.6 | HP2595 / ATK196 | 将来セット（※再アンカー前提） |

- 隣接階の倍率は最大1.09倍のため doc72 の EHP急墜アラート（2.5倍WARN）に整合
- **運用（D-19 決定）**: 式の形は固定し、セット追加ごとに係数を再アンカー。焼き込み後の値は管理画面（StageForm）で個別調整可能とし、ゲームバランスとの整合を admin バリデータ + シミュレータで取る
- ⚠️ **BAL-2 是正後の更新値**: 上表は是正前の ossuary_wyrm_lord（hp90/def10）基準。是正案（hp180/def24 → doc123 §B）適用後は **B10=HP391/ATK26/DEF36、B20=HP925/ATK51/DEF55** に更新。また「B20 想定 ATK≈200」は BAL-1 是正後に陳腐化するため **260〜320（Ch2序盤・残滓部分投資）** へ更新推奨（doc123 §B-3）。最終確定は §6.5-3 のシミュレータ実測で
- ⚠️ **U-2**: リリースが Ch2 同梱に決定したため、「B10 = Ch1クリア直後の壁」というアンカーが Ch2 進行中プレイヤーには緩く感じられる可能性がある。§6.5 のシミュレータ実測時に Ch2 想定装備水準でも検証すること

### 6.2 階層構成テンプレート（v2: 1階=3WAVE・本編互換 — D-18 決定）

各階は本編ステージと同じ 3WAVE 構成（`waveCount:3`、role: WARMUP/ELITE/BOSS 等の既存パターン）で制作する。非周回コンテンツのため、旧仮説（1階=1WAVE・周回テンポ最優先）は廃棄。

| 階層 | WAVE 構成の目安 | 想定戦闘時間 |
|---|---|---|
| 通常階（n%5≠0） | WARMUP ×2 + 締め（MINION 中心） | 2〜3分 |
| 精鋭階（n%5=0） | WARMUP → SHIELD/ELITE → ELITE（霊的防壁ギミック有効） | 2.5〜3分 |
| ボス階（n%10=0） | WARMUP → ELITE → BOSS（ENRAGE/AV_DELAY/REVIVE/SUMMON 有効化） | 3〜4分 |

B1〜B20 の初回踏破は合計 40〜60分規模の挑戦型コンテンツとなる（1階ずつ独立挑戦・リトライ自由）。

### 6.3 報酬設計（v2: 初クリア報酬のみ — D-10 / A-1 裁定）

- **原則**: 専用レアリティ・専用装備を新設しない。残滓の絶対数値レンジも動かさない。**周回 farm 報酬は置かない**（非周回コンテンツ。旧 Layer1/Layer3 構想は廃棄）
- **各階の初クリア報酬**: ゴールド・強化素材（`firstClearGuaranteed` パターン流用）
- **節目チェスト（5/10/15/20階の初到達）**: 武器強化素材・確定残滓に加え、目玉として「**残滓オプションを1枠自由に設定できるアイテム**」等の特別報酬を検討（仕様 → U-3。BLK-1 解消が前提）
  - ⚠️ **v2.2 訂正**: 当初案の「大量ゴールド」は現行型では実装不可 — `DropEntry` に GOLD 型が存在せず、唯一の通貨経路 `baseGold` は毎回払い出しのため黄泉では 0 固定（doc125 前提訂正#8）。→ **U-6 裁定済み（2026-07-05）: 通貨なしで確定**
- **UR(hidden) 抽選は対象外**（D-20 決定: 非周回のため不要）
- **シーズン報酬**: Ch2 時点では導入しない（A-1 裁定）。将来導入する場合に備えた設計担保のみ → U-4
- リプレイ（クリア済み階の再挑戦）は可能だが報酬は付けない、または名目程度に留める（経済インフレ源にしない）

### 6.4 リソース/挑戦制限（決定）

- **HP/Energy は階層ごと全回復**（D-4 決定）。各階が独立ダンジョンなので本編と同じ「戦闘後全回復」（doc81 §8）がそのまま適用される
- **挑戦回数無制限**（D-5 決定。本編の柱「STAMINA FREE」と一貫）
- 全滅ペナルティなし（独立階層のためリトライするだけ。旧「1〜2階後退」案は run 廃止に伴い対象消滅）

### 6.5 実装前の必須アクション

1. BLK-1 残滓スケール再設計を先行（最重要・BAL-1）
2. BLK-2 敵HP逆転の是正（BAL-2・Ch1 Phase 2 と合流）

- `bestDungeonFloor` の更新は `recordStageClear` 経路で `max(現値, クリア階)` — ステージ ID `yomi_b01`〜`yomi_b20`（確定・実装計画書 M2-1）からパーサ `/^yomi_b(\d+)$/` で階層番号を導出
- キャッシュキー `ranking:DUNGEON_FLOOR:global:{limit}` を `invalidate()` に追加。既存「Redis=キャッシュのみ・真実は Postgres」構造を踏襲（ZSET 化はスコープ外）

### 7.3 マイグレーション影響

- `PlayerStats` への default 付き列追加のみ（PG11+ でメタデータ操作・ロック軽微）。**新規テーブルなし**
- Neon dev ブランチで `migrate dev` → 確認 → 本番 `migrate deploy`（doc119 運用踏襲）

### 7.4 実装順序案

`PlayerStats` 列追加 → `RankingType`/`RankingService` 拡張 → ステージデータ生成（B1〜B20） → 専用タブ UI → Server Actions 配線（初クリア報酬・世界ログ節目フィルタ）。※playerState v4 移行は U-7 決定（2026-07-05）により削除。

### 7.5 不採用アーカイブ（将来「連続潜行モード」を作る場合の参照）

独立階層方式の決定（D-4/D-6/D-11、A-2 裁定）により以下は**不採用**。設計自体は健全だったため、将来連戦モードを導入する場合の出発点として要点のみ残す:

- **`DungeonRun` テーブル + 行内カウンタトークン**: `consumeStageAttempt` と同じ条件付き updateMany + 影響行数チェックを run 1行の上書きで繰り返す方式。単調性ガード（飛び番拒否）・最小所要時間ガード・`floorCapAtStart` スナップショットで改竄耐性を確保。行数 O(1) で Neon 書き込みコストに有利
- **報酬の都度銀行化**（`rewardBanked*`）: フロアクリアごとに確定加算し run 失効でも失われない。push-your-luck 設計と切断悪用対策を両立
- **フロア境界の partySnapshot**: 値をデノーマライズして保持（ダングリング参照回避）。ターン単位再開は BattleEngine への永続化責務新設になるため非推奨
- **`DungeonSeasonRecord`**（`@@unique([userId, seasonId])`）: シーズン導入時に `bestDungeonFloor`（生涯・不可逆）とは別軸で併設する案 → U-4
