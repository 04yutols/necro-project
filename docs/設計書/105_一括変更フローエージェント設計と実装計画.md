## 1. 目的と位置づけ

仕様変更時、「条件に合致する複数エンティティへ同じ変更を一括適用」したい場面がある:

- 「MAGIC_AOE で mpCost 15 以下の全スキルの power を 0.1 下げる」
- 「全 MINION エネミーの def を 10% 上げる」
- 「rarity が R の武器の subOption value を +0.5 する」

現状は 1 件ずつ手編集。**Agent D は自然言語の一括指示を受け、対象を抽出し、変更を diff で提示し、
全変更を決定論ゲートで検証してから一括適用する。**

### 設計の核心（doc100 と同一・最重要）

> **LLM は「自然言語 → 構造化スペック（条件 + 操作）」の変換だけを行う。**
> 実際のフィルタ抽出と数値変更は**決定論エンジン**が行う（LLM に値を計算させない＝捏造が起きない）。
> 正しさは既存 per-content バリデータ + `auditMasterData` が判定し、永続化は既存 `saveEntry` のみ。

これにより「LLM が 200 件を 1 件ずつ書き換えて間違える」リスクが原理的に存在しない。
LLM が触るのは**たった 1 つの小さな JSON（BulkSpec）**だけ。

## 2. アーキテクチャ

```
[/admin/agents/batch（新規ページ）]  自然言語で一括指示
      │
      ▼
Server Action: previewBulkChangeAction(instruction)   ← 非破壊（書き込まない）
      │
      ▼
[LLM] bulkAgent: 指示 → BulkSpec（file / filter[] / operation[]）   ← LLMはここだけ
      │  BulkSpec をスキーマ検証（不正なら再生成）
      ▼
[決定論] applyBulkSpec(entities, spec)  ← フィルタ抽出 + 数値変更（純関数・LLM不使用）
      │  変更された各エンティティの { id, before, after, diff }
      ▼
[二層ゲート] 各変更を per-content バリデータ + auditMasterData(override) で検証
      │  - 変更後に新たな FAIL が出ないか（auditFix と同じ仕組み）
      ▼
UI: 変更 N 件の diff テーブル + 検証サマリ（FAIL/WARN 件数）を表示
      │  ユーザーが確認
      ▼
applyBulkChangeAction(spec)  ← 承認後のみ。各 entity を saveEntry で永続化（+ 適用後に再監査）
```

**ポイント**: preview は完全に非破壊（メモリ内のみ）。ディスクへ書くのは承認後の apply だけ。

## 3. 詳細設計

### 3.1 構造化スペック（BulkSpec）

LLM が生成する唯一の出力。小さく・検証しやすい。

```ts
type Comparator = '==' | '!=' | '<' | '<=' | '>' | '>=' | 'in' | 'exists';
type Condition = { field: string; op: Comparator; value?: unknown }; // field はドット記法（stats.atk 等）
type MutationOp = 'set' | 'add' | 'mul' | 'clampMin' | 'clampMax';
type Mutation = { field: string; op: MutationOp; value: number | string | boolean };

type BulkSpec = {
  file: 'enemies'|'skills'|'stages'|'jobs'|'items'|'materials'|'monsters'|'demonForms'|'areas';
  filter: Condition[];     // AND 結合
  operation: Mutation[];   // 上から順に適用
  note?: string;           // LLM による意図の言語化（UI 表示用）
};
```

例（「MAGIC_AOE で mpCost<=15 の power を 0.1 下げる」）:
```json
{ "file": "skills",
  "filter": [ {"field":"type","op":"==","value":"MAGICAL"},
              {"field":"targetType","op":"==","value":"ALL_ENEMIES"},
              {"field":"mpCost","op":"<=","value":15} ],
  "operation": [ {"field":"power","op":"add","value":-0.1} ] }
```

### 3.2 決定論エンジン（`bulk/bulkEngine.ts`・純関数）

```ts
matchesFilter(entity, conditions): boolean        // ドット記法でフィールド取得し比較
applyMutations(entity, mutations): entity         // set/add/mul/clamp を順次適用（数値型を保つ）
applyBulkSpec(entities: Record<string,object>, spec): BulkChange[]
//   → 各 BulkChange = { id, before, after, diff: FieldDiff[] }（diff は auditFix/diff.ts を再利用）
```
- **LLM 不使用**。フィルタ一致と数値演算のみ。`mul` は丸め規則を持つ（小数 power は桁維持、整数 hp は四捨五入など型に応じて）。
- スペックの `operation` 値はユーザー指示由来（例 -0.1）。エンジンはそれを**そのまま**適用する（捏造しない）。

### 3.3 二層ゲート（既存資産の再利用）

各 BulkChange の `after` を:
1. **per-content バリデータ**（`auditFix/scopeRegistry.ts` の `getScopeEntry(file).validate`）で検証。
2. **in-memory 監査**（`auditMasterData({ [file]: { ...全変更を適用したコレクション } })`）で全体整合を確認。
   - ベースライン FAIL 集合と比較し、**新規 FAIL を 0 件**に保つ（Agent B と同じロジック）。

→ 一括変更が**1 件でも壊れたら**ユーザーに警告（該当 id を明示）。全 PASS のときのみ「適用」を有効化。

### 3.4 LLM の役割（`bulkAgent.ts`）

- 入力: 自然言語指示 + 各 file のフィールド一覧（ヒント）。
- 出力: BulkSpec（JSON）。スキーマ検証（file 列挙・op 列挙・field 文字列・value 型）。
- 不正スペック（未知 file / 不正 op）は再生成（最大 maxAttempts）。
- **値の計算はしない**。「10%上げる」→ `{op:'mul', value:1.1}`、「0.1下げる」→ `{op:'add', value:-0.1}` への**翻訳**のみ。

### 3.5 適用（`applyBulkChangeAction`）

- 承認後のみ。`applyBulkSpec` を再実行して最新 diff を取り、各 `after` を **既存 `saveEntry(file, id, after)`** で保存。
- 全件保存後に `auditMasterData()` を再実行し、結果を返す（UI が再監査表示）。
- 失敗時は途中まで保存済みの可能性 → 保存は entity 単位で結果を集計し、失敗 id を返す（部分適用の可視化）。

## 5. プロンプト設計（bulkAgent）

```
あなたは Necromance Brave のデータ運用担当です。一括変更の自然言語指示を、構造化スペック(JSON)に
**翻訳**してください。あなたは値を計算しません。指示を filter（条件）と operation（操作）に分解するだけです。

# 指示
{instruction}

# 対象ファイルとフィールド（filter/operation で使えるキー）
{file → field 一覧（型付き）}

# 出力（このJSONのみ）
{ "file": "...", "filter": [ {"field":"...","op":"==|!=|<|<=|>|>=|in|exists","value":...} ],
  "operation": [ {"field":"...","op":"set|add|mul|clampMin|clampMax","value":...} ],
  "note": "この一括変更の意図を1文で" }

# 厳守
- 「N%上げる」→ mul value=1+N/100。「N%下げる」→ mul value=1-N/100。「X 下げる/上げる」→ add value=∓X。
- file は対象1つ。filter は AND。field はドット記法（stats.atk 等）。
- 値の計算結果を書かない（mul/add の係数だけ書く。各エンティティへの適用はシステムが行う）。
```

## 6. UI 設計（/admin/agents/batch）

- **指示入力**: テキストエリア + 「プレビュー」。
- **BulkSpec 表示**: LLM が解釈した file / filter / operation（人間が意図を確認できる）+ note。
- **diff テーブル**: 変更される N 件。各行 `id ・ field ・ before → after`。
- **検証サマリ**: per-content / 監査の FAIL・WARN 件数。FAIL があれば該当 id を赤表示し「適用」を無効化。
- **適用**: 全 PASS 時のみ有効。押下で `applyBulkChangeAction` → saveEntry 一括 → 再監査結果表示。
- **0 件ヒット**時は「条件に一致する対象がありません」。

## 7. 安全性

| リスク | 対策 |
|---|---|
| LLM が値を誤計算 | LLM は係数の翻訳のみ。数値適用は決定論エンジン |
| 一括変更が別の違反を誘発 | 全変更を per-content + auditMasterData で検証し新規 FAIL を 0 件に保つ。FAIL 時は適用不可 |
| 意図と違う対象に当たる | BulkSpec（filter）を UI に明示。diff で全対象を確認してから適用 |
| 破壊的・不可逆 | preview は非破壊。適用は承認後のみ。適用前に diff 確認必須。将来: 適用前スナップショット保存 |
| 大量変更の取り違え | ヒット件数と全 diff を提示。件数が想定外なら適用しない判断ができる |
| 開発環境外実行 | `assertDev()` 踏襲 |

## 8. テスト計画

### 8.1 ユニット（jest・API不使用・**ディスク非依存**）
- `bulkSpec.test.ts`: BulkSpec スキーマ検証（不正 file/op/field を弾く）。
- `bulkEngine.test.ts`: **合成エンティティ**（テスト内で定義したオブジェクト）に対し:
  - filter 一致（==/<=/in/exists、ドット記法 stats.atk）。
  - mutation（set/add/mul/clamp）が型を保ち正しく計算（add -0.1、mul 1.1、整数四捨五入）。
  - 非一致エンティティは不変。diff が変更フィールドのみ。
  > **`src/data/master/*.json` は読まない・書かない。** すべてテスト内の合成データで完結する。

### 8.2 ライブ統合（`npm run agent:verify-bulk`・Vertex・**保存しない**）
- マスターデータを**ディープコピー**して読み込み、NL 指示 → BulkSpec → `applyBulkSpec`（メモリ内）。
- アサーション: 期待した file/op に翻訳された／対象件数 > 0／diff が operation と一致／検証 PASS。
- **`saveEntry` を一切呼ばない**。スクリプトはファイルを書き換えない（preview 相当のみ）。
- 既存データの値を変えないため、検証後にコピーを破棄するだけ（元 JSON は不変）。

### 8.3 回帰
- `npx tsc --noEmit` / 全 jest（既存 520+ 件が不変）/ `/admin/agents/batch` HTTP 200。

> **テスト非破壊の担保**: ①ユニットは合成データのみ。②ライブはディープコピー + saveEntry 不使用。
> ③`applyBulkChangeAction`（実保存）はテスト・スクリプトから呼ばない。④CI でも `git diff src/data/master` が空であることを確認可能。
