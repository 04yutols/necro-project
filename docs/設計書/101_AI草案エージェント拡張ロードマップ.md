## 1. 方針（Agent A で確立したパターンの横展開）

各コンテンツで以下の 3 点セットを再利用する:

1. **素性付きコンテキスト**: 既存データ + 参照可能 ID + 設計指針（設計書 or 実データから学習）をプロンプトへ
2. **決定論的バリデータ**（純関数）: 構造・参照整合・数値スケール・帯逸脱を機械判定（PASS/WARN/FAIL）
3. **生成→検証→FAILなら再生成** ループ（LangGraph）+ フォーム流し込み（保存は既存 Server Action）

`gemini.ts`（クライアント・リトライ）と `thinkingBudget.ts`（動的予算）はそのまま共通利用できる。

## 3. 個別の設計メモ（実装時の要点）

### 🔴 #2 skills（スキル）— 最優先

**理由**: 最も多く参照される（`enemies.necromance.skillIds` / `jobs.skills` / 味方魔物）。
かつ **設計書 19 が「数値の憲法」として cost 帯ごとの power 倍率表を既に定義済み**なので、
決定論的ゲートが即座に作れる（ROI 最大）。

- スキーマ: `id, name, mpCost, power, type(PHYSICAL/MAGICAL), element, attackType, targetType, effectKey, description`
- バリデータ:
  - `power` を **19§2.2 の分類×コスト帯テーブル**に照合（範囲外 FAIL/WARN）
  - `type / element / attackType / targetType` 列挙チェック
  - `mpCost` を 19§3 のコスト設計式と照合
  - `effectKey` の命名規約、`id` 重複/snake_case
- プロンプト: 既存スキルの power 分布 + 分類テーブルを提示し、インフレ/デフレを防ぐ
- 連携候補: 既存サブエージェント **`balance-designer`** の知識と重複 → 統合検討

### 🔴 #3 demonForms（魔神化）— 高

**理由**: ゲームの核心機能。既に **`demonization-designer` サブエージェント**が存在する（Tier設計ルールを持つ）。
これを Gemini ベースの管理画面フローに移植/接続する形が自然。

- スキーマ: `jobId, formName, tier(1/2), concept, effectA{statBoosts,flags}, effectB{riskType,onAttackEffect}, ultimateSkill{damage{power,element,targetType,attackType,flags}, lingering{type,duration}}, visual`
- バリデータ:
  - `jobId` → jobs.json 参照（FAIL）
  - `tier ∈ {1,2}`、`ultimateSkill.damage.power` を **16§3 の魔神技 power 基準**に照合
  - `statBoosts` の倍率レンジ（過剰インフレ WARN）、`flags / onAttackEffect / lingering.type` 列挙
  - 同 jobId × tier の重複チェック
- 注意: Tier1=直感的な強さ / Tier2=リスク&リワード（悪魔合体）の設計ルール（doc16）を踏襲

### 🟡 #4 stages（ステージ）— 中（複合・参照重い）

**理由**: 第2章エリア構築に必須だが、複合オブジェクトで参照整合が多い。

- スキーマ: `id, name, chapter, area, nodeType, element, difficulty, waveCount, areaGimmick, unlockRequires[], waves[]{enemyIds[]}, rewards{baseExp,baseGold,dropTable[]}, position`
- バリデータ:
  - `waves[].enemyIds` → enemies.json 参照（FAIL）
  - `unlockRequires` → 他 stage 参照（FAIL）、循環依存チェック
  - `nodeType / areaGimmick / element` 列挙、`difficulty` と報酬カーブの整合（章進行）
  - `rewards.dropTable` の itemId 参照 + rate 0〜1
- 連携: 95_エリアマップ管理とステージ反映設計 の制約を踏襲

### 🟡 #5 monsters（味方魔物）— 中

**理由**: プレイヤー所持の魔物ロスター。enemies の味方化検証ロジックをほぼ流用できる。

- スキーマ: `name, tribe, cost, stats, resistances`（+ 編成で skills/spiritCore 等）
- バリデータ: `tribe` 列挙、`cost` と stats の釣り合い、stat スケール、resistances スケール（enemy 検証を再利用）

### 🟡 #6 items（武器）— 中

- スキーマ: `id, name, type, rarity/weaponRarity, archetype, rank, ilv, isUnique, stats, subOptions[]{type,value}, passiveA/B{nameJa,descTemplate,values[]}, flavor`
- バリデータ:
  - `rarity / archetype / subOption.type` 列挙
  - `passive.values[]` の長さ（rank 段階数）と rarity 別レンジ
  - `descTemplate` の `{value}` プレースホルダ整合、`id` 重複
- 参照: enemies.dropTable から参照される（被参照側）

### 🟢 #7 materials（素材）— 低（簡単・早い勝ち）

- スキーマ: `id, name, quantity, expValue, rarity`
- バリデータ: `rarity` 列挙、`expValue` 帯、`id` 重複。最小工数で 1 つ追加できる。

### 🟢 #8 jobs（職業）— 低頻度・複合

- スキーマ: `name, displayName, nameEn, title, tier, category, baseAttackType, role, description, statModifiers, energyCurve, levelBonuses, skills[]{level,skillId}`
- バリデータ: `category / baseAttackType` 列挙、`statModifiers` は 1.0 前後の倍率レンジ、`skills[].skillId` 参照、`tier`。
- 注: 12職業は概ね固定。新規追加頻度は低いが、追加時の整合確認には有用。

### 🟢 #9 areas（エリア）— 低（メタデータ）

- スキーマ: `id, chapter, area, nameJa, nameEn, description, color, position, sortOrder`
- バリデータ: `chapter/area` の一意性・連番、`color` HEX、`position` 範囲。

### 🔵 #10 story（ストーリーシーン）— 別系統

- 100 の提案 §3.4「ストーリーシーン生成フロー」/「Agent C」に相当。
- 検証は narrative 整合（キャラ口調・固有名詞・前後シーン）で、数値ゲートとは性質が異なる。
- 既存サブエージェント **`narrative-director`** の知識を活用。dialogue 配列の複数案生成 + 人間選択。

## 4. 推奨実装順

1. **skills** 🔴 — doc19 の表で決定論的ゲートが即作れる。被参照の中心。
2. **demonForms** 🔴 — 核心機能 + 既存 demonization-designer 連携。
3. **materials** 🟢 — 簡単。共通基盤（Server Action + パネル）の横展開テンプレ確立に好適。
4. **items** 🟡 → **monsters** 🟡 → **stages** 🟡
5. **jobs / areas** 🟢（必要時）
6. **story** 🔵（narrative 系として別途）

> 共通化の機会: `AIEnemyDraftPanel` を汎用 `AIDraftPanel<T>` に一般化し、
> 各コンテンツは「プロンプト構築 + バリデータ」だけ差し替える構成にすると追加コストが下がる。

---

## 5. 既存サブエージェントとの関係

プロジェクトには設計知識を持つサブエージェントが既にある（`balance-designer` / `demonization-designer` /
`economy-designer` / `narrative-director` 等）。これらは「設計知識」、本ロードマップの管理画面エージェントは
「決定論的ゲート + フォーム流し込み + 永続化」を担う。両者は競合せず、
**サブエージェントの設計ルールをバリデータ/プロンプトに落とし込む**形で接続するのが望ましい。
