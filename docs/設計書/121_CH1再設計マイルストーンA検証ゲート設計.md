# CH1再設計 マイルストーンA 検証ゲート詳細設計

> 作成日: 2026-06-27  
> 対象計画: `docs/progress/CH1_REDESIGN_実装計画.md` マイルストーンA  
> 対象範囲: `/admin/audit` へ G1/G2 の検証ゲートを追加する。マスターデータ変更は行わない。

---

## 1. 目的

第1章ステージ拡張では、既存 stage ID を維持したままノード数と解放順を増やす。ここで壊れやすいのは次の2点である。

1. `stages.json` の `unlockRequires` が作る解放グラフが、循環・未到達・孤立を含んでも UI 上では気付きにくい。
2. チュートリアルや残滓解放など、コード側に残る stage ID 参照が、ステージ再配置やID変更で黙って欠落する。

マイルストーンAでは、この2点を `/admin/audit` の FAIL/WARN として機械検知できる状態にする。以降の C/B 実装前に網を張ることが目的なので、ステージJSONの再結線や新規ノード追加は扱わない。

---

## 2. 現状整理

### 2.1 既存 audit

`src/app/admin/actions.ts` の `auditMasterData()` は以下を検査済み。

- 各マスターのキーと `id` フィールド整合
- `stages.waves[].enemyIds` → `enemies`
- `jobs.skills[].skillId` → `skills`
- `stages.rewards.dropTable` / `firstClearGuaranteed` → `items` / `materials` / `enemies`
- `stages.unlockRequires[]` の参照先 stage ID 存在
- `demonForms.jobId` → `jobs`

ただし、`unlockRequires` を個別参照として見るだけで、グラフ全体の到達可能性・循環は見ていない。

### 2.2 コード内 stage ID 参照

現時点でマイルストーンAの検査対象にするコード参照は以下。

| 参照元 | stage ID | 用途 |
|---|---|---|
| `AbyssalResidueUnlockSystem.ts` | `area1_node3` | 深淵の残滓解放条件 |
| `data/tutorial/triggers.ts` | `tutorial_battle_01`, `area1_node1` | バトル基礎チュートリアル開始 |
| `data/tutorial/triggers.ts` | `area1_node1`, `area1_node2`, `area1_boss` | クリア後チュートリアル連鎖 |

`tutorial_battle_01` は現状 `stages.json` に存在しない仮想/旧チュートリアルIDであり、現行第1章では `area1_node1` が実ステージとして同じ役割を担っている。G2 は「マスターに存在すべきコード参照」を検査するゲートなので、仮想IDは集約対象から除外する。

## 3. 実装方針

### 3.1 G1: 解放チェーングラフ健全性

新規純関数 `src/lib/agent/stageGraph.ts` を追加する。

```ts
export type StageGraphFinding = {
  level: 'PASS' | 'WARN' | 'FAIL';
  id: string;
  message: string;
};

export function validateStageGraph(stages: Record<string, unknown>): StageGraphFinding[];
```

検査対象は `stages.json` 全体。`stageBalance` が保存時の1ノード検証を担うため、ここではグラフ全体の性質だけを見る。

#### 到達可能性

- ルートは `unlockRequires` が空配列、または配列でない/未定義のステージとする。
- `unlockRequires` は「前提 → 現ステージ」の有向辺として扱う。
- 全ルートから DFS/BFS して到達集合を作る。
- 到達できないステージがあれば `FAIL`。
- 全ステージ到達可能なら `PASS` を1件出す。

#### 循環検出

- 各ステージから `unlockRequires` 方向へ DFS し、`visiting` 中の再訪で循環を検出する。
- 循環があれば `FAIL`。メッセージには `A -> B -> A` 形式の経路を含める。
- 循環がなければ `PASS` を1件出す。

#### 孤立ノード

- `unlockRequires` が空のルートのうち、他ステージから参照されていないものを孤立候補とする。
- ただし、複数ルートを許容するため、孤立は `WARN` に留める。
- 第1章には `area1_safe` と `area1_node1` のような初期開放ルートが共存し得るので、G1 は孤立を FAIL にしない。

#### dangling 参照

`unlockRequires` が存在しない stage ID を指すケースは既存 audit の「Unlock conditions」が検出済み。G1 では dangling を主目的にしない。ただし循環/到達性計算のため、存在しない参照は辺から無視する。

### 3.2 G2: コード参照 stage ID の存在検査

コード内 stage ID を各責務元で named export 化し、`src/data/stageRefs.ts` で集約する。

```ts
export type CodeReferencedStageId = {
  id: string;
  referencedBy: string;
};

export const CODE_REFERENCED_STAGE_IDS: CodeReferencedStageId[];

export function validateCodeReferencedStageIds(
  stageIds: ReadonlySet<string>,
): StageReferenceFinding[];
```

#### named export

- `AbyssalResidueUnlockSystem.ts`
  - 既存 `ABYSSAL_RESIDUE_UNLOCK_STAGE_ID` を利用する。
- `data/tutorial/triggers.ts`
  - `TUTORIAL_BATTLE_STAGE_IDS`
    - `area1_node1` を含む。
    - 旧/仮想ID `tutorial_battle_01` は runtime 判定の互換用に残してよいが、G2 集約からは除外する。
  - `TUTORIAL_CHAIN_STAGE_IDS`
    - `PARTY_FORMATION: area1_node1`
    - `WEAPON_EQUIP: area1_node2`
    - `JOB_CHANGE: area1_node2`
    - `WEAPON_ENHANCE: area1_boss`
    - `DEMONIZATION: area1_boss`

#### audit finding

- `CODE_REFERENCED_STAGE_IDS` の各 `id` が `stages.json` に存在すれば `PASS`。
- 欠落すれば `FAIL`。
- メッセージには `referencedBy` を含め、どのコード経路が壊れたかを追えるようにする。

## 4. `/admin/audit` 連携

`auditMasterData()` の `stageIds` 作成後に次を追加する。

1. `validateStageGraph(data.stages)` の結果を `AuditFinding` に変換して `findings` へ追加。
2. `validateCodeReferencedStageIds(stageIds)` の結果を `scope: 'stages'` の `AuditFinding` として追加。

scope は計画書どおり `stages` に統一する。`id` は以下。

| ゲート | id |
|---|---|
| 到達可能性 PASS | `__stage_graph_reachability` |
| 循環 PASS | `__stage_graph_cycles` |
| 孤立 WARN | 対象 stage ID |
| コード参照 PASS/FAIL | 対象 stage ID |

既存 `AuditPanel` は `scope/id/message` をそのまま表示するため UI 変更は不要。

## 5. テスト計画

### 5.1 `src/lib/agent/stageGraph.test.ts`

必須ケース:

- 正常チェーン: 全到達、循環なし、FAILなし。
- 未到達ノード: ルートから届かないノードを `FAIL`。
- 循環: `A -> B -> A` を `FAIL`。
- 孤立ノード: 参照されない追加ルートを `WARN`。

### 5.2 `src/data/stageRefs.test.ts`

必須ケース:

- 現行 `stages.json` に対して `CODE_REFERENCED_STAGE_IDS` が全て存在する。
- 小さな `Set` を渡したとき、欠落IDを `FAIL` として検出する。
- 同じIDを複数経路が参照しても、各 `referencedBy` がメッセージに残る。

### 5.3 既存非破壊確認

- `npx tsc --noEmit`
- 関連テスト:
  - `src/lib/agent/stageGraph.test.ts`
  - `src/data/stageRefs.test.ts`
  - `src/data/tutorial/triggers.test.ts`
  - `src/logic/AbyssalResidueUnlockSystem.test.ts`
- 既存非破壊:
  - `npm test -- --runInBand --testPathIgnorePatterns=src/tests/`
  - `src/tests/` 配下の DB 統合テストは Neon 等の外部接続に依存するため、既存CI同様にローカル非破壊確認からは除外する。
