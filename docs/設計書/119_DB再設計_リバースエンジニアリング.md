# 119_DB再設計（実装リバースエンジニアリング起点）

> 作成: 2026-06-19
> 目的: `prisma/schema.prisma`（全18モデル）に対し、**実装が実際に読み書きしているテーブル・カラム**を
> コードから逆引き（reverse-engineering）して棚卸しし、現状の構造的負債を可視化した上で、
> **完成形のスキーマを再設計**する。
> ステータス: **P4まで実装済み（playerState一本化・旧ミラーDROP）。P5は未適用**。
> 前提: `117_DBスキーマとゲーム実装の整合性調査.md`（playerState 導入前の調査）/
> `118_永続化アーキテクチャ方針.md`（個人データ=JSONブロブ方針の決定）。
> 本書は 117/118 を**現コードの実態（playerState 半移行済み）に合わせて更新し、目標スキーマを具体化**するもの。

## 0. 要約（最重要の発見）

1. **二重真実（dual source of truth）が現存**。`Character.playerState`（JSONB / `PlayerSaveV1`）が
   2026-06-15 のマイグレーションで追加され（doc 118 Phase 1-2）、**ロード時はブロブが優先**される。
   しかし旧リレーショナルカラム（`gold` / `necro*` / `passive*` / `equip*Id` / `partySlot*Id` /
   `clearedStages` / `equippedResidue*Id`）と `UserJob` / `WeaponMaterial` テーブルにも**書き込みが残存**。
   → 同じ事実が2箇所に保存され、**ブロブが勝つ**ため、リレーショナル側は実質「書き捨ての中継ステージ」。
   doc 118 の **Phase 3（旧カラム移送）が未完**で、最も摩擦の大きい中間状態にある。
2. **完全な死蔵テーブルが4つ**: `Account` / `Session` / `VerificationToken`（NextAuth アダプタ未使用・
   JWT+Credentials 戦略のため一切アクセスなし）、`SpiritCore`（read 専用・`create` 経路が皆無）。
3. **書き込まれないカラム**: `User.emailVerified` / `User.image`、`Character.necroExp`（常に0）、
   `Character` の非武器装備7枠（`equipSub`〜`equipAcc2`、weapon-only 設計）。
4. **再設計の方針**: doc 118 を完遂する。**個人 private 進行は `playerState` 1本に集約**し、
   横断クエリ・整合性・採番・認証に必要なものだけ正規化テーブルとして残す。

## 1. 調査範囲と方法

- スキーマ: `prisma/schema.prisma`（18モデル）。
- 実アクセス（DBに触る全コード）:
  - `src/app/actions.ts` … Server Actions 本体（最大のデータ層、2132行）
  - `src/logic/GameManager.ts` … バトル開始/リザルトのDB往復（旧経路。一部はテスト/レガシー）
  - `src/services/{JobService,NecroService,RankingService,WorldEventService,AuthService,SessionSecurityService}.ts`
  - `src/auth.ts` / `src/app/api/auth/login/route.ts` … 認証
  - `src/lib/prisma.ts` … クライアント
- 手法: `prisma.<model>.<method>` / `tx.<model>` / `include` / `select` を grep で全列挙し、
  各カラムの **read / write / 経路** を関数単位で追跡。`src/data/master/*.json`（マスターデータ）と
  `src/app/admin/*`（マスター JSON のみ操作・DB非接触）は本書の対象外（doc 27 の領域）。

照合軸: **store が必要とする状態 ↔ `ServerGameData`（往復の口）↔ DBカラム / `playerState` ブロブ**。

## 3. `PlayerSaveV1`（現・真実のブロブ構造）

`src/types/playerSave.ts` ＋ `actions.ts` の normalize/serialize 群（`readPlayerSave`/`playerSaveToJson`/
`buildPlayerSaveFromDb`）から逆引きした実構造。**schemaVersion 内包・前方マイグレーション可能**。

```jsonc
{
  "schemaVersion": 1,
  "player": {
    "name": "アルド",
    "currentJobId": "warrior",
    "gold": 50000,
    "clearedStages": ["area1_node1", ...],
    "jobs": [{ "jobId": "warrior", "level": 1, "exp": 0 }],          // ← UserJob 相当
    "passives": { "passiveAtkBonus": 0, ...6項目 },                   // ← Character.passive*
    "necroStatus": { "level": 1, "rank": 1, "maxCost": 10,
                     "baseStatsBonus": 1, "exp": 0 },                 // ← Character.necro*
    "equipmentIds": { "weapon": "<itemId>", "sub": null, ...8枠 },    // ← Item.id 参照
    "partyMonsterIds": ["<monsterId>", null, null],                  // ← Monster.id 参照
    "equippedResidueIds": [null,null,null,null,null]                 // ← AbyssalResidue.id 参照
  },
  "weaponMaterials": [{ "type": "...", "name": "...", "quantity": 0 }], // ← WeaponMaterial 相当
  "residueMaterials": [{ "id","name","quantity","expValue","rarity" }], // ★テーブル無し（ブロブのみ）
  "transmutationPoints": 0                                             // ★列無し（ブロブのみ）
}
```

> **doc 117 の 🔴2件（`transmutationPoints` / `residueMaterials`）は、本ブロブ導入で実は解決済み**。
> 117 はブロブ導入前の記述であり、その点は本書で更新する（列追加ではなくブロブ収容で解決した）。

## 5. 再設計 — 目標スキーマ

方針（doc 118 を完遂）: **個人 private 進行は `Character.playerState` 1本に集約**。
横断クエリ／整合性／採番／認証に必要なものだけ正規化で残す。エンティティ（Monster/残滓/魂片/Item）は
**実体テーブルを維持しブロブは ID 参照のみ**。

### 5-1. 残す（正規化のまま） — 変更最小

- `User`（**`emailVerified`/`image` を削除**、`accounts`/`sessions` リレーション削除）
- `Item` + `ItemSerialCounter`（所有権・第一発見者グローバルクエリ・連番採番）
- `StageRecord` / `StageAttempt`(SEC-8) / `PlayerStats` / `WorldLog`
- エンティティ: `Monster` / `AbyssalResidue` / `SoulShard`

### 5-2. 削除（死蔵）

- **`Account` / `Session` / `VerificationToken`** … NextAuth を将来 OAuth へ拡張する予定があるなら
  「採用時に `@next-auth/prisma-adapter` 導入＋復活」を条件に**今は削除**。当面 JWT+Credentials のみ。
- **`SpiritCore`** ＋ `Monster.spiritCoreId` FK … write 経路が無く常に null。
  霊核を実装する際に「付与アクション＋本テーブル」を同時復活させる前提で**削除**
  （`MonsterAttackSystem`/`BattleEngine` の `spiritCore?` 参照は optional のまま無害）。

### 5-3. ブロブへ移送 → 列/テーブル削除（118 Phase 3 完遂）

`Character` から削除（すべて `playerState` が保持）:
`gold` / 8基礎stat / `passive*`(6) / `currentJobId` / `equip*Id`(8) / `necro*`(5) /
`partySlot*Id`(3)+index / `clearedStages` / `equippedResidue*Id`(5)。

テーブルごと削除（ブロブの `jobs` / `weaponMaterials` が代替）:
- **`UserJob`** → `playerState.player.jobs[]`
- **`Job`** → master(jobs.json) があれば FK 充足ミラー不要。`category/tier` は master 参照で得る
- **`WeaponMaterial`** → `playerState.weaponMaterials[]`
  - ⚠️ 注意: 現状テーブルは `updateMany ... quantity:{gte}` で**原子的な在庫減算**を担保している
    （`spendWeaponMaterialsForUser`）。ブロブ化後は **`Character` 行を `FOR UPDATE`
    （既存 `lockCharacterForUpdate:535`）でロックし、ブロブ内数量を検証→減算**してから UPDATE する
    1トランザクションに置換する（在庫マイナス防止の責務をブロブ更新側へ移す）。

### 5-4. 目標スキーマ（Prisma 抜粋・**提案。未適用**）

```prisma
// ── 認証・横断系（据え置き）─────────────────────────────
model User {
  id            String   @id @default(uuid())
  email         String?  @unique
  passwordHash  String?
  displayName   String?
  name          String?
  sessionVersion Int     @default(1)   // SEC-6 JWT一括失効
  createdAt     DateTime @default(now())
  // emailVerified / image / accounts / sessions は削除

  character     Character?            // 1ユーザー1キャラ
  ownedItems    Item[]   @relation("ItemOwner")
  discoveredItems Item[] @relation("Discoverer")
  stageRecords  StageRecord[]
  stageAttempts StageAttempt[]
  playerStats   PlayerStats?
  worldLogs     WorldLog[]
}

// ── 個人セーブ（薄いコア＋JSONブロブ）──────────────────
model Character {
  id            String   @id @default(uuid())
  userId        String   @unique           // findFirst→findUnique 化。1ユーザー1キャラを型で保証
  user          User     @relation(fields: [userId], references: [id], onDelete: Cascade)

  playerState   Json                        // = PlayerSaveV1（schemaVersion 内包）
  saveVersion   Int      @default(1)        // 横断クエリ/移行用に列出し（任意・ブロブ内とは別管理可）
  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt

  // エンティティは characterId 起点で残す（ブロブは ID 参照のみ）
  monsters        Monster[]        @relation("CharacterMonsters")
  soulShards      SoulShard[]      @relation("CharacterSoulShards")
  abyssalResidues AbyssalResidue[] @relation("CharacterResidues")
  // 装備 8 / パーティ 3 / 残滓スロット 5 の FK 列・リレーションは廃止 → ブロブの *Ids に集約
}

// ── ゲームエンティティ（ID参照先）──────────────────────
model Monster {
  id          String  @id @default(uuid())
  masterId    String?
  characterId String?
  character   Character? @relation("CharacterMonsters", fields: [characterId], references: [id], onDelete: SetNull)
  name String; tribe String; cost Int
  hp Int; atk Int; def Int; spd Int
  critRate Float @default(0); critDmg Float @default(150)
  effectHit Float @default(0); effectRes Float @default(0)
  currentEnergy Int @default(30); maxEnergy Int @default(30)
  resistances Json @default("{}")
  skillIds    Json @default("[]")
  soulShardId String?
  soulShard   SoulShard? @relation(fields: [soulShardId], references: [id])
  // spiritCoreId / SpiritCore リレーションは削除（死蔵）
  @@index([characterId])
}

model SoulShard {
  id String @id @default(uuid())
  characterId String?
  character Character? @relation("CharacterSoulShards", fields: [characterId], references: [id], onDelete: SetNull)
  originMonster String; atkBonus Int @default(0); elementDmgBoost Int @default(0); specialAbility String?
  monsters Monster[]
  @@index([characterId])
}

model AbyssalResidue {
  id String @id @default(uuid())
  name String
  itemId String        // 部位種別 'head'|'arms'|'chest'|'waist'|'legs'（Item FK ではない）
  characterId String?
  character Character? @relation("CharacterResidues", fields: [characterId], references: [id], onDelete: SetNull)
  rarity String @default("R")          // 実値 R/SR/SSR/UR にコメント/デフォルト是正（D5）
  mainStat Json
  subOptions Json @default("[]")
  level Int @default(1); exp Int @default(0); maxExp Int @default(800)
  // equippedResidue0-4 の Character 側スロットFKは廃止（ブロブ参照へ）
}

// Item / ItemSerialCounter / StageRecord / StageAttempt / PlayerStats / WorldLog は現状維持
// （Item.rarity コメントのみ実値へ是正）
```

### 5-5. 再設計の効果

- 新規個人フィールド = **ブロブ型に1行**。migration も `ServerGameData`/`toServerGameData`/`loadFromServer`
  の往復4箇所更新も不要 → doc 117 で漏れたクラスのバグが**構造的に消滅**。
- 18 → **約11モデル**（Account/Session/VerificationToken/SpiritCore/Job/UserJob/WeaponMaterial を削減）。
- `Character` は ~40列 → **5列**（id/userId/playerState/saveVersion/timestamps）＋エンティティ3リレーション。
- 保存が原子的（`Character.playerState` 1 UPDATE）。読みは「ブロブをパース→store」の1経路に集約。
