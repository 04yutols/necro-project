## 実装サマリ（P5で入ったもの）

1. **schemaVersion を 1→2 へ昇格**（`playerSave.ts`）。`MIN_SUPPORTED_PLAYER_SAVE_SCHEMA_VERSION=1` を新設。
   ※ペイロード shape は v1 と同一（バージョンマーカーのみ。前方移行プラミングの確立が目的）。
2. **前方マイグレーション機構**（`PlayerSaveService.ts`）— `PLAYER_SAVE_MIGRATIONS` レジストリ＋
   `migratePlayerSaveSchema()` が v(n)→v(n+1) を順次適用。各段で「バージョンが必ず進む」ことを検証（ループ安全）。
3. **F1 解消** — `readPlayerSave` / `hasCompletePlayerSave` を `migratePlayerSaveSchema` 経由に変更。
   不正・未対応・未来バージョンは **`PlayerSaveSchemaError` を throw**（旧: `emptyPlayerSave()` へサイレントリセット）。
4. **F4 解消** — `updatePlayerSaveSnapshot` が `playerState` と同時に `saveVersion: PLAYER_SAVE_SCHEMA_VERSION`
   を書込み、列とブロブ内 `schemaVersion` を同期。schema 既定値も `@default(2)`。
5. **DBマイグレーション** — 既存 v1 blob を `jsonb_set(...,'{schemaVersion}','2')` で v2 へスタンプ、`saveVersion=2` 同期。
   `jsonb_typeof = 'object'` ＋ 正規表現ガード、`WHERE version<2` で冪等的。shape 不変ゆえデータ無リスク。
6. **localStorage 格下げ**（`useGameStore.ts`）— persist version 1→2、`partialize` に
   `cacheKind`（`guest-save` / `server-snapshot`）・`cachedAt`・`offlineQueue` を付与。
   `migrate` で旧 persist にメタ補完。ロード時に「CACHED CLOUD SNAPSHOT」/「LOCAL SAVE」を区別。

## 良い点

- **F1 を「fail-loud」で正しく解決** — 破損・未知バージョンを黙って初期化せず例外化。`readPlayerSave` の
  ユニットテストで happy（v1→v2 で gold/clearedStages/name 保持）と異常（`{schemaVersion:'1'}`・未来版）の両系統を網羅。
- **マイグレーションレジストリが拡張容易** — v2→v3 は `PLAYER_SAVE_MIGRATIONS[2]` を足すだけ。
  各段のバージョン前進チェックで「移行漏れ／逆行／無限ループ」を構造的に防止。
- **F4 を列・ブロブ同期で解消** — 書込のたび `saveVersion` を更新し、横断クエリ用の列が陳腐化しない。
- **DBマイグレーションの安全設計** — shape 不変＋冪等条件＋型/正規表現ガード。既存データを壊さずバージョンだけ前進。
- **localStorage の真実格下げの第一歩** — `cacheKind` で「ゲスト進行」と「クラウドのキャッシュ複製」を分離し、
  doc 116/117 §4-1 の「localStorage が第2の真実化」する非対称を解消する土台を敷いた。

## 指摘事項

### 🟢 F-P5-1. v2 は shape 不変のバージョン昇格（インフラ確立が目的）
`PlayerSaveV1` interface を `schemaVersion:2` で再利用し、v1→v2 移行は `{...state, schemaVersion:2}` の no-op。
前方移行プラミングの確立としては妥当だが、**実データ進化は伴わない**。型名 `PlayerSaveV1` は実態（v2 形状）と
ずれており、`PlayerSaveData` エイリアスへ寄せる等の改名を後続 cleanup で検討。

### 🟢 F-P5-2. DBマイグレーションが `jsonb_set` でバージョンを直接スタンプ（app 移行関数をバイパス）
shape 不変の今は app の `migratePlayerSaveSchema` と同一結果で安全。だが**将来 shape を変える v2→v3** では
SQL の `jsonb_set` で JS 移行ロジックを再現できない。→ 規約として「実 shape 変更時は **app 側の遅延移行**
（`readPlayerSave` が読込時に移行 → 次回 `updatePlayerSaveSnapshot` で移行済みblobを永続）を正とし、SQLの
eager スタンプは任意」に統一するのが安全。doc にこの方針を明記推奨。

### 🟢 F-P5-3. `readPlayerSave` の throw 化と caller 境界
本番は全 blob が有効 v2 のため発火しないが、万一の破損時は server action 境界で**未捕捉例外＝不透明な500**になりうる。
F1 的には fail-loud が正しいので、`loadCharacterForUser` 等の境界で `PlayerSaveSchemaError` を捕捉し、
**制御されたエラー＋テレメトリ**（「セーブデータ異常」表示）に変換するのが理想。
なお `readPlayerSave(state, fallback)` の `fallback` は今や「フィールド欠落の既定値」専用で、
「不正blob時に丸ごと返す」用途は消滅（旧 `buildPlayerSaveFromDb` 撤去済みで依存 caller なし）。API 意味の縮小に留意。

### 🔵 F-P5-4. localStorage 格下げは「足場」段階（offlineQueue は未実体）
`offlineQueue` は `never[]`（常に空）、`cacheKind` は主にログ表示を駆動。構造分離（guest/snapshot＋version2＋migrate）は
正しい土台だが、「サーバーが常に真実／キャッシュは非権威」の強制は既存 `loadFromServer` フローに依存（本PRでは未変更）。
P5 の締めとしては妥当だが、**完全なオフライン同期ではなく基盤整備**である点を認識しておく。

### ⚠️ F-P5-5. 実DBでの migration＋統合テスト未実行
当環境は `DATABASE_URL` 未設定。P5 は migration ＋ store 変更を含むため、マージ前に
実DBで `prisma migrate deploy` ＋ `npm test` を1回流して退行なしを確認推奨（前段の 699/699 を更新）。

> 既知の G1（死霊術育成が未実装で rankUp の Lv.99 ゲート到達不能）は P5 でも未解決＝想定通りスコープ外。
