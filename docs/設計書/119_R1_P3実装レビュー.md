## 良い点（設計上正しく担保されている）

1. **原子性の維持** — 武器素材のテーブル原子減算（`updateMany ... gte`）を失わず、
   `SELECT ... FOR UPDATE`（`lockCharacterForUpdate`）でCharacter行をロックしてからブロブ内検証減算。
   doc 119 §5-4 の懸念に正面から対応。
2. **FK `onDelete:SetNull` の代替** — `cleanPlayerSaveReferences` が毎更新で
   Item/Monster/AbyssalResidue の実在を照合し、消えた参照IDを掃除。魂石化（`monster.delete`→sync）で
   編成スロットから自動除去されることを確認。doc 119 §6 の懸念に対応済み。
3. **後方互換** — `hasCompletePlayerSave` が偽の旧データだけ `buildPlayerSaveFromDb` で旧列フォールバック。
   `loadCharacter` はバックフィル後に再フェッチして整合を取る修正も入っている。
4. **GameManager も一貫移行**（読みも `readPlayerSave` 起点）で片肺化していない。

## 指摘事項

### 🟠 H1. 正規化/シリアライズ層が actions.ts と PlayerSaveService に二重定義
`actions.ts` は依然ローカル定義を保持（`readPlayerSave:471` / `playerSaveToJson:504` /
`buildPlayerSaveFromDb:545` / `hasCompletePlayerSave:611` / `toBaseStats:635` / `emptyPlayerSave:278` /
`normalize*` 群）。同名関数が `PlayerSaveService` にも存在し、**書込パス（`updatePlayerSaveBlob`）は
PlayerSaveService 版、読込パス（`toServerGameData`/`loadCharacter`）は actions.ts ローカル版**を使う二系統。

- とくに `playerSaveToJson` は両者で**実装が非同一**（PlayerSaveService 版は
  `normalizeJobs/Passives/NecroStatus/...` を再適用、actions.ts 版は素の spread）。
- 現状の正常系では出力が一致するため tsc/動作は通るが、**今後どちらか一方だけ正規化ルールを直すと
  write/read のブロブ解釈がズレる**（ラウンドトリップ破壊）リスク。
- **推奨**: actions.ts は
  `readPlayerSave/playerSaveToJson/buildPlayerSaveFromDb/hasCompletePlayerSave/toBaseStats/emptyPlayerSave`
  を `PlayerSaveService` から import し、ローカル定義を削除して**単一の真実**にする。
  `createCharacter` のブロブ直書きも PlayerSaveService 版に統一。

### 🟡 M1. 個人進行ロジックの多重実装
「職業EXP→レベル→永続パッシブ加算」「転職（解放判定＋付与）」「死霊術ランクアップ」が
**actions.ts（本番）/ GameManager / JobService・NecroService** に並存。
`GameManager`/`JobService.changeJob`/`NecroService.performRankUp` の **DBパスは本番から呼ばれず
（`new GameManager` は test 専用）**、実質テスト専用の並行実装になった。
- **推奨**: ①actions.ts がサービスへ委譲して一本化、②または本番未使用のサービスDBパスを
  「テスト専用」と明記/集約、のどちらかで重複を解消。放置すると将来「解放条件」「パッシブ式」を
  片方だけ直す事故の温床。

### 🟢 L1. デッドコード `mergeResidueMaterials`（actions.ts:364）
旧 `syncPlayerStateSnapshot` 本体撤去で呼び出し元が消え、定義のみ残存（未使用）。
H1 のローカル層削除とあわせて除去。

### 🟢 L2. `cleanPlayerSaveReferences` の固定3 SELECT/更新
全 mutation で Item+Monster+AbyssalResidue を毎回 `findMany`。装備変更など参照種別が限定される操作では
monster/residue スキャンは不要。連打される装備系でDB往復が増える。
- **推奨**: `options` に掃除対象スコープ（equipment/party/residue）を持たせ、必要な系統だけ照合。

### 🟢 L3. 武器強化でブロブ更新2回
`rankUpWeaponForUser`/`reforge` は `spendWeaponMaterialsForUser`（=blob更新）＋
末尾 `syncPlayerStateSnapshot`（=blob更新）で**ロック/読込/掃除が2周**。1回の updater に集約可能。

### 🔵 設計メモ（P4 を待たず認識しておくべき点）
- 新規キャラは `currentJobId/gold/equip*Id/UserJob/WeaponMaterial` を**もう書かない**ため、
  `buildPlayerSaveFromDb` の旧列フォールバックは**新規キャラでは信頼不可**
  （gold は schema 既定値50000、currentJobId は null）。万一ブロブ欠損時のロールバック先が壊れる。
  → **P4（旧列・旧テーブル DROP）と `schema_version` 前方移行（P5）を早めに**入れてフォールバック依存を断つ。
  `Character` の基礎8ステータスは seed として残置＝意図的でOK。
- **既存ギャップ G1 は本リファクタでも未解決**: 死霊術レベルを増やす経路が無く
  `necroStatus.level` は1のまま＝rankUp（Lv.99要求）は依然到達不能。対象外だが、
  ブロブ化で `necroExp` を活かす実装余地ができた点は前進。

- **原子性を維持したまま簡素化** — `cleanReferences:false` でも `lockCharacterForUpdate`（行ロック）は先頭で必ず実行され、武器素材の検証減算の原子性は保持。スキップしたのは不要な参照掃除だけ、という判断が正確。
- **掃除スキップの安全性検証が妥当** — dismantle は「装備中武器は分解不可」を先に確認 → 削除アイテムが equipmentIds に存在しない保証があり、dangling 参照が生じない。
- **共有関数の純粋化** — DB I/O を持たない `*InSave` 関数群に切り出し、個人進行ロジックをユニットテストで直接検証可能にした。
