## 1. 目的と位置づけ

`/admin/simulator` は職業 × スキル × 敵を選び、`calculateBattleDamage` で**単発の期待ダメージ**を表示する。
しかし「この数値が適正か？」「強すぎ/弱すぎか？」「いくつにすべきか？」の**判断はユーザーの目視**に委ねられている。

**Agent E（シミュレータ連携）は、決定論的に計算した多シナリオの結果を LLM が解釈し、
バランス評価と具体的な調整値を自然言語で提示する。**

### 設計の核心（doc100 と同一・最重要）

> **ダメージ計算は LLM がしない。`calculateBattleDamage`（= 実バトルと同一ロジック）が行う。**
> LLM は決定論的に算出された数値**を読んで解釈・推奨する**だけ。
> これにより「LLM が計算を間違える」リスクが原理的に存在しない（幻覚的な数値が出ない）。

Agent A（生成）/ Agent B（修正）が「JSON の構造・参照・帯」を担保するのに対し、
Agent E は「**実際に戦わせた時の体感バランス**」という、静的検証では届かない領域を担う。

## 3. アーキテクチャ

2 つの入口を持つが、中核（決定論的レポート → LLM 解釈）は共通。

```
入口A: /admin/simulator の「AI評価」ボタン（既存の選択 job×skill×enemy を評価）
入口B: Agent A 草案パネルの「生成後に評価」（生成した skill/enemy 草稿を即評価）
            │
            ▼
[決定論的] buildSimulationReport(attacker, skill, targets[])
   calculateBattleDamage を N 回実行し、メトリクスを集計（LLM 不使用）
   - 各敵への normal/crit/expected ダメージ
   - 1確率（expected >= enemyHP）、撃破ターン数
   - エネルギー効率（expected / mpCost）
   - 弱点/耐性カバレッジ
            │  構造化レポート（純データ）
            ▼
[LLM] simEvalAgent: レポート + 設計帯(doc19/15) を渡し「解釈・評定・推奨」を生成
   出力: verdict(適正/強すぎ/弱すぎ) + 根拠(数値引用) + 具体推奨(数値変更案)
            │
            ▼
UI: 評価カード表示。推奨があれば「推奨値で再シミュレート」→ 数値が動くのを確認
   （任意）推奨を skill/enemy の修正としてフォーム or Agent B に渡す
```

**ポイント**: レポートは純データなので**そのまま画面にも出せる**（LLM 不通でも数値は見える）。
LLM はその上に「読み解き」を載せるだけ。

## 4. 詳細設計

### 4.1 決定論的シミュレーションレポート（`simulationReport.ts`）

入力:
```ts
type SimAttacker = { atk: number; critRate: number; critDmg: number; elementBoostPct?: number };
type SimSkill = { power: number; mpCost: number; element: ElementType; targetType: 'SINGLE'|'ALL_ENEMIES' };
type SimTarget = { id: string; tier?: string; hp: number; def: number; resistances: Record<string, number> };

buildSimulationReport(attacker: SimAttacker, skill: SimSkill, targets: SimTarget[]): SimulationReport
```

出力（純データ・LLM 不使用）:
```ts
type PerTarget = {
  id: string; tier?: string;
  normal: number; critical: number; expected: number;
  hp: number; oneShot: boolean;            // expected >= hp
  hitsToKill: number;                       // ceil(hp / expected)
  isWeakness: boolean; isResisted: boolean; // resistances[element] の符号
};
type SimulationReport = {
  attacker: SimAttacker; skill: SimSkill;
  perTarget: PerTarget[];
  summary: {
    energyEfficiency: number;               // expected(代表) / mpCost
    oneShotRate: number;                    // 1確になった敵の割合
    avgHitsToKill: number;
    weaknessCoverage: number;               // 弱点を突けた敵割合
  };
};
```

- 計算は `calculateBattleDamage`（rng=()=>1 で非会心、rng=()=>0 で会心）を各 target に対し実行し、
  `expected = normal*(1-critRate) + crit*critRate`（simulate() と同一式）。
- AoE は per-target ベースで評価しつつ、summary に「全体ヒット数 × ダメージ」も付す。
- **完全に純関数 → jest で網羅テスト可能**（API 不要）。

### 4.2 LLM 解釈エージェント（`simEvalAgent.ts`）

- 入力: `SimulationReport` + 設計帯コンテキスト（doc19 の該当 power 帯、エネルギー効率目安 20〜35、敵HP帯）。
- 出力（structured）:
```ts
type SimEvaluation = {
  verdict: 'BALANCED' | 'TOO_STRONG' | 'TOO_WEAK';
  rationale: string;                 // 数値を引用した日本語解説
  recommendations: {                 // 任意・複数可
    target: 'skill.power' | 'skill.mpCost' | 'enemy.hp' | 'enemy.def';
    current: number; suggested: number; reason: string;
  }[];
};
```
- **生成ループは不要**（検証付き生成ではなく解釈）。ただし軽い決定論チェックを付す:
  - 推奨値が設計帯（doc19）内か `verifyRecommendation()` で確認し、帯外なら警告タグを付ける。
  - これにより「LLM が帯外の推奨を出す」事故も決定論的に検出。

### 4.3 推奨の再シミュレーション（任意ループ）

UI で推奨値（例 power 1.55→1.35）を適用 → `buildSimulationReport` を再実行 → 数値の変化を即表示。
**LLM を介さず**に推奨の効果を検証できる（決定論的）。ユーザーが納得したら skill/enemy 修正へ。

### 4.4 ターゲット集合の自動構築

入口B（草稿評価）では、評価対象の敵集合を自動で組む:
- skill 草稿 → 同章の全 enemies（MINION/ELITE/BOSS）を targets にして「章全体での体感」を評価。
- enemy 草稿 → 代表的な職業スキル数種を attacker にして「どれくらいの壁か」を評価。
入口A（手動）では simulator の現在選択（単一 job×skill×enemy）+ オプションで「章の全敵に展開」。

## 6. プロンプト設計（simEvalAgent）

```
あなたは Necromance Brave のバランスデザイナーです。以下は実バトルと同一の計算式で算出した
シミュレーション結果（決定論的・確定値）です。この数値を解釈し、バランスを評定してください。
数値はあなたが計算したものではありません。与えられた数値のみを根拠にしてください。

# シミュレーション結果
攻撃側: atk={atk} / critRate={critRate}% / critDmg={critDmg}%
スキル: power={power} / mpCost={mpCost} / element={element} / {targetType}
対象別:
  {id} [{tier}] HP {hp} → 期待 {expected}（通常 {normal}/会心 {critical}）/ {oneShot? "1確" : "{hitsToKill}発"} / {弱点|耐性|等倍}
要約: 1確率 {oneShotRate}% / 平均撃破 {avgHitsToKill}発 / エネルギー効率 {energyEfficiency} / 弱点カバー {weaknessCoverage}%

# 設計帯（doc19/15）
- {分類} の Tier{n} power 帯: {lo}〜{hi}
- エネルギー効率の目安: 20〜35
- {tier} の HP 帯: {…}

# 出力（JSON のみ）
{ "verdict": "BALANCED|TOO_STRONG|TOO_WEAK",
  "rationale": "数値を引用した日本語の評定（2〜4文）",
  "recommendations": [ { "target": "skill.power", "current": x, "suggested": y, "reason": "…" } ] }

# 厳守
- 数値は与えられたものだけを使う（再計算・捏造しない）。
- 推奨は設計帯に収める。推奨が無ければ recommendations は空配列。
```

## 8. 安全性

| リスク | 対策 |
|---|---|
| LLM が数値を再計算して誤る | 計算は `calculateBattleDamage` のみ。プロンプトで「与えられた数値だけ使う」を厳命。レポートは画面にも出すので照合可能 |
| LLM の推奨が設計帯外 | `recommendationCheck` で帯チェックし帯外に警告タグ。適用は手動 |
| 評価の過信 | 評定は助言。適用は既存フォーム/Agent B 経由でユーザー操作。Agent E は何も書き込まない |
| 開発環境外実行 | `assertDev()` 踏襲 |

## 11. Agent A / B / E の役割整理（単一の真実）

| エージェント | 担う検証 | ゲート |
|---|---|---|
| Agent A（生成） | 構造・参照・数値帯（静的） | per-content バリデータ |
| Agent B（監査修正） | 既存データの違反解消（静的） | per-content + 監査再実行 |
| **Agent E（シミュレータ連携）** | **実戦の体感バランス（動的）** | **`calculateBattleDamage` の多シナリオ実行** |

A/B は「データとして正しいか」、E は「遊んで面白い数値か」。三者で静的・動的の両面を覆う。
E の推奨は将来 B（修正）に流し込むことで「評価 → 自動修正 → 再評価」の閉ループにできる。
