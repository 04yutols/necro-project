## 1. 本ターンで修正したギャップ（🔧）

### 1.1 【高】Agent D の二層ゲートが未到達だった
- **問題**: `verify-bulk` は `runBulkAgent` + `applyBulkSpec`（メモリ内変換）のみで、
  核心の安全機構（per-content バリデータ + `auditMasterData` override による新規 FAIL 検出）が**一度も実行されていなかった**。
- **対応**: `scripts/verify-bulk-agent.mts` を拡張し `previewBulkChangeAction` を**非破壊で**ライブ到達。
- **実証**: 「全 MAGIC_AoE スキルの power を 0.1 下げる」で `ok: false`（一部スキルが設計帯を外れるため）を返し、
  **適用をブロック**することを確認。＝ ゲートは本当に機能する。`git diff src/data/master` も空。

### 1.2 【中】一括変更が存在しないフィールドを無警告で処理
- **問題**: `add`/`mul` は欠落フィールドを黙ってスキップ、`set` は新規フィールドを作成。
  LLM のフィールド幻覚やタイプミスが検出されず、preview で気付けない。
- **対応**: `bulk/bulkEngine.ts` に `auditMutationFields()` を追加し、
  preview で「一致エンティティに存在しない operation フィールド」を WARN 表示（`missingFields`）。ユニット 3 件追加。

### 1.3 【中】ストーリー 0 候補時に理由が不可視
- **問題**: 全候補が構造 FAIL で除外された際、UI は汎用文のみ。
  原因（archiveTitle 未入力 / 無効 expression 等）が分からず再生成しても改善しない。
- **対応**: `StoryAgentResult.rejectionReasons` を追加し、UI に除外理由 +「基本情報を先に埋めて」を表示。

## 3. 本番投入前のチェックリスト（推奨実装）

### 3.1 R-1: 実保存パス（applyBulkChangeAction）の検証
- 手段案 A: 一時ディレクトリにマスターデータをコピーし、`MASTER_DIR` を差し替えられるよう
  `saveEntry` / `getAllMasterData` をテスト用に注入可能化 → 一括適用 → コピー側のみ変化を確認。
- 手段案 B（簡易）: git クリーンな状態で手動 E2E（preview → apply → 結果確認 → `git checkout` で復元）。
- 完了条件: 適用後に対象 entity のみ変化し、`failedIds` ハンドリング（部分失敗）が機能する。

### 3.2 R-2: 一括適用前スナップショット
- `applyBulkChangeAction` の冒頭で対象ファイル（例 `skills.json`）を
  `src/data/master/.snapshots/{file}.{timestamp}.json` へ退避。
- UI に「直前の一括変更を元に戻す」導線（最新スナップショットから復元）。
- これにより R-2（不可逆性）を実用上解消。

### 3.3 共通: 適用系アクションの最終ゲート
- `applyBulkChangeAction` / `saveEntry`（AI 草案・監査修正の保存）は、保存直前に
  もう一度 `auditMasterData(override)` でドライランし、新規 FAIL があれば保存を中断する二重化を検討
  （現状は preview/検証で担保。UI を経由しない将来の自動適用に備える）。

## 8. R-3 対応完了（2026-06-10）

per-content バリデータが未知トップレベルフィールドを黙認していた問題を解消。

### 実装
| ファイル | 区分 | 内容 |
|---|---|---|
| `src/lib/agent/knownFields.ts` | 新規 | scope 別の既知トップレベルフィールド集合 + `findUnknownFields(entity, scope)`（WARN） |
| 9 バリデータ（enemy/skill/demon/stage/weapon/material/job/area/monster Balance.ts） | 変更 | 検証末尾で `findings.push(...findUnknownFields(draft, scope))` を配線 |

### 仕様
- 既知集合は**実データ + 型上の正当なオプションの上位集合**（誤検出防止）。`__` プレフィックスは無視。
- 未知フィールドは **WARN**（FAIL ではない）。「スキーマ更新前に新フィールドを置く」等の正当ケースを妨げないため。
- 生成（Agent A）・監査修正（B）・一括変更（D）すべてが per-content バリデータ経由なので**全経路で有効**。
  bulk の `set foobar` のような新規フィールド作成も per-content WARN で surface される（#1.2 の add/mul 不在フィールド WARN と相補）。

### 検証結果
| 種別 | 結果 |
|---|---|
| 型チェック | PASS |
| ユニット（`knownFields.test.ts`：検出/誤検出防止/実データ網羅 + enemy 配線実証） | PASS |
| agent ユニット合計 | 266 件 → 全体 65 suites / 578 tests PASS（既存 fixture に誤 WARN なし） |
| ライブ（bulk preview・非破壊） | 「全スキルに foobar を set」→ 未知フィールド WARN 検出 = true。md5 一致・git diff 空 |

> **結論**: R-3 解決。未知/タイプミスのフィールドは生成・監査・一括の全経路で WARN として可視化される。
> 残課題は R-4（Server Action 単体テスト・設計判断）/ R-5（sim AoE 簡略化）/ R-6（gimmick 型）/ R-7（enemy 草案の評価）の低リスク 4 件のみ。
