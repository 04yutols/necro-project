# 100 — 管理画面 AI エージェント設計（LangGraph 統合提案）

> 作成: 2026-06-07  
> ステータス: **提案書（未実装）**  
> 目的: 管理画面の既存インフラ（決定論的ゲート・永続化）を活かしつつ、LangGraph エージェントをその上流に置く

---

## 1. 設計の核心思想

### 管理画面が持つ 2 つの資産

現在の `/admin` パネルはすでに以下の**決定論的インフラ**を持っている:

| インフラ | 実装 | 役割 |
|---|---|---|
| **データ監査** | `runMasterDataAudit()` | 参照整合・ドロップ率・必須フィールドを機械的に PASS/WARN/FAIL 判定 |
| **ダメージシミュレータ** | `SimulatorClient` + `BattleEngine` | ATK×power×防御軽減の期待値を実コードで計算 |
| **Server Actions** | `admin/actions.ts` の `saveMasterData()` 系 | ファイル書き込みの唯一の正規ルート |

これらは「LLM が正しいと言った」ではなく「コードが正しいと言った」ものだ。  
**エージェントが担うべき役割は、この決定論的ゲートに通すための草稿を作ること**であり、ゲート自体をバイパスしたり置き換えることではない。

### アーキテクチャの原則

```
自然言語の意図
    │
    ▼
LangGraph Agent ── JSON 草稿を生成する
    │
    ▼ (草稿を既存インフラに流す)
┌─────────────────────────────────────┐
│           管理画面の決定論的ゲート    │  ← ここは一切変えない
│  ┌──────────────────────────────┐   │
│  │  runMasterDataAudit()        │   │
│  │  BattleEngine シミュレータ    │   │
│  └──────────────────────────────┘   │
│  PASS / WARN / FAIL の結果が出る    │
└──────────┬──────────────────────────┘
           │ ユーザーが確認・承認
           ▼
     saveMasterData()   ← 永続化は Server Action 経由のみ
           │
           ▼
     src/data/master/*.json に書き込まれる
```

**エージェントが直接ファイルを書くことはない。** 永続化のパスは管理画面の Server Action だけである。

## 2. 現状のワークフローと課題

エネミーを 1 体追加するだけで、以下の往復が発生する:

```
1. 設計書を開いて tier 帯の stats を確認（手動）
2. JSON を手書き
3. /admin/audit を開いて監査実行
4. FAIL があれば原因を推定して手修正 → 3 に戻る
5. /admin/simulator で実際のダメージ期待値を確認（手動）
6. 問題があれば stats を再調整 → 3 に戻る
```

往復のたびに「設計書を読んで判断する」という知識労働が発生する。  
**エージェントが担うのはステップ 1〜2 の草稿生成と、4・6 のフィードバック解釈**である。  
ステップ 3・5（決定論的な正しさの検証）は管理画面が引き続き担う。

## 3. 提案するエージェントフロー

### 3.1 コンテンツ生成フロー（新規エネミー・スキル・魔神化フォーム）

```
[管理画面 /admin/enemies/new]

既存: フォームに手入力して Save

新規追加:「AI 草案」ボタン
  ↓
ユーザーが自然言語で要件を入力
  「area1_boss 前座の ELITE アンデッド。ICE 弱点、高DEF」
  ↓
LangGraph Agent
  ├─ 設計書 (15_ワールド設計, 19_バランス設計) を読み込む
  ├─ 既存エネミーと重複・差別化を確認
  └─ JSON 草稿を生成して既存フォームのフィールドに流し込む
  ↓
[既存フォームに草稿が入った状態]
  ↓
ユーザーが「監査実行」を押す（既存機能 runMasterDataAudit）
  ├─ PASS → そのまま Save（既存 Server Action）
  └─ FAIL → AI に「この FAIL を修正して」と追加指示 → 草稿修正 → 再監査
```

**ポイント**: フォームへの流し込みと Save は既存の UI/Server Action をそのまま使う。エージェントは「フォームを事前に埋める補助」に徹する。

---

### 3.2 監査 FAIL 修正フロー（既存監査ページの拡張）

```
[管理画面 /admin/audit]  ← このページは変えない

FAIL: skills / soul_shatter / power 2.8 が PHYS_SINGLE 低コスト上限 1.55 を超過

[既存] テキストで FAIL 内容を表示するだけ
[追加] 「AI に修正案を聞く」ボタン
  ↓
Agent:
  ├─ 違反している設計書ルールを特定
  ├─ 最小変更（power を下げるだけ or critRate で補正するか）を提案
  └─ 修正済み JSON diff を返す
  ↓
ユーザーが diff を確認して「適用」
  ↓
再度 runMasterDataAudit() を自動実行
  ├─ PASS になった → Save ボタンが有効化
  └─ まだ FAIL → 差し戻し（エージェントに再提案させる or 手修正）
```

**ポイント**: 監査実行（`runMasterDataAudit`）は何度でも走らせていい。エージェントの提案が正しいかどうかは監査が判定する。LLM の自己申告は信用しない。

---

### 3.3 シミュレータ連動フロー（数値の妥当性を即時確認）

```
[管理画面 /admin/simulator]  ← このページは変えない

既存: スキル × 職業 × エネミーを選んでダメージ期待値を確認

[追加] 生成直後の草稿 JSON をシミュレータに即時投入
  ↓
BattleEngine.calculateDamage() で実際に計算（決定論的）
  ↓
期待値が表示される
  ↓
「MINION HP の 80〜120% 範囲に収まっているか？」を
  Agent がシミュレータの出力を読んで自然言語でコメント
  「1撃で倒せる。設計書の想定より火力が高い。power を 1.35 に下げることを推奨」
  ↓
ユーザーが判断して草稿を修正 → シミュレータを再実行
```

**ポイント**: ダメージ計算は LLM がしない。`BattleEngine` がする。LLM はその結果を解釈してコメントするだけ。

---

### 3.4 ストーリーシーン生成フロー

```
[管理画面 /admin/story/pack/ch1/scene/new]

既存: テキストフォームに手入力

[追加] 「AI 初稿」ボタン
  ↓
Agent:
  ├─ 前後シーンのコンテキストを既存 JSON から取得
  ├─ 22_ストーリー設計.md のキャラ定義・ト書きルールを参照
  └─ dialogue[] の配列を 3 案生成して返す
  ↓
ユーザーが案を選んでフォームに反映
  ↓
既存の Save（Server Action）で保存
```

---

### 3.5 一括変更フロー（仕様変更対応）

```
[管理画面 /admin/agents/batch]（新規ページ、ただし Save は既存 Server Action）

ユーザー: 「MAGIC_AOE で mpCost 15 以下の全スキルの power を 0.1 下げる」
  ↓
Agent: 条件に合致するエントリを抽出し diff 一覧を生成
  ↓
管理画面に diff テーブルを表示（変更前→変更後）
  ↓
「全て適用」ボタン → runMasterDataAudit() を自動実行
  ├─ 全 PASS → Save ボタン有効化
  └─ FAIL あり → 個別に修正フローへ
```

## 4. 管理画面に追加する UI（最小限）

既存ページへの追加で完結させる。新しいページはバッチ変更フロー用の 1 枚だけ。

| 追加場所 | 追加物 | 説明 |
|---|---|---|
| `/admin/enemies/new` 等の新規作成フォーム | 「AI 草案」ボタン | フォームフィールドに草稿を流し込む |

## 5. 技術スタック

| レイヤー | 採用技術 |
|---|---|
| エージェントフレームワーク | **LangGraph.js** (`@langchain/langgraph`) |
| LLM | **Gemini** (Google AI Studio) |
| ストリーミング | **Vercel AI SDK** (`ai`) — `useObject()` で JSON diff をリアルタイム表示 |
| Route Handler | `/admin/api/agent/route.ts` — Node.js runtime (Cloudflare Workers 外) |
| 永続化 | **既存 `admin/actions.ts`** — 変更なし |
| 決定論的ゲート | **既存 `runMasterDataAudit()`・`BattleEngine`** — 変更なし |

```bash
npm install @langchain/langgraph @langchain/anthropic ai
```

エージェント処理は `assertDev()` ガードで開発環境限定（既存パターンを踏襲）。

## 6. 安全性の担保

| リスク | 対策 |
|---|---|
| LLM が設計書無視の数値を生成 | `runMasterDataAudit()` が FAIL を出す。LLM の自己申告ではなくコードが判定する |
| 承認なしでファイルが書き換わる | エージェントは diff を返すだけ。書き込みは既存 Server Action 経由・ユーザー操作のみ |
| シミュレータの計算が LLM 依存になる | `BattleEngine.calculateDamage()` は変更しない。LLM はその出力を読むだけ |
| Cloudflare Workers 非互換 | Route Handler を Node.js runtime に固定 (`export const runtime = 'nodejs'`) |

## 7. 実装優先順位

| 優先度 | フロー | 効果 |
|---|---|---|
| 🔴 1 | **監査 FAIL 修正フロー** | 監査ページは毎日使う。FAIL → 手修正の往復が最も頻繁 |
| 🔴 2 | **コンテンツ生成フロー** | 第2章以降でエネミー・スキルの追加量が増える |
| 🟡 3 | **シミュレータ連動** | 生成後の数値確認を自動化 |
| 🟡 4 | **ストーリーシーン生成** | 台詞は品質センシティブ。ユーザー判断が必須 |
| 🟢 5 | **一括変更フロー** | 仕様変更時に必要。頻度は低い |

## 7.5 実装状況 — Agent A（コンテンツ生成: エネミー）✅ 実装済み（2026-06-07）

LLM は **Gemini 2.5 Flash（Google AI Studio）** を採用。`.env` の `GEMINI_API_KEY` を使用。

### ファイル構成

| ファイル | 役割 |
|---|---|
| `src/lib/agent/gemini.ts` | Gemini REST クライアント（重い SDK 非依存）。thinking 無効化・一時エラー指数バックオフ・`json` フェンス除去パーサ |
| `src/lib/agent/enemyBalance.ts` | **決定論的バリデータ**（LLM 不使用の純関数）。tier 帯を実データから学習し、構造・参照・スケール規約・tier 帯逸脱を検証 |
| `src/lib/agent/enemyAgent.ts` | LangGraph `StateGraph`。`generate → validate → (FAILなら) regenerate` ループ（最大3試行） |
| `src/app/admin/agents/actions.ts` | Server Action `generateEnemyDraftAction`。設計コンテキスト構築 + 既存マスターデータ読込 + エージェント実行。保存はしない |
| `src/components/admin/AIEnemyDraftPanel.tsx` | 新規エネミー作成フォーム上部の「AI 草案」パネル。草稿を生成 → 検証結果表示 → フォームに反映 |
| `src/components/admin/forms/EnemyForm.tsx` | `isNew` 時にパネルを表示。`onApply` で `initForm(draft)` してフォームに流し込む |

### 設計思想の実現

- **エージェントは保存しない**: 草稿を生成しフォームに流し込むだけ。永続化は既存 `saveEntry()`（保存ボタン）。
- **正しさは決定論的ゲートが判定**: LLM の自己申告ではなく `enemyBalance.ts` が PASS/WARN/FAIL を出す。FAIL なら自動再生成。
- **tier 帯は設計書ではなく実データから学習**: 設計書の数値は古くなるため、`enemies.json` の現行値から min/max を算出して逸脱を WARN。
- **スケール規約の機械検出**: LLM が `critDmg:1.5` / `resistances:-0.5`（0〜1分数）を出しがちな問題を、整数%規約として FAIL/WARN で検出 → 再生成で矯正。

### 追加対応 — ギミック / シールドの構造化（2026-06-07）

当初、難問要件の「激昂・蘇生・召喚・フェーズ」が `description` の文章止まりで、構造化された
`gimmicks` フィールドに落ちない問題があった（プロンプトのスキーマ提示に未掲載だったため）。
以下で対応:

- **プロンプト**: スキーマ提示に `gimmicks` / `shieldHp` / `maxShieldHp` を追加し、
  「激昂→`HP_BELOW_50`+`ENRAGE`」「蘇生→`HP_BELOW_50`+`REVIVE`」「シールド破壊で召喚→`ON_SHIELD_BREAK`+`SUMMON_MINIONS`」
  等のマッピング指示と「MINION には付けない」ルールを明記。
- **決定論的バリデータ**（`enemyBalance.ts`）: `gimmicks` の trigger/effect 列挙
  （`src/types/game.ts` の `BossGimmick` と同期）・value 数値・意味的整合（REVIVE は HP_BELOW_50、
  ON_SHIELD_BREAK はシールド必須）・MINION ギミック警告・shieldHp/maxShieldHp を検証。
- **テスト**: ギミック/シールドのユニットテスト 10 件追加。ライブで難問BOSSが
  `ENRAGE` / `REVIVE` / `SUMMON_MINIONS` + `shieldHp:60` を構造化出力することを確認。

> 検証量: 決定論的テストは **46 suites / 334 tests PASS**。

## 8. まとめ

管理画面の価値は「決定論的に正しさを担保できる場所」と「正規の永続化パス」にある。  
LangGraph エージェントはその**上流**に位置し、人間が設計書を読んで JSON を手書きしていた部分を補う。

- **エージェントが担う**: 設計書を読む・草稿 JSON を生成する・FAIL の原因を解釈して修正案を出す
- **管理画面が担う**: 草稿が正しいかを決定論的に検証する・ユーザーが確認して永続化する

この役割分担により「LLM の出力を盲信して壊れたデータが入る」という最大のリスクを既存インフラで防げる。
