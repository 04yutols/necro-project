# 117_DBスキーマとゲーム実装の整合性調査

> 作成: 2026-06-14
> 目的: `prisma/schema.prisma` の実カラムと、ゲーム/管理画面が SELECT・INSERT・UPDATE で
> 必要としているデータ構成を突き合わせ、不整合（DB欠落・往復しないフィールド・死蔵カラム）を洗い出す。
> ステータス: 調査完了 / 修正は未実施

---

## 1. 調査範囲と方法

- スキーマ: `prisma/schema.prisma`（全 18 モデル）
- ゲーム読み書き: `src/app/actions.ts`（Server Actions / トランザクション）、`src/store/useGameStore.ts`、`src/types/serverGame.ts`、`src/services/*`
- 管理画面: `src/app/admin/*`（後述: **DB ではなくマスター JSON を操作**するため本調査の対象軸が異なる）

照合軸: **store フィールド（ゲームが必要とする状態）↔ ServerGameData（DB往復の口）↔ DBカラム**。

---

## 2. 結論サマリ（重大度順）

| 重大度 | 項目 | 症状 |
|---|---|---|
| 🔴 High | **`transmutationPoints` が DB に無い** | ログイン時、リロードで毎回 0 にリセット（武器分解ポイントが永続しない） |
| 🔴 High | **`residueMaterials` が DB に無い** | ログイン時、残滓強化素材がリロードで毎回空にリセット |
| 🟡 Mid | **localStorage 永続が DB より多い** | ゲスト→ログインで上記2つが消える（保存層の非対称） |
| 🟡 Mid | **`SpiritCore` テーブルがゲームから書き込まれない** | read 専用。霊核はゲームプレイで付与されない（死蔵 or 別経路） |
| 🟢 Low | スキーマコメント/デフォルトの陳腐化 | `rarity` の enum 表記が古い（実値は R/SR/SSR/UR） |
| 🟢 Low | 装備スロット 7枠が死蔵 | `equipSub/Head/...Acc2` は DB往復するが「weapon only」設計で未使用 |

---

## 3. 🔴 確定ミスマッチ（DB欠落）

### 3-1. `transmutationPoints`（武器分解ポイント）
- **store**: `transmutationPoints: number`（`useGameStore.ts:256`）。武器分解で増加、錬成で消費。
- **localStorage**: 永続対象（`partialize` :395 / 復元 :424）。
- **DB**: `Character` に**カラムが存在しない**。
- **ServerGameData**: フィールド**無し**（`serverGame.ts`）。
- **loadFromServer**: `transmutationPoints: 0` を**ハードコード**（`useGameStore.ts:861`）。
- **結果**: ログインユーザーは DB ロードのたびに **0 にリセット**。ゲスト（localStorage）だけ保持される非対称。
- **第1章影響**: 武器分解（DISMANTLE タブ）は第1章で機能するため、**実害あり**。

### 3-2. `residueMaterials`（深淵の残滓 強化素材）
- **store**: `residueMaterials: ResidueMatData[]`、`addResidueMaterials`（ステージ報酬 `dropResult.materials` で加算）。
- **localStorage**: 永続対象。
- **DB**: **テーブルが存在しない**（`ResidueMaterial` モデル無し）。
- **保存**: `processStageResultAction` のトランザクションで **`dropResult.materials` を一切保存していない**（保存しているのは `weaponMaterials` のみ、`actions.ts:917`）。
- **ServerGameData**: フィールド**無し**（`weaponMaterials` だけ存在）。
- **loadFromServer**: `residueMaterials: []` を**ハードコード**（`useGameStore.ts:860`）。
- **結果**: ログインユーザーは残滓強化素材がリロードで**毎回消失**。残滓強化ループ（Lv.20まで育成）が DB 上は成立しない。
- **第1章影響**: 残滓解放は `area1_node3`（第2章導入）以降のため第1章スコープでは軽微だが、**第2章で破綻**。

> 対比: `weaponMaterials` は `WeaponMaterial` テーブル（複合PK `[userId,type]`）＋ upsert で**正しく永続**（`actions.ts:917`）。同じ素材系で残滓側だけ欠落している。

## 4. 🟡 設計レベルの非対称・死蔵

### 4-1. localStorage 永続が DB より多い（保存層の非対称）
直近の persist 修正（`necro-game-store-v1`、doc 116）は `transmutationPoints` / `residueMaterials` を localStorage に保存する。一方 DB はこれらを持たない。
→ **ゲストでプレイ→ログイン**すると `loadFromServer` が両者を 0/空で上書きし、**ゲスト進行の一部が消える**。
→ 永続の「真実」が項目ごとに食い違う（多くは DB、2項目だけ localStorage のみ）。

### 4-2. `SpiritCore` テーブルが書き込まれない
- `Monster.spiritCoreId` FK と `SpiritCore` テーブルは存在し、`loadCharacter` で `include`・`toSpiritCoreData` で**読み出す**。
- しかし**ゲームコードに `spiritCore.create` が無い**（`soulShard.create` はある: `actions.ts:1314` / `NecroService.ts:45`）。
- → 霊核はゲームプレイで付与されず、常に null。テーブルは実質**書き込み死蔵**（将来機能 or 別経路想定なら明記が必要）。

### 4-3. 装備スロット 7枠が DB往復するが未使用
- `Character.equipSub/Head/Body/Arms/Legs/Acc1/Acc2` の 7枠は include・`toServerGameData` で往復するが、ゲームは「**weapon only active**」（CLAUDE.md）で未使用。
- 機能バグではないが、**死蔵カラム**として認識しておくべき。

## 6. ✅ 整合が取れている主要項目（問題なし）

- **クリア状況** `Character.clearedStages`（String[]）↔ `array_append` で UPDATE。読み書き一致。
- **職業レベル/EXP** `UserJob`（複合PK）↔ update。`Job` テーブルは `ensureJobRow` upsert で **FK 充足**（`actions.ts:478`）。
- **武器/アイテム** `Item`（ownerId）、**残滓本体** `AbyssalResidue`（characterId + equippedResidue0-4 の5枠）、**魔物** `Monster`、**魂の欠片** `SoulShard` — いずれも create/include 一致。
- **ネクロステータス** `necroLevel/Rank/Exp/MaxCost/BaseStatsBonus` ↔ `necroStatus` マッピング一致。
- **ゴールド/パッシブ累積** `Character.gold / passive*Bonus` ↔ increment UPDATE 一致。
- **ランキング/トークン/世界ログ** `StageRecord`(unique `[userId,stageId]`) / `StageAttempt`(SEC-8) / `WorldLog`(`type/payload/authorId`、`WorldEventService` と一致) / `PlayerStats`(BigInt totalDamage) — 整合。

## 7. 管理画面の扱い（スコープ注記）

- 管理画面（`src/app/admin/*`）は **`src/data/master/*.json`（マスターデータ）を読み書き**しており、本調査の DB テーブル（`Character`/`Monster` 等の**プレイヤー進行データ**）には**書き込まない**。
- したがって「管理画面 ↔ DB スキーマ」の不整合は本質的に存在しない。
- 別軸の整合性（**マスター JSON ↔ `game.ts` 型 ↔ ランタイム読込**）は本書の対象外で、`master-data-validator` / doc 27 の領域。必要なら別途調査。

## 8. 修正案

### 修正案 A（推奨）— 欠落2項目を DB に追加して往復させる
1. **`transmutationPoints`**: `Character` に `transmutationPoints Int @default(0)` を追加。
   - `serverGame.ts ServerGameData` に追加、`toServerGameData` で読み出し、`loadFromServer` のハードコード 0 を `data.transmutationPoints` に。
   - 分解/錬成の Server Action（`dismantleWeaponAction` 等）で UPDATE。
2. **`residueMaterials`**: `ResidueMaterial` テーブル新設（`WeaponMaterial` と同型: 複合PK `[characterId,type]` or `[userId,type]` + quantity）。
   - `processStageResultAction` の transaction で `dropResult.materials` を upsert。
   - `ServerGameData` / `toServerGameData` / `loadFromServer` に往復追加。残滓強化の消費 Server Action でも UPDATE。
3. マイグレーション: `npx prisma migrate dev` ＋ `npx prisma generate`。

### 修正案 B（最小）— 永続層を localStorage に寄せると割り切る
- DB 追加せず、`transmutationPoints` / `residueMaterials` は**端末ローカル専用**と明示（doc 116 の persist がカバー）。
- ただしオンライン＝サーバー権威設計に反し、別端末で消える。**非推奨**（第2章の残滓育成が端末依存になる）。

### 修正案 C（整理）— 死蔵の明文化
- `SpiritCore` 書き込み経路の要否を決める（実装予定なら付与アクション追加、当面不要ならスキーマにコメント）。
- スキーマコメント/デフォルトの rarity 表記を実値（R/SR/SSR/UR）へ修正。

---

## 9. 推奨プラン（フェーズ）

```
Phase 1: 🔴 transmutationPoints を Character に追加し往復（修正案A-1）  ← 第1章で実害、最優先
Phase 2: 🔴 ResidueMaterial テーブル新設＋保存/復元（修正案A-2）        ← 第2章までに必須
Phase 3: 🟡 persist(localStorage) と ServerGameData の項目を一致させ非対称解消
Phase 4: 🟢 SpiritCore 方針決定 / スキーマコメント是正（修正案C）
```

工数感: Phase 1 は小（1カラム＋往復4箇所）。Phase 2 は中（新テーブル＋migration＋transaction＋往復）。
