## G1. 死霊術レベルの育成（✅ 対応確認）

### 実装
- 純粋関数 `applyNecroExpGainToSave(save, expGain)`（`PlayerSaveService.ts:500`）:
  `newExp = exp + expGain`、`newLevel = min(99, max(current.level, levelFromTotalExp(newExp)))`。
  ジョブと同じ EXP カーブ（`levelFromTotalExp`）を流用し、**単調増加・99上限・入力正規化**。
- 配線: `processStageResultForUser`（actions.ts:870）と `GameManager.processStageResult`（:182）の
  ステージクリア updater で `applyJobExpGainToSave` → `applyNecroExpGainToSave` を順に適用（同一 `expGain`）。
  gold/clearedStages と合わせ **1回のブロブ書込**に集約。

### 評価（良い点）
- **DB変更ゼロで成長軸を復活** — `necroStatus.exp/level` は P5 で既にブロブにあるため、列追加不要。推奨フォロー通り。
- **rankUp 到達不能の解消** — Lv.99 に到達できるようになり、`rankUpNecroInSave`（Lv.99要求）が機能する。
- **単調性の担保** — `max(current.level, …)` でランク内のレベル逆行を防止。rankUp 後の `level=1/exp=0` リセットとも整合。
- テスト「applies necro exp without requiring a schema change」で保存→ロードの exp/level 進行を検証。

### 指摘
- 🔵 **G1-1 [Info/balance]** necro EXP にジョブと**同一の `expGain`** を加算＝死霊術はジョブと同ペースで育つ。
  到達速度はバランス設計事項（バグではない）。Lv.99→rankUp リセットのペースが意図通りか、`balance-designer` 観点で一度確認推奨。

## G2. 深淵の残滓 強化の永続（✅ 対応確認）

### 実装
- 新規 `src/logic/ResidueEnhancement.ts`（純粋）:
  - `spendResidueMaterials(materials, matIds)` — 要求IDを集計し `min(要求, 在庫)` を消費、`expValue×消費数` を合算、
    枯渇素材を除いた新配列を返す。
  - `calculateResidueEnhancement(residue, expGain)` — `exp += gain`、`maxExp×1.5` でレベルアップ、
    `MAX_RESIDUE_LEVEL=20` で上限クランプ、最大レベル時は exp を maxExp に丸め。
- Server Action `enhanceResidueForUser`（actions.ts）:
  認証→所有キャラ確認→`getEffectiveClearedStages`（SchemaError 捕捉付き）→第2章解放ゲート→
  `SELECT … FOR UPDATE` で残滓行ロック（`characterId` 一致で所有検証）→
  `updatePlayerSaveBlob` 内で素材消費（Character 行ロック）→`AbyssalResidue.update` を**単一トランザクション**で実行。

### 評価（良い点）
- **二系統の原子的永続** — 素材（`playerState.residueMaterials`＝ブロブ）と残滓本体（`AbyssalResidue` テーブル）を
  同一 `$transaction`＋行ロックで更新。中断時の不整合が起きない。
- **サイレント no-op の防止** — `spendResidueMaterials` は未所持IDを無視するが、`if (spent.expGain <= 0) throw`
  で「何も消費できなかった」場合を確実にエラー化。
- **規約踏襲** — `cleanReferences:false`（素材消費は参照を変えない）、`FOR UPDATE` ロック、
  `residueEnhancementErrorMessage` が `PlayerSaveSchemaError` を制御メッセージへ変換（F-P5-3 と一貫）。
- クライアント（NecroLab 等）も共通計算 `ResidueEnhancement` に寄せ、表示とサーバーの算出を一致。

### 指摘
- 🟢 **G2-1 [Low / 要フォロー]** `ResidueEnhancement.ts` に **co-located ユニットテストが無い**。
  レベルアップループ・`maxExp×1.5`・上限クランプ・部分消費という非自明な純粋ロジックが、
  CI除外の DB 統合テスト経由でしか検証されていない。→ `PlayerSaveService` 同様に
  `ResidueEnhancement.test.ts` を追加し、(a) 複数レベル一括上昇、(b) Lv.20 クランプ、
  (c) 在庫超過要求時の部分消費、(d) 未所持IDのみ＝expGain0 を単体で固定化することを推奨。
- ✅ **対応**: `src/logic/ResidueEnhancement.test.ts` を追加し、上記ケースに加えて
  `applyResidueEnhancement` が残滓の identity fields を保持することも固定化。
- 🟢 **G2-2 [Low]** 部分消費が**寛容** — 在庫を超える要求は「在庫分だけ消費・残りは黙って無視」（全ゼロのみエラー）。
  UI が常に所持数内を送る前提なら可だが、クライアント/サーバーの数量ずれを隠蔽しうる。
  厳密化（要求数＝消費数を検証）するか、現仕様で問題ないことを確認しておく。
- ✅ **対応**: `spendResidueMaterials` が `requestedCount/consumedCount/missingCount` を返すようにし、
  Server Action は `missingCount > 0` を素材不足として拒否。ローカル Store の既存寛容挙動は維持。
  `account-progression.integration.test.ts` で過剰要求時にDB行が変化しないことを検証。
- 🔵 **G2-3 [style]** `enhanced` を updater 内のクロージャ変数再代入で外へ受け渡している
  （`updatePlayerSaveBlob` が updater を同期実行するため動作は正しい）。読みやすさのため、
  トランザクション戻り値で受ける形も検討可。`calculateResidueEnhancement(residue, 0)` の初期代入は
  TS の definite-assignment 充足用のプレースホルダ（無害）。
- ✅ **対応**: `calculateResidueEnhancement(residue, 0)` のプレースホルダ初期化をやめ、
  `undefined` ガードで「強化結果が計算されなかった」ケースを明示的にエラー化。
