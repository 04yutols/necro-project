## 1. 目的と位置づけ

Agent A 系（コンテンツ生成）は「新規作成」を担う。**Agent B（監査エージェント）は「既存データの違反修正」**を担う。

管理画面の `/admin/audit` は `runMasterDataAudit()` で全マスターデータを検査し FAIL/WARN/PASS を列挙するが、
現状は**違反を表示するだけ**で、修正はユーザーが手作業で行う。Agent B は各 FAIL に対し:

1. 違反エンティティの現在 JSON を読む
2. 違反している設計ルールを特定する
3. **最小変更**で違反を解消する修正パッチを LLM に生成させる
4. **決定論的に再検証**する（per-content バリデータ + 監査再実行）
5. PASS するまで自動再生成し、最終パッチを diff 付きで提示する

> **設計の核心（doc100 と同一）**: エージェントは修正案（パッチ）を出すだけ。正しさの判定は
> 決定論的ゲート（既存バリデータ + `runMasterDataAudit`）が行い、永続化は既存 `saveEntry()` が行う。
> LLM の自己申告は信用しない。

## 3. アーキテクチャ

```
[/admin/audit]  runMasterDataAudit() が FAIL 一覧を表示（既存）
      │  各 FAIL 行（または entity 単位グループ）に「AI に修正させる」ボタン（追加）
      ▼
Server Action: fixAuditFindingAction(scope, id)
      │
      ▼
LangGraph Audit-Fix Graph
  ┌─────────────────────────────────────────────┐
  │ loadEntity   getEntry(scope,id) + 関連マスター │
  │     ▼                                         │
  │ generatePatch  LLM: 現エンティティ + 該当findings + ルール → 修正済みJSON（最小変更）│
  │     ▼                                         │
  │ validate (二層ゲート)                          │
  │   1. per-content バリデータ（scope別・詳細）    │
  │   2. in-memory 監査 auditMasterData(override)  │
  │     ▼  FAIL残存 & 試行<max → regenerate へ      │
  │     ▼  PASS or 試行上限 → END                  │
  └─────────────────────────────────────────────┘
      │  パッチ + before/after diff + 検証結果
      ▼
UI: diff 表示 →「適用」→ saveEntry(scope,id,patched) → 監査自動再実行
```

**ポイント**: 一次ゲート（per-content）は詳細な再生成フィードバックを与え、二次ゲート（監査再実行）は
「対象 FAIL が消えたか」「新たな FAIL を生んでいないか」を全体整合で最終確認する。

## 4. 詳細設計

### 4.1 入力: finding のグルーピング

監査は同一エンティティに複数 FAIL を出しうる（例: enemy が necromance 欠落 + drop 参照切れ）。
Agent B は **(scope, id) 単位でグルーピング**し、そのエンティティの全 FAIL を 1 回の LLM 呼び出しで同時修正する。

```ts
type AuditFixTarget = {
  scope: string;          // 'enemies' 等
  id: string;             // エンティティキー
  findings: AuditFinding[]; // この entity に対する FAIL（+ 任意で WARN）
};
```

UI からは「この entity を修正」または「全 FAIL をまとめて修正」を選べる。

### 4.2 修正ループ（LangGraph State）

```ts
State = {
  scope, entityId,
  findings: AuditFinding[],          // 解消対象
  currentEntity: Record<string,unknown>, // 現在のJSON（getEntryで取得）
  context: ScopeContext,             // scope別の参照マスター
  patched: Record<string,unknown> | null,
  validation: { perContent, audit } | null,
  diff: FieldDiff[] | null,
  feedback: string, attempts: number, log: string[], errorMsg?
}
```

ノード:
1. `generatePatch` — プロンプト（§7）で LLM に修正済みエンティティ全体を生成させる（パッチ操作ではなく全体出力 → パースが安定。diff は後段で計算）。
2. `validate` —
   - per-content バリデータを実行（FAIL があれば feedback 化）
   - `patched` を override として `auditMasterData()` を実行し、対象 (scope,id) の FAIL が 0 かつ全体 FAIL 数が増えていないか確認
3. 条件分岐: `(perContent.ok && auditResolved) || attempts>=max` → END、それ以外 `regenerate`

### 4.3 最小変更の原則

- プロンプトで「**指摘された箇所のみ**を直し、それ以外のフィールドは現状維持」を厳命。
- 出力後に **before/after の deep diff** を計算し、変更フィールドパスのみを UI に表示。
- 変更が指摘外フィールドに及んでいたら UI で黄色強調（ユーザーが意図しない改変に気付ける）。

```ts
type FieldDiff = { path: string; before: unknown; after: unknown };
```

### 4.4 二層ゲートと in-memory 監査（必要な既存コード変更）

現在 `runMasterDataAudit()` はディスクから全 JSON を読む。**非破壊プレビュー**のため、in-memory override を
受け取れるよう薄くリファクタする:

```ts
// src/app/admin/actions.ts
export async function auditMasterData(
  override?: Partial<MasterDataCollection>   // { enemies: {...patchedEntityMerged} } 等
): Promise<AuditFinding[]> { /* 既存ロジック。読み込みだけ override で差し替え */ }

export async function runMasterDataAudit() { return auditMasterData(); } // 後方互換
```

Agent B は `auditMasterData({ [scope]: { ...allEntities, [id]: patched } })` を呼び、
- 対象 (scope,id) の FAIL が消えたか
- override 前後で全体 FAIL 件数が増えていないか（= 新規違反を作っていないか）
を判定する。**これが「LLM の修正が本当に正しいか」をコードで担保する核心**。

### 4.5 失敗時の扱い

- `maxAttempts`（既定3）試行しても PASS しない場合 → 最後の試行のパッチ + 残存 findings を提示し、
  「手動修正が必要」と明示（無理に適用させない）。
- LLM が壊れた JSON を返す → `gemini.ts` の `parseJsonLoose` で吸収、失敗時は再試行。

## 6. scopeRegistry の設計

各 scope の「バリデータ呼び出し」と「コンテキスト構築」を 1 箇所に集約し、グラフ本体を scope 非依存にする。

```ts
type ScopeEntry = {
  file: keyof MasterDataCollection;
  // 修正対象を除いた全データ + 参照集合からコンテキストを組む
  buildContext(all: MasterDataCollection, id: string): unknown;
  // パッチ済みエンティティを検証（per-content バリデータ）
  validate(patched: unknown, ctx: unknown): { ok: boolean; findings: { level: string; field: string; message: string }[] };
};

const SCOPE_REGISTRY: Record<string, ScopeEntry> = {
  enemies:    { file: 'enemies',    buildContext: ..., validate: validateEnemyDraft },
  skills:     { file: 'skills',     buildContext: ...(owner逆引き), validate: validateSkillDraft },
  demonForms: { file: 'demonForms', buildContext: ...(jobs), validate: validateDemonFormDraft },
  stages:     { file: 'stages',     buildContext: ..., validate: validateStageDraft },
  items:      { file: 'items',      buildContext: ..., validate: validateWeaponDraft },
  materials:  { file: 'materials',  buildContext: ..., validate: validateMaterialDraft },
  jobs:       { file: 'jobs',       buildContext: ...(skills meta), validate: validateJobDraft },
  areas:      { file: 'areas',      buildContext: ..., validate: validateAreaDraft },
  monsters:   { file: 'monsters',   buildContext: ..., validate: validateMonsterDraft },
};
```

> 各 `buildContext` は対象 id を除外集合にして「自分自身との重複」を誤検出しないようにする
> （= 既存エンティティの再検証では id 重複 FAIL を出さない）。

## 7. プロンプト設計（generatePatch）

```
あなたは Necromance Brave のデータ修正担当です。以下のエンティティには検証違反があります。
指摘された違反【のみ】を最小限の変更で修正し、それ以外のフィールドは現状を維持してください。

# 対象（scope: {scope} / id: {id}）
{現在のエンティティ JSON}

# 検出された違反（すべて解消すること）
{findings を [scope/id] message のリストで}

# このコンテンツの設計ルール（要点）
{scope 別ルール抜粋: enemies=tier帯/スケール, skills=power表, ... 既存バリデータの規約}

# 参照可能なID（参照切れ修正用）
{itemIds / skillIds / enemyIds 等、scope に応じて}

# 出力（修正後のエンティティ JSON のみ。説明文・マークダウン不要）
- 指摘されたフィールド以外は変更しない。
- 参照切れは実在IDに差し替える（捏造禁止）。
- 数値スケール・列挙・帯は設計ルールに従う。
```

再生成時は前回パッチの残存 findings（per-content + 監査）を追記する。

> doc100 の原則どおり、適用＝既存 `saveEntry` 経由のみ。エージェントは書き込まない。

## 9. 安全性

| リスク | 対策 |
|---|---|
| LLM が指摘外を勝手に改変 | deep diff で全変更を可視化、指摘外変更は警告表示。最小変更をプロンプトで厳命 |
| 修正が別の FAIL を誘発 | in-memory 監査で override 前後の全体 FAIL 件数を比較し、増加を検出（増えたら不合格扱い） |
| 参照IDの捏造 | per-content バリデータの参照集合チェック（FAIL）+ プロンプトで実在IDのみ許可 |
| 破壊的上書き | 適用前に diff 確認必須。永続化は既存 saveEntry のユーザー操作のみ |
| 開発環境外実行 | `assertDev()` ガード踏襲 |

## 12. Agent A 系との関係（コードの一貫性）

- Agent A（生成）と Agent B（修正）は **同じ per-content バリデータを共有**する。
  片方のルール更新が双方に効く（単一の真実）。
- 相違点は「入力」だけ: A=自然言語要件、B=既存エンティティ+違反。生成ループ（generate→validate→regenerate）は同型。
- 将来 `auditMasterData` の in-memory 化は Agent A 側でも「保存前に全体監査でドライラン」する用途に再利用できる。
