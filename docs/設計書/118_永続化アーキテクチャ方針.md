# 118_永続化アーキテクチャ方針

> 作成: 2026-06-14
> 目的: 「フィールド追加のたびにマイグレーション＋往復4箇所、漏れるとデータ消失」という
> 現状の摩擦（doc 117 で顕在化した `transmutationPoints` / `residueMaterials` 欠落）を、
> 商用オンラインゲームの標準パターンを参照して構造的に解消する方針を定める。
> ステータス: 方針提案（未実装）。前提調査: `117_DBスキーマとゲーム実装の整合性調査.md`

---

## 1. 背景（なぜ今これを決めるか）

プレイヤー個人データを **18モデルにフル正規化**（装備8スロット・パーティ3枠・残滓5枠を全FKリレーション）した結果：

- 新フィールド＝**DB列追加＋migration＋`ServerGameData`＋`toServerGameData`＋`loadFromServer` の4箇所更新**
- 往復が散在し、**`transmutationPoints` / `residueMaterials` が静かに漏れて DB 非永続**（doc 117 §3）
- localStorage persist が DB より多くを持ち、**第2の真実**が生まれた（doc 117 §4-1）

これは「実装ミス」というより**設計選択の代償**。コンテンツを高速反復するほど悪化する。

---

## 2. 商用オンラインゲームの標準パターン

### 2-1. サーバー権威（Server-authoritative）
クライアントは表示＋入力のみ。通貨・所持品・進行はサーバーが唯一の真実。自己申告は信用しない。
→ 本作の SEC-5 / SEC-8（`StageAttempt` リプレイ防止トークン）/ Server Actions は**この思想で正しい**。

### 2-2. プレイヤー private 状態は「セーブブロブ（JSONドキュメント）」
多くのガチャ/ライブサービスRPGは、個人進行を**正規化分割せず1行のJSON/protobufブロブ**で保存する。
```
player_save( user_id PK, schema_version INT, data JSONB, updated_at )
```
- **新フィールド追加にマイグレーション不要**（`data` に足すだけ）← 本作の摩擦が消える
- **保存が原子的 / ロードが1リードで速い**
- 弱点: 横断クエリ不可 → 別系統に分離（§2-3）

### 2-3. ハイブリッド（現実の本命）
| データ種別 | 置き場所 | 本作の現状 |
|---|---|---|
| 個人進行（通貨・素材・クリア状況・編成・装備参照） | **JSONセーブブロブ** | 過剰正規化（要見直し） |
| ランキング | **Redis Sorted Set** | Upstash Redis 採用済み ✓ |
| ワールドログ/ソーシャル | **追記イベントログ＋pub/sub** | Pusher + `WorldLog` 採用済み ✓ |
| 第一発見者（武器のグローバル初取得・一意採番） | **正規化テーブル** | `Item`/`ItemSerialCounter` 維持 ✓ |
| 認証 | 専用テーブル | NextAuth 採用済み ✓ |

### 2-4. セーブのバージョニング＋前方マイグレーション
ブロブに `schema_version` を持たせ、ロード時に `v(n)→v(n+1)` 変換を関数で適用。
→ ライブ運用中に**DBマイグレーション無しでフィールド追加**できる（live-service の定石）。

### 2-5. クライアントキャッシュは「真実」ではない
localStorage は UI設定・オフラインキュー・高速起動スナップショットのみ。接続時に必ずサーバーと突き合わせる。
→ 本作の「localStorage が DB に無い通貨を保持」は**この原則違反**（doc 116 の persist が裏目）。

## 3. 本作の評価（どこが合っていて、何が欠けているか）

✅ **既に商用構成の「正しい横断系」を踏襲**: Redis ランキング / Pusher ワールドログ / SEC-8 トークン / サーバー権威。
❌ **欠けている1ピース**: 「個人セーブをブロブ化して追加摩擦を消す」。個人データを過剰正規化したことが唯一の構造的負債。

---

## 4. 推奨アーキテクチャ：薄い正規化コア ＋ プレイヤーセーブJSON

### 4-1. 正規化のまま残す（横断クエリ・整合性・外部システムが必要）
- `User / Account / Session / VerificationToken`（認証）
- `Item` + `ItemSerialCounter`（第一発見者の全体クエリ・一意採番）
- `StageRecord`（ランキング） / `StageAttempt`（SEC-8） / `PlayerStats` / `WorldLog`

### 4-2. `Character.playerState JSONB` に寄せる（個人 private・追加が頻繁）
- `necroLevel/rank/exp/maxCost/baseStatsBonus`、`clearedStages`、`gold`、`passive*Bonus`
- `transmutationPoints`、`weaponMaterials`、`residueMaterials`（← 今回欠落した2件が**列追加なしで解決**）
- 装備スロット・残滓スロット・パーティ編成の**参照ID**（実体は `Item`/`Monster`/`AbyssalResidue` テーブル）

> `Item` 実体だけは所有権・採番の都合で正規化に残し、ブロブには ID 参照を持つのが綺麗。
> `Monster`/`AbyssalResidue` も当面テーブル維持（soulShard/spiritCore リレーションがあるため）、ブロブは参照IDのみ。

### 4-3. 効果
- **新フィールド追加 = ブロブの型に1行**。migration も往復4箇所も不要。今回のクラスのバグが構造的に消滅。
- 保存が原子的（`Character.playerState` を1回UPDATE）。
- `loadFromServer` / `toServerGameData` は「ブロブをパース→ store」の**1経路**に集約。

---

## 5. 移行プラン（後方互換重視・段階的）

```
Phase 0: 設計合意（本書）。playerState の TypeScript 型 (PlayerSaveV1) を定義
Phase 1: Character に playerState JSONB? を追加（nullable・migration 1回のみ）
         読み込み: playerState があればそれを優先、無ければ既存カラムからフォールバック（後方互換）
Phase 2: 今回欠落の2件を playerState に載せて即解決
         - transmutationPoints / residueMaterials を PlayerSaveV1 に追加し往復
         - これ以降の新規個人フィールドは原則 playerState に追加（列を増やさない）
Phase 3: 既存の個人カラム（necro*, gold, clearedStages, passive*）を playerState へ移送
         - 書き込みを playerState 一本化、読み出しは「playerState ?? 旧カラム」二重対応で無停止移行
         - 移送完了後、旧カラムを deprecated コメント化（削除は後続）
Phase 4: schema_version + 前方マイグレーション関数を実装（v1→v2…）
Phase 5: localStorage persist を「最終スナップショット＋オフラインキュー」に限定し真実を一本化（doc 116 整合）
```

- **Phase 1–2 だけでも** doc 117 の 🔴2件は解決し、以後の摩擦が止まる（最小到達点）。
- 各 Phase は後方互換（`playerState ?? 旧カラム`）で**無停止**。一括書き換え不要。

---

## 6. 既存設計との整合（矛盾チェック）

- **サーバー権威は不変**: ブロブ化しても真実はサーバー。クライアントは送り返さない。SEC-5/ランキング/第一発見者の信頼境界は維持。
- **横断系は据え置き**: Redis ランキング / Pusher ワールドログ / `Item` 採番はテーブルのまま（ブロブに入れない）。
- **doc 116（persist）との関係**: 本方針の Phase 5 で localStorage を「キャッシュのみ」に格下げし、doc 117 §4-1 の非対称を恒久解消。
- **トランザクション原子性**: ステージクリアは引き続き `$transaction`。`Item`/`Monster` の INSERT とブロブ UPDATE を同一トランザクションで実施。

---

## 7. 代替案（再設計したくない場合の最小保険）
正規化を維持しつつ、**「保存フィールドを列挙する場所を1箇所に集約」＋「store のフィールド ⊆ 永続フィールド を検証する契約テスト」**を導入。
今回の根本は「往復が4箇所に散って漏れた」**プロセス事故**でもあるため、これだけでも再発防止になる（ただし追加摩擦は残る）。

| 状況 | 推奨 |
|---|---|
| 第1章リリース＋AIで高速反復 | **§4 ハイブリッド（個人=JSONブロブ / 横断=Redis・正規化）** |
| 今は触りたくない | §7 最小保険（集約＋契約テスト）で漏れだけ止める |
