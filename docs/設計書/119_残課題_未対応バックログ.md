## 1. 🔵 F-P5-4. localStorage 格下げが「足場」段階（オフラインキュー未実体）

- **現状**: `useGameStore` の persist は `cacheKind`（`guest-save` / `server-snapshot`）・`cachedAt`・
  `offlineQueue` を持つが、`offlineQueue` は型 `never[]` で**常に空**。`cacheKind` は主にロード時のログ表示を駆動。
- **未対応の中身**: 「サーバーが常に真実／キャッシュは非権威」「オフライン操作をキューして再接続時に再送」という
  doc 118 §2-5 の完全形は未実装。現状は既存 `loadFromServer` フローに権威を依存（P5では未変更）。
- **影響**: 第1章スコープでは実害なし（オンライン前提）。オフライン編集の再送が必要になる将来機能で顕在化。
- **推奨フォロー**: `PersistedOfflineMutation` を実型化し、オフライン中の mutation をキュー→再接続時に
  Server Action へ順次フラッシュ。競合は `saveVersion` / `updatedAt` で楽観ロック。
- **出典**: `119_R3_P5実装レビュー.md` F-P5-4 ／ `116_リロード時データリセット…md`。

## 2. 🟡 G1. 死霊術（ネクロマンス）レベルの育成が未実装 → 対応済み

- **現状**: `playerState.necroStatus.level` を増やす経路がコードに無く常に 1、`exp` も常に 0。
  `rankUpNecroInSave` は `level < 99` で例外を投げるため、**ランクアップが恒久的に到達不能**。
- **影響**: 死霊術ランク（`maxCost`/`baseStatsBonus` 成長）が一切進まない＝編成コスト上限が固定。
  ゲームループの成長軸が1本欠けている。
- **推奨フォロー**: ステージクリア等で `necroStatus.exp` を加算し、閾値で `level` を上げる処理を
  `applyJobExpGainToSave` と同様の純粋関数（例 `applyNecroExpGainToSave`）として追加。
  P5で `necroStatus.exp` はブロブに載っているので**DB変更は不要**（ブロブ更新のみ）。
- **対応**: `applyNecroExpGainToSave` を追加し、`processStageResultForUser` / `GameManager.processStageResult` の
  ステージクリア保存でジョブEXPと同じ `expGain` を死霊術EXPにも加算。Home表示も累積EXPカーブへ揃えた。
- **確認**: `PlayerSaveService.test.ts` と `account-progression.integration.test.ts` で、保存ブロブとロード後データの
  `necroStatus.exp/level` が進むことを検証。
- **出典**: `119_DB再設計…md` §7 G1。

## 3. 🟡 G2. 深淵の残滓の強化（level/exp 育成）が永続しない → 対応済み

- **現状**: `AbyssalResidue.level/exp/maxExp` は create 時のみ書込み、**強化して育成する Server Action が無い**。
  消費素材 `residueMaterials` はブロブに溜まるだけで、消費して残滓を育てる経路が未実装。
- **影響**: 残滓解放は第2章導入（`area1_node3` 以降）のため第1章スコープでは軽微だが、**第2章で育成ループが破綻**。
- **推奨フォロー**: `enhanceResidueAction`（仮）を追加し、`residueMaterials` を消費して `AbyssalResidue.exp/level`
  を更新（実体テーブルはP4後も維持）。素材消費はブロブ、残滓実体はテーブルの二系統トランザクション。
- **対応**: `enhanceResidueAction` / `enhanceResidueForUser` を追加し、素材消費（`playerState.residueMaterials`）と
  残滓本体更新（`AbyssalResidue.level/exp/maxExp`）を単一トランザクションで永続化。残滓行は `FOR UPDATE` でロック。
  クライアント側のローカル強化も `logic/ResidueEnhancement.ts` の共通計算へ寄せた。
- **確認**: `account-progression.integration.test.ts` で第2章ゲート到達後の素材消費・残滓育成・装備スロット反映・
  DB/ブロブ永続を検証。
- **出典**: `119_DB再設計…md` §7 G2 ／ `117_…整合性調査.md` §3-2。

## 4. 🟢 G3. モンスター装備残滓が未永続

- **現状**: `MonsterData.equippedResidues`（5枠）はランタイム型のみで、`Monster` テーブルに残滓スロット列が無い。
- **影響**: モンスター個別の残滓ロードアウトを保存できない（キャラ側5枠とは別軸）。第1章では未使用想定。
- **推奨フォロー**: 仕様確定後、`Monster` に残滓参照列を足すか、`playerState` 側にモンスター別マップを持つかを決める
  （個人 private なのでブロブ寄せが方針上は自然）。
- **出典**: `119_DB再設計…md` §2-3 / §7 G3。

## 5. 🟢 G4. 霊核（SpiritCore）の付与経路が無い（P4でテーブル削除済み）

- **現状**: バトルの追撃計算は `spiritCore?` を参照する実装が残るが（optional・無害）、
  **付与＝書込経路は元から無く、P4で `SpiritCore` テーブルと `Monster.spiritCoreId` を削除**。
  → 現在は「霊核は常に未装備」で確定。
- **影響**: 霊核という成長/カスタム軸が存在しない。第1章スコープ外。
- **推奨フォロー**: 霊核を実装する場合は「付与アクション＋保存先」を同時に新設。
  保存先は方針上 `playerState`（個人 private）か、共有性が要るなら実体テーブル再追加かを設計判断。
- **出典**: `119_DB再設計…md` §5-2 / §7 G4 ／ `117_…md` §4-2。
