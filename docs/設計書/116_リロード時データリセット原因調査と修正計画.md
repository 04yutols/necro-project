# 116_リロード時データリセット原因調査と修正計画

> 作成: 2026-06-14
> 症状: ページをリロードすると クリア状況・レベル等ほとんどのデータが初期値に戻る。
> ステータス: 調査完了 / 修正計画（未実装）

---

## 1. 結論（根本原因）

**`useGameStore` は `persist` を使っておらず、ゲーム進行（player / level / clearedStages / party / inventory）は完全にメモリ上のみ。**
リロードで状態は必ず破棄され、その後の復元は**起動フローが DB ロードに成功した時だけ**成功する。
ロード経路が「ゲスト（モック再シード）」や「認証要求」に落ちると、`initialize()` が**レベル1のモックデータを毎回再生成**するため、全リセットに見える。

```
useGameStore = create<GameState>((set) => ({ ... }))   // ← persist ラッパー無し（src/store/useGameStore.ts:325）
```
対照的に **ストーリー / チュートリアルは localStorage 永続**（`useStoryStore` / `useTutorialStore`）なので残る。
→ 「ストーリーの既読は残るのにレベルは消える」という非対称はこれが原因。

---

## 2. 起動時のデータ復元フロー（`src/hooks/useAuthFlow.ts`）

```
boot()                                                  useAuthFlow.ts:94
 └ fetchAuthSession()  → GET /api/auth/session
     ├ JSON で取得できない (available=false)
     │     → initialize()           ← ★モック再シード（level1, clearedStages空）→ status 'guest'
     ├ JSON だが user.id 無し
     │     → clearServerData() → status 'authRequired'（ログイン画面）
     └ user.id あり
           → loadCharacterWithRetry() → loadFromServer(data) → status 'ready'   ← これだけが進行維持
```

### `initialize()` が再シードする初期値（`useGameStore.ts:789`〜）
- `level: 1, rank: 1, maxCost: 10, exp: 0`
- `clearedStages: initialClearedStages`（E2E用 sessionStorage 以外は**空配列**）
- `isServerBacked: false`

### 関連する事実
- **DB 保存自体は実装済み**: `actions.ts:936`（`exp/level`）/ `actions.ts:987`（`clearedStages: { push }`）。保存先の口は存在する。
- **保存は Next.js ランタイムでのみ試行**: `processStageResultLocal` は `isNextClientRuntime()`（`window.__NEXT_DATA__` 判定、`BattleCanvas.tsx:562`）が真のときだけ `processStageResultAction` を呼ぶ。**Vite（`dev:ui`）では false → DB 保存をスキップ**しローカル即席結果のみ。

## 3. 根本原因の候補（どれかは §5 の手順で確定）

| # | 状況 | 起動フローの着地 | リロード時の症状 | 典型ケース |
|---|---|---|---|---|
| **A** | **`npm run dev:ui`（Vite）で動作** | `/api/auth/session` が JSON 不可 → **guest** → `initialize()` | **毎回フルリセット**。さらにクリアも DB 未保存 | UI 高速イテレーション中。最有力 |
| **B** | `npm run dev`（Next）だが未ログイン | session に user 無し → `authRequired` | ログイン画面に戻る（プレイ続行不可） | ログインしていない |
| **C** | ログイン済みだがセッションが継続しない | reload で user 消失 → authRequired/guest | フルリセット/ログイン要求 | `AUTH_SECRET` 未設定・Cookie 不持続・sessionVersion 失効(SEC-6) |
| **D** | ログイン済み・セッションOKだが DB 書込失敗 | ready だが古い DB をロード | 直近の進行だけ消える（部分損失） | 保存処理の失敗・タイムアウト(3.5s) |

**症状「ほとんどのデータがリセット」＝初期値に戻る、は A もしくは C（guest 再シード経路）に最も一致。**

---

## 4. 設計上の問題点（なぜこうなっているか）

- 本作はオンライン＝**サーバー権威**設計（SEC-5 ドロップ整合 / ランキング / 第一発見者）。よって `useGameStore` を非永続にし「DB が唯一の真実」とするのは**意図的**。
- しかし起動フローに **「DB ロード失敗時の安全網が無い」**。ゲスト時は `initialize()` でモックを毎回作り直すだけで、**前回のゲスト進行を保持する仕組みが無い**。
- 結果、ログイン経路が少しでも崩れると即フルリセットに見える。**堅牢性（resilience）が欠落**している。

---

## 5. 確定手順（実装前の切り分け — コードは触らない）

`useAuthFlow.ts` には診断用 `console.log('[AuthFlow] ...')` が既に入っている。**リロード直後のブラウザ Console** を見て着地を特定する：

| Console 出力 | 着地 | → 該当原因 |
|---|---|---|
| `→ guest`（`fetchAuthSession available:false`） | ゲスト再シード | **A**（Vite）/ デプロイで auth 到達不可 |
| `→ authRequired` | 未ログイン | **B** / **C**（セッション切れ） |
| `→ ready` なのにデータが古い/欠落 | DBロード成功 | **D**（保存失敗） |
| `→ error` | ロード失敗 | DB 到達不可（Neon DNS 等） |

あわせて確認：
1. 起動コマンドが `npm run dev`（フル）か `npm run dev:ui`（Vite, 保存不可）か。
2. `.env.local` の `AUTH_SECRET` / `DATABASE_URL` が設定済みか。
3. DevTools → Application → Cookies にセッション Cookie が**リロード後も残るか**。

## 6. 修正案

### 方針判断（プロダクト要件次第）
「ログイン必須でDB権威」なのか「未ログインでも遊べてローカル保持」なのかで対応が変わる。

### 修正案 1（推奨・堅牢性）— ゲスト/オフライン用に `useGameStore` を localStorage 永続化
- `useGameStore` を `persist` でラップし、`partialize` で `player / necroStatus / party / inventory* / clearedStages / weaponMaterials` を保存。
- **サーバー権威を壊さないガード必須**:
  - ログイン成功時は `loadFromServer(data)` が**常に localStorage を上書き**（DB が勝つ）。
  - 永続データは**クライアント利便のみ**。サーバーは一切信用しない（送り返して真実にしない）。SEC-5/ランキング整合に影響させない。
- 対象ファイル: `src/store/useGameStore.ts`（persist 追加 + `isServerBacked` による優先制御）

### 修正案 2（正攻法）— ログイン継続経路を堅牢化
- `AUTH_SECRET` 設定・Cookie 持続・`sessionVersion`（SEC-6）失効条件を確認し、`→ ready` を安定化。
- `dev:ui` ではなく `npm run dev` で全機能テストする運用を明文化（README へ追記）。
- `processStageResultLocal` のタイムアウト(3.5s)失敗時に**ユーザーへ保存失敗を通知**（現状は `console.warn` のみで握りつぶし）。

### 修正案 3（UX）— モードの可視化と安全網
- guest/server-backed を UI に明示（「ゲスト：進行は端末内のみ」バナー等）。サイレントなフルリセットを防ぐ。
- ゲスト→ログイン時に**ローカル進行を DB へマージ移行**するフロー（任意・大きめ）。

## 7. 推奨プラン（フェーズ）

```
Phase 0: 切り分け（§5）          — Console の [AuthFlow] 着地で A/B/C/D を確定（最優先・コード変更なし）
Phase 1: 原因別の即時対処
         - A/B なら: npm run dev で検証する運用へ + README 明記
         - C なら:   AUTH_SECRET / Cookie / sessionVersion を是正
         - D なら:   保存失敗の通知＋リトライ（修正案2）
Phase 2: 堅牢性（修正案1）        — useGameStore の localStorage 永続化（サーバー権威ガード付き）
Phase 3: UX（修正案3）           — モード可視化、ゲスト→DB マージ（任意）
```

工数感: Phase 0 はゼロ（観測のみ）。Phase 2 が中心で、`persist` 追加 + 「DB が常に勝つ」優先制御 + 回帰テストが要点。

---

## 8. 既存設計との整合（矛盾チェック）

- **サーバー権威モデルを壊さない**: 修正案1は「ログイン時は DB が常に上書き／ローカルは未ログイン時の利便のみ」を厳守。SEC-5（ドロップ整合）・ランキング・第一発見者の信頼境界は不変。
- **ストーリー/チュートリアル（localStorage）との一貫性**: それらは既に端末ローカル。修正案1でゲーム進行も同方式の安全網を持たせると、`116`以前に指摘した「DB(clearedStages) と localStorage(進行) の非対称」も緩和される（[[115]] の HOME 強制やチュートリアル再発火問題にも波及）。
- **E2E**: `initialClearedStages` は sessionStorage(E2E)経由。persist 追加時は E2E 初期化と衝突しないようキー分離・テスト更新が必要。
