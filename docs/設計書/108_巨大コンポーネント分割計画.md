## リスクと検証

- **iOS Safari ルール（overflow:hidden と transform の同居禁止）**: 各大ビューは `motion.div(transform) > div(overflow:hidden)` の 2 層構造（例: GearHubView 2443-2463、MonsterPickerPage 3729-3741）。**JSX をファイル移動する際に、この 2 層を 1 つのコンポーネントの返り値ごと丸ごと移すこと。途中で `<>` ラップやレイアウト div を追加・削除しない。** Phase ごとに `/ios-audit` を移動対象ファイルに対して実行する。
- **AnimatePresence の key 安定性**: ルーターの `key="list"/"detail"/"gear"`（4174/4182/4191）は出入りアニメに必須。コンポーネントをファイル分割しても **JSX 上の key と mount/unmount タイミングを変えない**こと。
- **サーバーアクションの dynamic import パス**: L11 抽出時、`import('../../app/actions')` の相対深度が変わる。新ファイル `legion/useGearActions.ts` からは正しい相対パスへ修正必須（`tsc` で検出可能）。
- **Zustand セレクタの粒度**: LegionListView は個別セレクタ（`useGameStore(s => s.setParty)` 等、3868-3874）を使い再レンダー最適化している。L13 フック化の際も**個別セレクタ形式を維持**し、`const { ... } = useGameStore()` の一括取得に退行させない。
- **検証手順（各 Phase 共通）**: (1) `npx tsc --noEmit`、(2) `npm test`、(3) `/ios-audit src/components/legion/<移動先>`、(4) 手動スモーク（編成→詳細→装備→残滓強化の往復で AnimatePresence が破綻しないこと）。

## リスクと検証

- **`enemyTurnSerialRef` クロージャ整合性（最重要）**: 敵ターンのスケジュール（`runEnemyTurn`, 2808-）は `setTimeout` の中で `enemyTurnSerialRef.current` の値を**キャプチャ時点と発火時点で比較**し、魔神化割り込み/敗北でインクリメントされていれば中断する（NM-3, NC-1）。**B7 抽出時、シリアル比較を行う関数を分離する場合は、比較対象の ref を引数で渡し、`const serial = enemyTurnSerialRef.current` のキャプチャを呼び出し側に残す**。フック境界でキャプチャタイミングをずらすと「接続バグの温床」が再発する。検証: 魔神化割り込み・敗北・WAVE クリアの 3 経路で敵 setTimeout が二重発火しないことを手動確認。
- **バトル init ガードの再マウント安全性**: `shouldInitializeBattle(initializedBattleKeyRef.current, battleKey)`（2236）は StrictMode 二重マウント / HMR での全 state リセット重複を防ぐ。**この effect 本体はメインに残す**（フックへ出さない）。`page.tsx` の `dynamic(() => import(...).then(mod => mod.default), { ssr:false })` 契約（default export）を維持。
- **iOS Safari ルール**: ルート return（3214-）は `div(overflow:hidden)` 直下にトップ HUD/Arena/Command を並べる構造。`BattleArena`（1251, `overflow:hidden` かつ `animation: shake`＝transform 系）は**単一要素に overflow:hidden と transform を持たないよう、shake を擬似要素/内側要素で当てている既存実装を変更しない**。HUD 部品を B6 へ移す際、ラッパ div を増減させない。Phase 3 完了後に `/ios-audit src/components/battle/hud src/components/battle/overlays` を実行。
- **60fps 制約**: 本ファイルはレンダーループを持たないが、`floats`/`skillEffect` の頻繁な setState がある。フック抽出で**追加の useEffect / 再計算を挿入しない**（純粋な関数移動に限定）。`spawnFloat` 等は `effectIdRef` のインクリメントで一意キーを払い出しており、この方式を保持。
- **重複防止**: ダメージ計算は `BattleDamage.calculateBattleDamage`、ターン順は `TurnOrderSystem`、ギミックは `BossGimmickSystem`/`AreaGimmickSystem`、状態異常は `StatusAilmentSystem`、敗北は `PlayerDefeat` に**既に集約済み**。本計画で新規ロジックは作らず、Canvas 側フックは「ref/state への配線」のみを担う。`B3` のビルダーは logic 層に無い Canvas 固有整形なので `battle/` に置き、logic 層へは移さない。
- **検証手順（各 Phase 共通）**: (1) `npx tsc --noEmit`、(2) `npm test`（BattleEngine/TurnOrderSystem/BossGimmickSystem/AreaGimmickSystem/PlayerDefeat/DemonizationSystem の全スイート）、(3) Phase 3/7 後に `/ios-audit`、(4) 手動スモーク: 通常攻撃→術→魔神化（敵ターン割り込み含む）→ボス REVIVE→WAVE クリア→敗北 の各経路で setTimeout 二重発火・ResultScreen 重複遷移が無いこと。

## 補足（両ファイル共通の重要所見）

1. **Pixi リスクは BattleCanvas には実在しない**（SVG/CSS 実装）。CLAUDE.md の「BattleCanvas.tsx (PixiJS)」記載は実態と乖離している。Pixi 利用は `MapCanvas.tsx` 等の別ファイル。BattleCanvas の真の再初期化リスクは `initializedBattleKeyRef` ガードであり、本計画はそれを保護対象に置いている。
2. **両ファイルとも Jest から直接 import されていない**ため、回帰検証の主軸は `npx tsc --noEmit` + 既存ロジックスイート + `/ios-audit` + 手動スモーク。コンポーネント単体テストは現状存在しない。
3. **ロジック層は両者ともほぼ抽出済み**。本作業は「巨大 UI ファイルの物理分割」と「ステートフル配線のフック化」が本質で、`src/logic/` への新規ロジック追加は不要。
