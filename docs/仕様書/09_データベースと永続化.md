# 09 データベースと永続化

> 最終更新: 2026-07-11 ｜ 生成方法: コードからのリバースエンジニアリング（コードが正） ｜ 主要ソース: `prisma/schema.prisma`, `src/services/PlayerSaveService.ts`, `src/types/playerSave.ts`, `src/app/actions.ts`, `src/logic/StageResultPersistence.ts`, `src/logic/GameManager.ts`, `src/services/RankingService.ts`, `src/services/{AuthService,SessionSecurityService,NecroService,JobService,WorldEventService}.ts`, `src/store/useGameStore.ts`, `src/lib/prisma.ts`

本書は Necromance Brave の永続化層の現行実装仕様である。データベースは PostgreSQL（Neon serverless）+ Prisma。プレイヤー個人の進行データは `Character.playerState`（JSONB のセーブブロブ、現行 schemaVersion 3）を**唯一の真実**とし、横断クエリが必要なもの（アイテム所有・第一発見者・ランキング・リプレイ防止トークン・ワールドログ）のみ正規化テーブルで持つハイブリッド構成。すべての書き込みはサーバー権威（Server Actions + `$transaction`）で行い、クライアントの localStorage は端末キャッシュに過ぎない。

## 1. アーキテクチャ概要

| 層 | 実装 | 根拠 |
|---|---|---|
| DB 本体 | PostgreSQL（`datasource db: provider = "postgresql"`） | `prisma/schema.prisma` |
| 接続 | Neon serverless driver（`@prisma/adapter-neon` + `driverAdapters` preview）。非 production では `ws` を WebSocket ポリフィルとして注入（`WS_NO_BUFFER_UTIL='1'`）。PrismaClient は `globalThis` シングルトン | `src/lib/prisma.ts` |
| 個人進行 | `Character.playerState` JSONB ブロブ（`PlayerSaveData`、schemaVersion 内包） | `src/types/playerSave.ts` |
| エンティティ実体 | `Item` / `Monster` / `AbyssalResidue` / `SoulShard` テーブル。ブロブは **ID 参照のみ**を持つ | `prisma/schema.prisma` |
| ランキングキャッシュ | Upstash Redis REST API（GET/SET/DEL 直叩き、TTL 300 秒、未設定時は素通し） | `src/services/RankingService.ts` |

| クライアントキャッシュ | zustand `persist` → localStorage（§9） | `src/store/useGameStore.ts` |

書き込み経路は Server Actions（`src/app/actions.ts`）にほぼ集約されている。DB に触れる production コードは `src/app/actions.ts`, `src/auth.ts`, `src/app/api/auth/login/route.ts`, `src/lib/prisma.ts`, `src/logic/GameManager.ts`, `src/services/{AuthService,JobService,NecroService,RankingService,SessionSecurityService,WorldEventService}.ts` のみ（grep で確認）。`GameManager` はどの production コードからも import されていないレガシー/テスト用経路である（§10）。

## 3. playerState ブロブ（PlayerSaveData v3）

### 3-1. 構造（`src/types/playerSave.ts`）

```jsonc
{
  "schemaVersion": 3,                     // PLAYER_SAVE_SCHEMA_VERSION = 3
  "player": {
    "name": "アルド",
    "currentJobId": "warrior",
    "gold": 50000,
    "clearedStages": ["area1_node1", ...],
    "jobs": [{ "jobId": "warrior", "level": 1, "exp": 0 }],   // UserJobState[]
    "passives": { "passiveAtkBonus": 0, "passiveDefBonus": 0, "passiveSpdBonus": 0,
                  "passiveCritRateBonus": 0, "passiveCritDmgBonus": 0, "passiveHpBonus": 0 },
    "necroStatus": { "level": 1, "maxCost": 6, "exp": 0 },    // v3: rank/baseStatsBonus は廃止（Lvから導出）
    "equipmentIds": { "weapon": null, "sub": null, "head": null, "body": null,
                      "arms": null, "legs": null, "acc1": null, "acc2": null },  // Item.id 参照
    "partyMonsterIds": [null, null, null],                    // Monster.id 参照（3枠固定）
    "equippedResidueIds": [null, null, null, null, null]      // AbyssalResidue.id 参照（5枠固定）
  },
  "weaponMaterials": [{ "type": "IDEA_COMMON", "name": "...", "quantity": 0 }],
  "residueMaterials": [{ "id": "...", "name": "...", "quantity": 0, "expValue": 0, "rarity": "COMMON" }],
  "transmutationPoints": 0
}
```

新規キャラクター初期値（`emptyPlayerSave()`, `src/services/PlayerSaveService.ts`）: name アルド / currentJobId warrior / **gold 50000** / jobs `[{warrior, Lv1, exp0}]` / necroStatus `{level:1, maxCost:calcNecroMaxCost(1)=6, exp:0}`（`calcNecroMaxCost = base6 + floor(level/10) + (rank-1)*2`, `src/logic/NecroGrowthSystem.ts`）。

### 3-2. バージョニングと前方マイグレーション

| 定数 | 値 | 根拠 |
|---|---|---|
| `PLAYER_SAVE_SCHEMA_VERSION` | **3** | `src/types/playerSave.ts` |
| `MIN_SUPPORTED_PLAYER_SAVE_SCHEMA_VERSION` | **1** | 同上 |

ロード時に `migratePlayerSaveSchema()`（`src/services/PlayerSaveService.ts`）が while ループで v1→2→3 と鎖状に前方移行する（アプリ側遅延移行が正。DB 一括スタンプは shape 不変の昇格のみ = v2 昇格時の SQL migration）。

| 移行 | 内容 |
|---|---|
| v1 → v2 | `schemaVersion: 2` のスタンプのみ（shape 不変） |
| v2 → v3 | necroStatus 再編。旧 `{level(1-99?), rank(1-10), maxCost, baseStatsBonus, exp}` → 新 `{level, maxCost, exp}`。**新 level = (旧rank − 1) × 50 + 旧level**（`clampNecroLevel` で 1〜500 に制限）、maxCost = `max(calcNecroMaxCost(新level), 旧maxCost)`。rank は以後 `deriveNecroRank(level) = clamp(floor((L-1)/50)+1, 1, 10)` で導出、baseStatsBonus は廃止 |

エラー方針: `playerState` が欠損/非オブジェクト、`schemaVersion` 欠損・非整数、対応最小版未満、**現行版より未来**、のいずれも `PlayerSaveSchemaError` を投げる（サイレント初期化しない）。Server Actions 側は `playerSaveSchemaErrorMessage()` で捕捉し「セーブデータの形式が不正です。サポートに連絡してください。」を返してサーバーログへ記録する（`src/app/actions.ts`）。

### 3-3. 正規化（`readPlayerSave()`）

ロードのたびに全フィールドを正規化する。主な規則:
- 数値は `normalizePositiveInt`（非有限→fallback、`Math.max(0, floor)`）。
- `jobs` は `{jobId, level>=1, exp>=0}` に正規化、空なら `[{warrior,1,0}]`。
- `necroStatus.maxCost` は **`max(calcNecroMaxCost(level), 保存値)`**（レベル由来の下限保証）。
- `partyMonsterIds` は長さ 3、`equippedResidueIds` は長さ 5 の nullable タプルに強制。
- `weaponMaterials` は type 単位で quantity をマージ、`residueMaterials` は id 単位でマージ（rarity は COMMON/RARE/EPIC/LEGENDARY のみ許可、quantity<=0 は捨てる）。

### 3-4. `saveVersion` 列との同期

`updatePlayerSaveSnapshot()` と `createCharacterForUser()` は書き込み時に必ず `saveVersion: PLAYER_SAVE_SCHEMA_VERSION`（=3）を併記する。列はブロブ内 schemaVersion の横断クエリ用ミラーであり、読み出しの真実はブロブ側。

## 4. セーブ更新の共通経路 — `updatePlayerSaveSnapshot()`

個人進行のすべての書き込みは `src/services/PlayerSaveService.ts` の `updatePlayerSaveSnapshot(tx, characterId, updater?, options?)` を経由する（トランザクション内でのみ使用）。処理順:

1. **行ロック**: `lockCharacterForUpdate()` — `SELECT id FROM "Character" WHERE id = $1 FOR UPDATE`（素材減算などの原子性はこのロックで担保。旧 `WeaponMaterial` テーブルの `updateMany gte` 減算の代替）。
2. `readPlayerSave(playerState)` でブロブを移行+正規化して読む。
3. `options.weaponMaterialAdditions` / `options.residueMaterialAdditions` をマージ加算。
4. `updater(draft, { character })` を適用（クローンに対して。戻り値 or 変異どちらも可）。
5. **参照掃除**（`options.cleanReferences === false` でスキップ可、`cleanReferenceScopes` で範囲指定可）:
   - `equipment`: `equipmentIds` の各 Item.id が `ownerId = userId` の Item に実在しなければ null 化
   - `party`: `partyMonsterIds` の各 Monster.id が `characterId` 所有でなければ null 化
   - `residue`: `equippedResidueIds` も同様
   - `currentJobId` が `jobs` に無ければ Lv1 で補完。name 空なら「アルド」
   （旧スキーマの FK `onDelete: SetNull` が担っていた掃除のアプリ側代替）
6. `playerSaveToJson()` で正規化シリアライズし、`playerState` + `saveVersion` を 1 UPDATE。

素材消費は `spendWeaponMaterialsInSave()`（不足時「武器強化素材が不足しています」を throw → トランザクション全体ロールバック）/ `spendResidueMaterials()` で行う。

## 5. ロード/キャラクター作成フロー

### 5-1. ロード（`loadCharacterAction` → `loadCharacterForUser`, `src/app/actions.ts`）

1. `auth()` セッション確認（失敗 → `{status:'UNAUTHENTICATED'}`）。
2. `prisma.character.findUnique({ where: { userId }, include: { abyssalResidues, soulShards } })`。無ければ `{status:'NO_CHARACTER'}`。
3. 並列で `item.findMany({ ownerId })`（id 降順）と `monster.findMany({ characterId, include: { soulShard } })`（id 昇順）。
4. `toServerGameData()` で `ServerGameData` を構築（§8）。`PlayerSaveSchemaError` は `{status:'ERROR'}` に変換。

戻り値 `LoadCharacterResult`（`src/types/serverGame.ts`）: `UNAUTHENTICATED | ERROR | NO_CHARACTER | READY`。

### 5-2. キャラクター作成（`createCharacterForUser`）

- 名前は trim 後 **2〜16 文字**、jobId はマスターデータ実在チェック。1 ユーザー 1 キャラ（既存なら既存データを返す）。
- トランザクションで: ①職業別スターター武器を `Item` に create（warrior→`bone_cleaver`, mage→`apprentice_cinder_staff`, dark_priest→`mourning_bell_crozier`, rogue→`grave_thorn_dagger`）、②`emptyPlayerSave()` に名前/職業/武器 ID を設定し、`weaponMaterials` に初期素材 `INITIAL_WEAPON_MATERIALS`（IDEA_COMMON×8, ABYSSAL_OBSIDIAN×10、`src/logic/WeaponSystem.ts`）を設定して `Character` を create。

## 6. ステージ結果の永続化

### 6-1. ステージ開始（`startStageForUser`）

1. セッション確認 → マスターデータからステージ取得（`STAGE_ID_ALIASES: '1-1' → 'area1_node1'` の別名解決あり）。`nodeType === 'SAFE'` は `STAGE_NOT_PLAYABLE`。
2. `getEffectiveClearedStages()` + `isStageUnlocked()` で解放判定（未解放 → `STAGE_LOCKED`）。
3. `StageAttempt` を create（`expiresAt = now + 2h`）し `stageAttemptId` を返す。

### 6-2. リザルト処理（`processStageResultForUser`）— 単一トランザクション

`stageAttemptId` 必須（無ければ `MISSING_STAGE_ATTEMPT`）。メトリクスは事前に `normalizeStageClearMetrics()` で検証・キャップ（§6-3）。トランザクション内の順序:

1. **トークン消費**: `stageAttempt.updateMany({ id, userId, characterId, stageId, consumedAt: null, expiresAt > now } → { consumedAt: now })`。失敗時は詳細エラーに分解: `INVALID_STAGE_ATTEMPT` / `TOKEN_USER_MISMATCH` / `TOKEN_CHARACTER_MISMATCH` / `TOKEN_STAGE_MISMATCH` / `STAGE_ATTEMPT_CONSUMED` / `STAGE_ATTEMPT_EXPIRED`。
2. `Character` を `FOR UPDATE` ロックしてブロブ読み込み。
3. EXP 計算（`RewardService.calculateExp`）、ドロップ抽選（`processStageDropTable` + `processStageNecromance`。ネクロマンス成功率は `deriveNecroRank(necroStatus.level)` 補正）。
4. **武器保存**: 各ドロップ武器を `Item.create`。発見対象レア度（SSR/UR/LR/UNIQUE/HIDDEN_UNIQUE または isUnique）は `ItemSerialCounter.upsert` で連番採番し、世界初なら `discovererId/discovererName/discoveredAt` を刻んで `UR_DISCOVERED`/`SSR_DISCOVERED` ワールドイベントを作成。
5. 消費アイテム → `Item.create`、残滓 → `AbyssalResidue.create`、ネクロマンス魔物 → `Monster.create`（8 ステータス + energy + resistances + skillIds）。
6. **ブロブ更新**（`updatePlayerSaveSnapshot`）: 職業 EXP 加算（レベルアップ時は levelBonuses をパッシブへ累積）→ ネクロ EXP 加算（`necroExpFromGain = floor(expGain × 1.5)`）→ gold 加算 → `clearedStages` へ stageId 追加（重複なし）。同時に素材ドロップ（`materials` / `weaponMaterials`）をブロブへ加算。
7. **ランキング記録**: `RankingService.recordStageClear()`（§7）。
8. **ワールドイベント**: ボスステージ（`nodeType === 'BOSS'` or `isAreaBoss`）の世界初クリアで `BOSS_CLEARED`、黄泉の階層の 10 階刻み初回クリアで `YOMI_MILESTONE`（`getYomiMilestoneFloorForFirstClear`, `src/logic/YomiFloors.ts`）、残滓スコア世界一更新で `RANKING_UPDATED`。

トランザクション成功後（外側）: `RankingService.invalidate()`（Redis キー削除）→ `publishWorldEvents()`（Pusher 配信）→ `loadCharacterForUser()` で最新 `ServerGameData` を再取得して返す。

### 6-3. メトリクス検証（`normalizeStageClearMetrics`, `src/services/RankingService.ts`）

非有限値・turnCount<1・clearTimeSec<1・totalDamage<0 は `INVALID_STAGE_RESULT_META`。デフォルト: turnCount=10、clearTimeSec=turnCount×5、totalDamage=0。上限キャップ（`getStageMetricCaps`, `src/app/actions.ts`）:

| メトリクス | キャップ |
|---|---|
| turnCount | `max(30, waveCount × 30)` |
| clearTimeSec | `60 × 60`（1 時間） |
| totalDamage | `max(1000, ステージ総敵HP × 4)`（REVIVE ギミック分の HP を含む） |

### 6-4. クライアント側フロー（`src/logic/StageResultPersistence.ts` + `src/components/battle/BattleCanvas.tsx`）

- `requiresCloudStageSave(ctx)` = `hasStageId && (requiresCloudSave || isServerBacked || hasStageAttempt)`。true ならクラウド保存必須（失敗は throw、タイムアウトなしで待つ）。
- false（ゲストプレイ等）の場合のみローカルフォールバック可: `processStageResultAction` を `LOCAL_STAGE_RESULT_TIMEOUT_MS = 3500` ms でタイムアウトさせ、失敗時はクライアント内でドロップ抽選して zustand に直接反映（`cloudSaved: false`）。
- `SESSION_EXPIRED` エラー時は `necro-session-expired` イベントを dispatch して再ログインを促す。

## 7. StageRecord / PlayerStats / ランキング（`src/services/RankingService.ts`）

### 7-1. `recordStageClear(tx, input)`

- `StageRecord` は `[userId, stageId]` 一意のベスト記録。**improved 判定**: 記録なし、または `turnCount` がより小さい、または同 turnCount で `clearTimeSec` がより小さい場合のみ update（`clearedAt` も更新）。
- `PlayerStats.upsert`: `totalDamage` は **increment**（累計）、`bossKillCount` はボスステージなら +1、`bestResidueScore` は `max(現値, 今回)`、`bestDungeonFloor` は `max(現値, getYomiFloorNumber(stageId) ?? 0)`（黄泉ステージ `yomi_bNN` のみ階数が入る。不可逆）。
- 戻り値に `becameTopResidue`（今回スコアが更新前の全体トップ超え）を含む。

### 7-2. `getRanking(type, options)`

| RankingType | ソース | ソート |
|---|---|---|
| STAGE_TIME | StageRecord（stageId 絞り込み可） | turnCount asc → clearTimeSec asc |
| TOTAL_DAMAGE | PlayerStats | totalDamage desc |
| BOSS_KILLS | PlayerStats | bossKillCount desc |
| DUNGEON_FLOOR | PlayerStats | bestDungeonFloor desc |
| その他（RESIDUE_SCORE） | PlayerStats | bestResidueScore desc |

limit は 1〜100 にクランプ（デフォルト 50）。Redis キー `ranking:{type}:{stageId|global}:{limit}`、TTL 300 秒。`invalidate()` は limits `[5,10,50,100]` × {RESIDUE_SCORE, TOTAL_DAMAGE, BOSS_KILLS, DUNGEON_FLOOR の global / STAGE_TIME の area1_boss} を削除する。プレイヤー表示名は `displayName ?? name ?? email ?? '名もなき死霊術師'`。

## 8. Character ⇔ ゲーム内型のマッピング

### 8-1. `toServerGameData()`（`src/app/actions.ts`）— DB → `ServerGameData`

| ServerGameData / CharacterData | ソース |
|---|---|
| `player.id` | `Character.id` |
| `player.name / currentJobId / gold / clearedStages / jobs / passives` | `playerState.player.*` |
| `player.baseStats` = `player.stats` | **保存しない。ロード時に再計算**: `getJobBaseStatsAtLevel(currentJob, currentJobLevel)`（`src/logic/JobGrowthSystem.ts`） |
| `player.currentEnergy / maxEnergy` | 再計算: `calculateEnergyState(currentJob, currentJobLevel)`（`src/logic/EnergySystem.ts`） |
| `player.category` | 職業マスター（jobs.json）の `category` |
| `player.necroLevel` | `playerState.player.necroStatus.level` |
| `player.equipment`（8 スロット） | `equipmentIds` の Item.id を所持 Item 一覧から解決（見つからなければ null） |
| `player.baseResistances` / `isAwakened` / `elementDmgBoosts` | サーバー側では固定値 `{}` / `false` / `{}`（装備・残滓由来の派生はクライアント store 側で計算） |
| `necroStatus` | `playerState.player.necroStatus`（rank は型に含まれない。UI は `deriveNecroRank(level)` で導出） |
| `party` | `partyMonsterIds` → 所持 Monster 解決（3 枠） |
| `equippedResidueSlots` | `equippedResidueIds` → AbyssalResidue 解決（5 枠）。ただし残滓未解放（`clearedStages` に `area1_node3` 無し）なら全 null |
| `inventoryMonsters / inventoryItems / abyssalResidues / soulShards` | 各テーブル行を `toMonsterData / toItemData / toResidueData / toSoulShardData` で変換 |
| `weaponMaterials / residueMaterials / transmutationPoints` | ブロブ直読 |

### 8-2. 行 → 型変換の要点

- **Monster 行 → MonsterData**（`toMonsterData`）: 8 ステータスは `toBaseStats()` でデフォルト補完（critRate 5 / critDmg 150 / 他 0。ただし DB 行には列があるので通常そのまま）。`hydrateMonsterEnergy()` で `currentEnergy <= maxEnergy` を保証。`soulShardId` → `equippedShardId`。`equippedResidues` / `spiritCore` に対応する DB 列は**存在しない**（ランタイム専用・未永続）。
- **SoulShard 行 → SoulShardData**: `originMonster` → `originMonsterName`、atkBonus/elementDmgBoost/specialAbility は `effect` にネスト。
- **BattleEngine への注入**: パーティモンスターは `applyNecroToMonster(monster, necroLevel)` で HP/ATK/DEF/SPD にネクロ倍率 `1 + min(L,50)×0.006 + max(0,L-50)×0.0024 + (rank-1)×0.05` を掛けた実効値で渡す（保存値は据え置き。`src/logic/NecroGrowthSystem.ts`、`src/logic/GameManager.ts`）。
- **サーバー用逆変換** `toCharacterDataForSave(character, save)`（`src/services/PlayerSaveService.ts`）: 職業解放判定（`getJobUnlockStatus`）用の CharacterData を組み立てる。equipment は全 null 固定。

## 9. クライアント側キャッシュ（zustand persist）

`src/store/useGameStore.ts`。**真実ではなく端末キャッシュ**。

| 項目 | 値 |
|---|---|
| ストレージキー | `necro-game-store-v1`（localStorage。SSR/例外時はインメモリ Map） |
| persist version | `GAME_STORE_VERSION = 2`（サーバーの schemaVersion とは独立のカウンタ） |
| 保存対象（partialize） | player / necroStatus / party / inventoryMonsters / soulShards / inventoryItems / abyssalResidues / equippedResidueSlots / residueMaterials / weaponMaterials / transmutationPoints |
| メタ | `cacheKind: 'guest-save' \| 'server-snapshot'`（`isServerBacked` で決定）、`cachedAt`（ISO 文字列）、`offlineQueue: []`（型は `never[]` = 現状オフラインキュー未実装） |

再水和（merge）後は必ず `isServerBacked: false` に戻す。ログイン成功時は `loadFromServer(ServerGameData)` が DB スナップショットで store を上書きするため、サーバー権威が維持される。残滓スロットは `clearedStages` に `area1_node3` が無ければ空に矯正。

## 11. 認証・セッションの永続化

- **戦略**: NextAuth v5 Credentials + **JWT**（`session.strategy: 'jwt'`, maxAge = `SESSION_MAX_AGE_SECONDS = 86400`（24 時間、`src/services/SessionSecurityService.ts`））。Account / Session / VerificationToken テーブルは存在しない（P4 で DROP 済み）。
- **登録**（`createCredentialsUser`, `src/services/AuthService.ts`）: メール形式検証、パスワードは「12 文字以上」または「英数字混在 8 文字以上」、表示名 2〜16 文字。`bcrypt.hash(password, 12)`。
- **一括失効**（SEC-6）: JWT に `sessionVersion` を焼き込み、リクエスト毎に `User.sessionVersion` と照合（`validateVersionedSessionToken`）。パスワード変更時に `sessionVersion` を increment して全端末のセッションを無効化する。
- 全 Server Actions は `getAuthorizedUser()`（`auth()` の userId と引数 userId の一致）で所有者を確認してから DB に触れる。
