# 12 管理画面とAIエージェント

> 最終更新: 2026-07-11 ｜ 生成方法: コードからのリバースエンジニアリング（コードが正） ｜ 主要ソース: `src/app/admin/`（layout.tsx / adminGuard.ts / actions.ts / agents/actions.ts / 各セクション page.tsx）, `src/lib/agent/`（gemini.ts / thinkingBudget.ts / *Agent.ts / *Balance.ts / bulk/ / auditFix/ / sim/ / story/）, `src/components/admin/`, `scripts/generate-yomi-floors.mjs`, `scripts/master-data-audit.mjs`, `scripts/verify-*.mts`

本書は開発専用の管理画面（`/admin`）と、その上で動く AI エージェント群（Agent A〜E）の実装仕様を記述する。管理画面は `src/data/master/*.json` と `src/data/story/*.json` を GUI で直接編集する Next.js ルートで、`NODE_ENV=development` 以外では到達不能。AI エージェントは Gemini（LangGraph）で草稿・修正案・一括変更スペックを「生成する」だけであり、正しさの判定は LLM を一切使わない決定論的バリデータ（`*Balance.ts` ほか）と `auditMasterData()` が担い、永続化は既存 Server Action（`saveEntry` 等）のみが行う。黄泉の階層のステージ量産は管理画面ではなく CLI ジェネレータ（`scripts/generate-yomi-floors.mjs`）が担当する。

## 4. AI エージェント共通基盤

### 4.1 設計原則（コードで実際に守られている不変条件）

1. **LLM は上流のみ**: 草稿 / 修正パッチ / BulkSpec を「生成・翻訳」するだけ。数値計算・正否判定はしない。
2. **正しさは決定論ゲート**: `*Balance.ts`（純関数・LLM 不使用）+ `auditMasterData(override)` の二層。FAIL なら自動再生成（既定 `maxAttempts: 3`）。
3. **エージェントはファイルを書かない**: 永続化は既存 `saveEntry` / `saveStoryScene` のみ。preview / 生成 / 評価はすべて非破壊。
4. **破壊的操作にはスナップショット**: 一括適用・監査修正適用の前に対象ファイル全体を `src/data/master/.snapshots/` へ退避（保持 20 世代、`SNAPSHOT_KEEP = 20`）。

### 4.2 Gemini クライアント二系統（`src/lib/agent/gemini.ts`）

| 項目 | 値 |
|---|---|
| 既定モデル | `DEFAULT_GEMINI_MODEL = 'gemini-2.5-flash'` |
| バックエンド選択 | `GEMINI_BACKEND=vertex\|aistudio` を優先。未指定時は `GOOGLE_CLOUD_PROJECT` があれば vertex、なければ aistudio |
| aistudio | `generativelanguage.googleapis.com/v1beta/models`、APIキー = `GEMINI_API_KEY` または `GEMINI` |
| vertex | `{region}-aiplatform.googleapis.com/v1/projects/{project}/locations/{region}/...`、認証 = google-auth-library の ADC（scope: cloud-platform）、region 既定 `us-central1`（`GOOGLE_CLOUD_REGION`） |
| タイムアウト | `GEMINI_TIMEOUT_MS`（既定 60,000ms、`AbortSignal.timeout`） |
| リトライ | 429/500/503 を最大 3 回。429 はサーバ指定 `retryDelay` + 1s を尊重（それ以外は指数バックオフ 2^attempt 秒）。待機が 30s 超なら中断 |
| 生成既定値 | temperature 0.7 / maxOutputTokens: JSON 8192・テキスト 2048 / JSON 時 `responseMimeType: application/json` + thinkingBudget 1024 |
| JSON パース | `parseJsonLoose`: ```json フェンス除去 + 最初の `{`〜最後の `}` 抽出 |

Vertex を使う動機は「AI Studio 無料枠の日次上限回避」（GCP プロジェクト課金クォータ）。

### 4.3 thinking 予算の動的決定（`src/lib/agent/thinkingBudget.ts`）

- 要件テキストのヒューリスティック（BOSS 言及 +2、複雑キーワード各 +1、属性言及 ≥3 で +2、句読点節数など）でスコア化し、初期予算 512 / 1024 / 2048 / 4096 を決定。
- リトライごとに ×1, ×2, ×4 とエスカレーション、上限 `MAX_THINKING_BUDGET = 8192`。
- `maxOutputTokens = thinkingBudget + JSON_OUTPUT_RESERVE(4096)`（+ エージェントによっては +2048）で JSON 切れを防止。

### 4.4 LangGraph 実行形態

全エージェントは `@langchain/langgraph` の `StateGraph` で「generate → validate →（FAIL なら feedback 付き regenerate）」ループを構成。グラフはモジュールスコープでシングルトンキャッシュ。リトライ時は temperature を下げる（例: enemyAgent 0.7 → 0.4、auditFixAgent 0.5 → 0.3、bulkAgent 0.4 → 0.3）。

LangGraph は ESM-only 依存のため Jest ではフルグラフを実行できず、ライブ検証は `scripts/verify-*-agent.mts`（`npm run agent:verify` 系、実 Gemini API 使用・`.env` を手動ロード）が担う。決定論バリデータ単体は Jest（`src/lib/agent/*.test.ts`）で網羅。

## 6. Agent B: 監査修正（`auditFixAgent.ts` + `auditFix/`）

- 入口: `/admin/audit` の各 FAIL 行 → `AuditFixModal` → `fixAuditFindingAction(scope, entityId)`。
- フロー: 対象エンティティの FAIL 一覧 + 現 JSON + 参照可能 ID ヒント（`scopeRegistry.referenceHint`）をプロンプトに渡し、「指摘違反のみを最小変更で修正」させる。id の変更は禁止。
- **二層ゲート**（`validateNode`）:
  1. per-content バリデータ — `auditFix/scopeRegistry.ts` が scope → バリデータ + コンテキスト構築（対象 id は重複チェックから自己除外）をレジストリ化。Agent A の 9 バリデータを再利用。
  2. in-memory 監査 — `auditMasterData({ [scope]: { [id]: patched } })` を実行し、(a) 対象 FAIL が解消したか (b) **baseline に無かった新規 FAIL を生んでいないか**（`baselineFailKeys` 比較）を判定。
- 結果は `deepDiff`（`auditFix/diff.ts`）のフィールド差分付きで UI に提示 → ユーザー承認後 `applyAuditFixAction` が**スナップショット作成 → `saveEntry`**。スナップショット作成に失敗した場合は保存自体を中止する。
- `getAuditFailGroupsAction()`（FAIL の scope/id 別グルーピング）は Server Action として存在するが、**一括修正バッチ UI は未実装**（後述）。

## 7. Agent C: ストーリーシーン生成（`storyAgent.ts` + `story/`）

- 原則: **構造は決定論ゲート、物語の質は多案生成 → 人間選択**。LLM に良し悪しを判定させない。
- 2 モード: `new`（骨子 + 指示 → lines 含む全体）/ `complete`（既存シーンの骨子を維持し lines のみ生成）。Action は `generateStorySceneAction` / `completeSceneLinesAction`。
- 候補数既定 3、temperature 0.85（多様性重視）。各候補を `storyValidator.validateStoryScene` で構造検証し、**FAIL 0 の候補のみ**返す。全滅時のみ再生成（最大 3 回）し、`rejectionReasons` で除外理由を UI 表示。
- 構造ゲートの検査: id（UPPER_SNAKE 推奨 WARN・重複 FAIL）、type ∈ {DIALOGUE, MONOLOGUE, ENVIRONMENT, CHAPTER_TITLE, CHOICE}、trigger.type ∈ {GAME_START, FLAG_SET, STAGE_CLEAR, STAGE_ENTER, AREA_UNLOCK, BOSS_CLEAR, DEMONIZE_FIRST, MANUAL} + variant 別必須参照（stageId/bossStageId/areaId/flagKey/sceneId）、speaker は null か characters.json のキー、expression は speaker の `expressions[]` 内、portraits.position ∈ {LEFT, CENTER, RIGHT}、`onComplete.unlockArea/navigateTo` 参照、textEn 欠落は WARN（`story/storyValidator.ts`）。
- 口調・世界観は `story/storyContext.ts` の**キャラバイブル**（characters.json + 既存シーンの実台詞を各キャラ最大 3 例抽出）+ 固有名詞グロッサリ + 挿入位置前後のシーン流れで担保。
- 保存はユーザーが候補を選んだ後、既存 `saveStoryScene` で行う。

## 8. Agent D: 一括変更（`bulkAgent.ts` + `bulk/`）

- 入口: `/admin/agents/batch`（BulkChangePanel）。
- **LLM の仕事は「自然言語 → BulkSpec への翻訳」だけ**。値の適用計算はしない（プロンプトで「係数だけ書く」ことを強制）。
- `BulkSpec`（`bulk/bulkSpec.ts`）:
  - `file`: enemies / skills / stages / jobs / items / materials / monsters / demonForms / areas の 1 つ
  - `filter[]`: `{ field(ドット記法), op: == != < <= > >= in exists, value }`（AND 結合。空 filter は全件 WARN）
  - `operation[]`: `{ field, op: set add mul clampMin clampMax, value }`（add/mul/clamp は数値必須、mul 1 は WARN）
  - LLM 出力は `validateBulkSpec` で機械検証し、不正なら再生成。
- `previewBulkChangeAction(instruction)` — **非破壊**:
  1. `applyBulkSpec`（`bulk/bulkEngine.ts`、純関数・入力不変・clone 適用）で `{ id, before, after, diff }` を算出。数値は元値が整数なら四捨五入、小数なら 6 桁丸め（`coerceNumber`）。
  2. 層1: 各変更を scopeRegistry の per-content バリデータで検証。
  3. 層2: `auditMasterData({ [file]: patched })` で**新規 FAIL** を検出（baseline 比較）。
  4. `auditMutationFields` で「一致エンティティのどれにも存在しない operation フィールド」（typo / LLM 幻覚）を `missingFields` として警告（set は新規追加意図がありうるため対象外）。
  5. `ok = per-content 全 PASS && 新規監査 FAIL 0` のときのみ適用ボタンが有効。
- `applyBulkChangeAction(spec)` — 適用前に `writeSnapshot`（`bulk/snapshot.ts`、`{file}__{timestamp}-{連番}.json` 形式）→ `applyChangesWithWriter`（`bulk/applyEngine.ts`、注入式保存ループ）で `saveEntry` を 1 件ずつ実行 → 適用後に全体監査の FAIL/WARN 件数を返す。
- undo: `listBulkSnapshotsAction` / `restoreBulkSnapshotAction(snapshotId)` — スナップショットの `data` を対象マスターファイルへ完全書き戻し。

## 9. Agent E: シミュレータ連携バランス評価（`simEvalAgent.ts` + `sim/`）

- **ダメージ計算は LLM がしない**。実バトルと同一の `calculateBattleDamage`（`src/logic/BattleDamage.ts`）を全対象にループ実行して `SimulationReport` を決定論的に構築し、LLM は「レポートを読んで解釈」するだけ（temperature 0.4 / thinkingBudget 1024）。
- レポート指標（`sim/simulationReport.ts`）: 対象別の 期待ダメージ（会心率加重）/ 1確判定 / 撃破発数 / 弱点・耐性判定、要約の energyEfficiency（平均期待 ÷ mpCost）/ oneShotRate / avgHitsToKill / weaknessCoverage。AoE（ALL_ENEMIES）は **想定 3 体同時ヒット**（`AOE_ASSUMED_TARGETS = 3`）の合算効率を別枠で持つ。
- 評定出力: `verdict ∈ {BALANCED, TOO_STRONG, TOO_WEAK}` + `recommendations[]`（target は `skill.power` / `skill.mpCost` / `enemy.hp` / `enemy.def` の 4 種のみ。coerce で不正 target は捨てる）。
- 推奨値は `sim/recommendationCheck.ts` が設計帯（skill は POWER_TABLE、enemy は実データ tier 帯 ±30%）と照合し、帯外に警告を付す。
- 3 つの入口:

| Action | 対象 | 既定レベル |
|---|---|---|
| `evaluateBalanceAction(jobId, skillId, level, enemyIds?)` | 保存済みスキル ×（指定 or 全）敵 | 引数指定（1〜100 clamp） |
| `evaluateSkillDraftAction(draft, jobId, level)` | 未保存スキル草案 × 全敵（E-5） | 60 |
| `evaluateEnemyDraftAction(draft, level)` | 未保存エネミー草案（R-7）。攻撃側 = 全職業ステータス中央値の代表アタッカー、スキル = 4 分類（PHYS/MAGIC × SINGLE/AOE）ごとの power 中央値スキルを決定論選抜。推奨 target は enemy.hp/def のみ | 10（第1章想定） |

- プロンプトの設計帯ヒント: 単体スキルは 1 EN あたり 20〜35、AoE 合算は 36〜63（単体の約 1.8 倍）。敵評定の目安は MINION 1〜2 発 / ELITE 3〜5 発 / BOSS 6 発以上（`agents/actions.ts` の `simDesignContext` / `simEvalAgent.ts`）。

## 10. 決定論的検証ゲート（`src/lib/agent/*Balance.ts`）の要点定数

全バリデータは LLM 不使用の純関数で、`{ ok: FAIL 0 件, findings: {level, field, message}[] }` を返す。共通で `knownFields.ts` の**未知トップレベルフィールド検出**（既知集合外のキーを WARN、`__` プレフィックスは無視）が配線されている。

### enemyBalance.ts
- tier/tribe/属性の列挙は `src/types/game.ts` と同期（MINION/ELITE/BOSS、6 種族、8+NONE 属性）。
- **tier 帯は設計書ではなく既存 enemies.json から動的学習**（`deriveTierBands`、対象 hp/atk/def/spd、許容 `BAND_TOLERANCE = 0.3` で min×0.7〜max×1.3 外は WARN）。
- スケール検閲: critDmg が 0 < x < 100 は FAIL（%表記、既存 150〜175）。critRate/effectHit/effectRes の 0 < x < 1 は WARN。resistances の 0 < |x| < 1 は WARN。
- necromance tier 規約（`NECROMANCE_TIER_CONVENTION`、doc97 と同期）:

| tier | captureRate | allyCost | skillIds 数 |
|---|---|---|---|
| MINION | 0.12 | 1 | 1〜2 |
| ELITE | 0.04 | 2 | 1〜3 |
| BOSS | 0.001 | 4 | 2〜4 |

- captureRate 上限は necroConfig の `captureRate.cap`（注入、既定 0.75）。R10 実効 = captureRate × rankMultiplier^9（既定 1.10^9）が cap 到達なら WARN。
- gimmicks: trigger ∈ {HP_BELOW_50, TURN_3, ON_SHIELD_BREAK, ON_REVIVE} / effect ∈ {ENRAGE, AV_DELAY, REVIVE, SUMMON_MINIONS}。REVIVE は HP_BELOW_50 以外だと WARN、ON_SHIELD_BREAK はシールド未設定で WARN、MINION へのギミックは WARN。
- 味方スキルの素性整合: 草稿の弱点属性と同属性のスキルは WARN。

### skillBalance.ts — power 表（設計書19 §2.2 を「数値の憲法」として実装）

| 分類 | cost帯 | Tier1 power | Tier2 power |
|---|---|---|---|
| PHYS_SINGLE | 4〜8 | 1.2〜1.55 | 1.4〜1.8 |
| | 9〜14 | 1.45〜1.8 | 1.65〜2.1 |
| | 15〜 | 1.7〜2.1 | 1.9〜2.4 |
| PHYS_AOE | 4〜8 | 0.9〜1.3 | 1.1〜1.5 |
| | 9〜14 | 1.25〜1.65 | 1.45〜1.9 |
| | 15〜 | 1.5〜1.9 | 1.7〜2.15 |
| MAGIC_SINGLE | 8〜12 | 1.4〜1.7 | 1.55〜1.9 |
| | 13〜18 | 1.6〜2.0 | 1.8〜2.25 |
| | 19〜 | 1.9〜2.3 | 2.1〜2.5 |
| MAGIC_AOE | 8〜12 | 1.1〜1.45 | 1.25〜1.6 |
| | 13〜18 | 1.3〜1.7 | 1.5〜1.95 |
| | 19〜 | 1.55〜2.0 | 1.75〜2.2 |

帯外 power は FAIL。power の絶対レンジ 0.5〜5 外も FAIL。owner-fit: スキル type ≠ 職業 category は FAIL、attackType ≠ baseAttackType は WARN。effectKey 規約は `{element}_{attackType}` 小文字（外れは WARN）。

### demonBalance.ts
- 魔神技 power 帯 `DEMON_ULT_POWER_RANGE`: Tier1 = 2.8〜3.6 / Tier2 = 3.6〜4.8。
- Tier1 はリスク（riskType）なし、Tier2 は riskType（SELF_DAMAGE/ENERGY_DRAIN/GLASS_CANNON/SETUP_DEPENDENT）+ lingering（FIELD/PARTY_BUFF/ENEMY_DEBUFF）必須（設計書16 のルール実装）。
- statBoosts は倍率表記: 2.5 超 WARN、5 超 FAIL（スケール誤り検出）。

### stageBalance.ts
- nodeType ∈ {SAFE, DUNGEON, BOSS}、wave role ∈ {WARMUP, SHIELD, ELITE, BOSS}、areaGimmick ∈ {SLIP_DAMAGE, STATUS_AILMENT, NONE}、drop type ∈ {WEAPON, RESIDUE, MATERIAL, MONSTER, CONSUMABLE}。
- `waves[].statScale` は hp/atk/def のみ・正の有限数、**3 倍超は WARN**（黄泉用途は許容）。
- waveCount と waves.length の不一致は FAIL。BOSS ノードに BOSS tier 敵不在は WARN。baseExp は既存レンジの min×0.3〜max×3 外で WARN（実データ学習 `deriveRewardBands`）。

### weaponBalance.ts / materialBalance.ts / jobBalance.ts / areaBalance.ts / monsterBalance.ts
- 武器: rarity ∈ {R, SR, SSR, UR}、`RARITY_SUBOPTION_SLOTS` = 通常枠は全レア 1 / 属性枠は R,SR = 0・SSR,UR = 1（設計書92 §2.1）。パッシブ 2 スロット（passiveA/B）必須、values は 5 要素（ランクⅠ〜Ⅴ）標準、systemTag ∈ {DEMON_MODE, SOUL_SHATTER, ACTION_VALUE, SHIELD_PIERCE, GIANT_KILLING}。
- 素材: rarity ∈ {COMMON, RARE, EPIC, LEGENDARY}。expValue 帯は実データ学習、無ければフォールバック帯 COMMON 80〜250 / RARE 400〜1000 / EPIC 1200〜3000 / LEGENDARY 3500〜8000。
- 職業: tier ∈ {1, 2}、category ∈ {PHYSICAL, MAGICAL}、category↔baseAttackType の妥当組合せ（PHYSICAL: SLASH/STRIKE、MAGICAL: MAGIC/PROJECTILE/SUMMON）。statModifiers 倍率はソフト帯 0.6〜1.6 外 WARN / ハード帯 0.1〜3 外 FAIL。baseStatsByLevel は草稿では任意（フォーム側が補間生成）。
- エリア: id は `ch{chapter}_area{area}` 規約に不一致で FAIL。sortOrder 推奨値 = chapter×100 + area。
- 味方魔物: cost 別 stat 帯を monsters.json から学習（敵とは別スケール）、許容 `BAND_TOLERANCE = 0.35`。

## 11. 黄泉の階層ジェネレータ（`scripts/generate-yomi-floors.mjs`）

`npm run data:generate-yomi`。管理画面ではなく CLI。**既に実行済み**で、`stages.json` に `yomi_b01`〜`yomi_b20` の 20 階層、`areas.json` に `ch1_area99` が登録されている（2026-07 時点の実データで確認）。

| フラグ | 挙動 |
|---|---|
| （なし） | dry-run: 生成 JSON + 実効ステータスサンプルを stdout 表示。**書き込まない** |
| `--write` | stages.json へ atomic write。既存 `yomi_bNN` があると拒否 |
| `--write --force` | 既存 yomi ステージを再生成値で上書き |
| `--floors=5-10` / `--floors=1,3,5` | 対象階層の指定（既定 1〜20） |
| `--json` | 機械可読 JSON 出力 |

生成規則（コード転記）:

- **スケーリング係数**（`computeStatScale`、B1 は省略）: `hp: 1.09^(n-1)`, `atk: 1.07^(n-1)`, `def: 1.045^(n-1)`（各 4 桁丸め）。全 WAVE の `statScale` に付与。
- **階タイプ**（`floorType`）: `n % 10 == 0` → BOSS、`n % 5 == 0` → ELITE、それ以外 NORMAL。いずれも 3 WAVE 構成（NORMAL: WARMUP→SHIELD→ELITE / ELITE 階: WARMUP→SHIELD→ELITE(bone_colossus 単体) / BOSS 階: WARMUP→ELITE→BOSS）。
- **敵プール**: MINION 7 種（grave_soldier, rot_hound, hollow_handmaid, earthbound_grudge, bloodmire_leech, wandering_guard_wraith, dragonbone_spawn）を階番号で巡回配置、SHIELD 枠 = {abyss_warden, bone_colossus, cursed_head_maid}、ELITE クローザー = {abyss_warden, grave_knight, bone_colossus, cursed_head_maid}、ボスは `ossuary_wyrm_lord` 固定。
- **報酬**（`buildRewardsForFloor`）: `baseExp: 0` / `baseGold: 0` / `dropTable: []` 固定（黄泉規約）。`firstClearGuaranteed` に素材（B1〜4: bone_chip、B5〜9: grave_crystal、B10〜: ossuary_memory。数量 = 節目 2、それ以外 `1 + floor(n/7)`）。節目階（5/10/15/20）は追加で WEAPON_MATERIAL（B5: IDEA_SR、B15: IDEA_SSR、B20: ABYSSAL_OBSIDIAN）+ RESIDUE（B5: RARE、B15: EPIC、B20: LEGENDARY）。
- **ステージメタ**: `chapter: 1` / `area: 99` / `nodeType: 'DUNGEON'` / `element: 'DARK'` / `difficulty: n` / `sortOrder: 9000 + n` / `position: { x: 900000 + n×100, y: 900000 }`。解放チェーン: B1 は `area1_node3`（`CH1_FINAL_NODE_ID`）、以降は直前階。
- **セルフチェック**（失敗時 exit 1）: id パターン `^yomi_b\d{2,}$`、`CH1_FINAL_NODE_ID` が `src/logic/YomiFloors.ts` の export と一致すること、chapter/area = 1/99、報酬ゼロ規約、SHIELD WAVE に shieldHp 持ち敵の存在、BOSS WAVE に BOSS tier 敵の存在、解放チェーンの連結。

既存バランスツール（balance-report / progression-report / /admin/simulator / Agent E の `buildSimTargets`）は `wave.statScale` を無視して enemies.json の生値のみを参照するため、黄泉の実効ステータス確認は本スクリプトの dry-run 出力（`effectiveStatsForStage`: `Math.floor(base × factor)` キー毎独立切り捨て）が唯一の手段。

## 12. 運用手順の要点

1. **起動**: `npm run dev`（Next.js。`npm run dev:ui`=Vite では admin 不可）→ `http://localhost:3000/admin`。
2. **Gemini 設定**: `.env` に `GEMINI_API_KEY`（AI Studio）。クォータ回避には `GEMINI_BACKEND=vertex` + `GOOGLE_CLOUD_PROJECT`（+ `gcloud auth application-default login`）。
3. **コンテンツ追加の標準フロー**: 各フォームの AI 草案パネルに要件入力 → 草稿がフォームへ流し込まれる → （スキル/敵は「バランス評価」で Agent E 評定）→ 保存 → `/admin/audit` で FAIL=0 を目視確認。
4. **監査 FAIL の修正**: `/admin/audit` → FAIL 行の修正ボタン → Agent B の diff を確認 → 適用（自動スナップショット付き）。
5. **一括変更**: `/admin/agents/batch` → 自然言語指示 → diff / 検証サマリ確認 → `ok` のときのみ適用 → 問題があれば「元に戻す」（スナップショット復元）。
6. **エージェントのライブ動作確認**: `npm run agent:verify`（enemy）ほか `agent:verify-{skill,demon,stage,weapon,material,job,area,monster,audit-fix,sim-eval,enemy-eval,story,bulk,bulk-apply}`。実 API を叩き、失敗時 exit 1。マスターデータ非破壊（CI の `git diff --exit-code src/data/master` でも担保）。
7. **CI の監査は非 strict**: `npm run data:audit` は FAIL があっても exit 0（`--strict` 時のみ exit 2）。リリース判定は `/admin/audit` の人間確認が必須。
8. **スナップショット**: `src/data/master/.snapshots/`（gitignore 対象外かは未確認）。file 毎に最新 20 世代保持。
