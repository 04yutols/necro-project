## 2. Jest ユニットテスト

### 2.1 設定（`jest.config.js`）

```js
module.exports = {
  preset: 'ts-jest',
  testEnvironment: 'node',
  testMatch: ['**/*.test.ts'],
  setupFiles: ['<rootDir>/jest.setup.js'],
  moduleNameMapper: { '^@/(.*)$': '<rootDir>/src/$1' },
  forceExit: true,
};
```

- `forceExit: true` — Neon の WebSocket 接続などが残ってもプロセスを強制終了する。実行すると常に `A worker process has failed to exit gracefully...` の警告が出るが、これは既知・無害（テスト結果には影響しない）

## 3. 「ユニット＝DB不要」レイヤ分離の乖離（解消済み、2026-07-13）

旧設計書・CI コメント（`.github/workflows/ci.yml` の「`src/tests/` の統合テストは実 DB が必要なため CI では除外」）はいずれも、**DBが必要なテストは `src/tests/` にのみ存在する**ことを前提にしていたが、かつては `grep -rl "lib/prisma"` の棚卸しで `src/tests/` の外にも実 DB（`prisma`）へ直接アクセスするテストファイルが3件見つかっていた（`src/logic/GameManager.test.ts`、`src/services/AuthService.test.ts`、`src/services/SessionSecurityService.test.ts`）。`DATABASE_URL` を一時退避してCIと同一コマンドを再現したところ、この3ファイルのみが `No database host or connection string was set` で失敗し、他は無傷だった。`.github/workflows/ci.yml` に `secrets.DATABASE_URL` 相当の注入は存在しないため、この3ファイルは `testPathIgnorePatterns="<rootDir>/src/tests/"` の対象漏れであり、CIの「Unit tests」ステップを壊しうる状態だった。

**対応（2026-07-13）**: 上記3ファイルを `src/tests/` 配下へ移動し、統合テストの命名規則（`*.integration.test.ts`）に揃えた:

| 旧配置 | 新配置 |
|---|---|
| `src/logic/GameManager.test.ts` | `src/tests/game-manager.integration.test.ts` |
| `src/services/AuthService.test.ts` | `src/tests/auth-service.integration.test.ts` |
| `src/services/SessionSecurityService.test.ts` | `src/tests/session-security.integration.test.ts` |

これにより「`src/tests/` = DB必須」「それ以外 = DB不要」の境界がディレクトリ構成と完全一致するようになり、`testPathIgnorePatterns="<rootDir>/src/tests/"` は実装上も過不足なくDB依存テストを除外する。移動に伴い `tsconfig.tests.json`（`tests/**/*` 型チェック専用、`npm run ts:e2e`）と `package.json` の `ts:e2e` スクリプトを追加した（詳細は §5.5）。移動後の再検証: `npx jest --ci --testPathIgnorePatterns="<rootDir>/src/tests/"` は85 suites全パス、`npx jest src/tests --ci` は7 suites（移動3ファイル含む）全パス（§2.3）。

### 5.3 E2Eの実行方式（`tests/helpers/e2e.ts`）

E2E は実DBを必要としない。`prepareE2EPage()` が以下を行う:

1. `page.route('**/api/auth/session', ...)` / `page.route('**/api/auth/**', ...)` で認証APIをインターセプトし、ゲストモードを強制（DB接続を発生させない）
2. `page.addInitScript()` で `localStorage` に既読ストーリーシーン（`necro-story-store-v2`）・完了チュートリアルフェーズ（`necro-tutorial-store-v2`）を事前投入し、初回チュートリアル/ストーリー演出をスキップ
3. `sessionStorage` に `necro-e2e-cleared-stages` / `necro-e2e-battle-boost=1` をセットし、クリア済みステージとバトル高速化（テスト用ブースト）を注入
4. `/` へ遷移し「拠点」表示を待機、スキップボタンが存在しないことを確認

`prepareE2EPage(page, { preset })` に `PresetName` を渡すと、上記1の前に進行プリセットの persist スナップショットを `localStorage('necro-game-store-v1')` へ注入する（後段の `removeItem` はスキップされる）。詳細は §5.5。

このため `baseURL: http://localhost:3080` は Next.js フルサーバ（`docker compose` の `app` サービス）でも Vite（`npm run dev:ui`、ポート3000）でも動作しうる。`new-player-onboarding.spec.ts` は docstring で明示的に「Vite/ゲストモードで実行（Next.js DB不要）」と注記している。

### 5.5 テストデータ基盤（`src/testing/`）

#### 5.5.3 E2E注入 — `seedGameState` / `prepareE2EPage` の `preset` オプション

`tests/helpers/e2e.ts` の `seedGameState(page, preset)` が `buildPresetSnapshot()` のスナップショットを `page.addInitScript()` で `localStorage('necro-game-store-v1')` へ書き込む（`fresh` は `removeItem` と同義）。`prepareE2EPage(page, { preset })` に `preset` を渡すとgoto前に自動的に呼ばれ、既存の無条件 `removeItem` はスキップされる。`preset` 未指定時は完全に従来どおりの動作（新規プレイヤー状態）。

```ts
// tests/some.spec.ts
await prepareE2EPage(page, { preset: 'ch1_cleared' });
```

#### 5.5.4 実機devシード — `?devPreset=<name>`（dev限定）

`src/hooks/useDevPreset.ts` の `useDevPresetInjection(authStatus)` を `src/app/page.tsx` の `GameContent`（`useAuthFlow()` 直後）に配線。`process.env.NODE_ENV !== 'production'` ガード内で動作し、本番ビルドではこの効果全体（`src/testing/presets` の dynamic import 含む）が除去される。

使い方: ブラウザで `http://localhost:3080/?devPreset=ch1_cleared` のように開くと、

1. URLの `devPreset` パラメータを検出
2. 認証解決前（`checking` / `loadingCharacter`）は待機
3. ログイン中（`guest` 以外）なら警告して無視（サーバーバックアカウントを上書きしない）
4. `dynamic import('../testing/presets')` → `buildPresetSnapshot()` の結果を `necro-game-store-v1` へ書き込み、`necro-story-store-v2` / `necro-tutorial-store-v2` にもストーリー/チュートリアルのスキップスナップショットを書き込む
5. URLパラメータを除去して `location.reload()`

不正なプリセット名は `console.warn` のみで無視する。ゲストモード専用。

## 8. マスターデータ非破壊規約

`CLAUDE.md` および `README.md` に明記された規約: **テストは `src/data/master/*.json`（10ファイル: `areas`, `demonForms`, `enemies`, `items`, `jobs`, `materials`, `monsters`, `necroConfig`, `skills`, `stages`）を変異させてはならない**。

- 強制方法: CI §6-7 の `git diff --exit-code --stat src/data/master`。ユニットテスト実行後にマスターデータJSONに差分があればビルド失敗
- `src/data/*.test.ts`（`stageRefs.test.ts`, `ch1Phase2NewEnemies.test.ts` 等）はマスターJSONを `import` して**読み取り専用**の整合性検証のみ行う（コード参照ステージIDの存在確認、新規エネミー/ステージのバランス検証）
- `src/lib/agent/*.test.ts` の決定論バリデータ群も同様に読み取り専用（実際にマスターデータを書き換えるのは `/admin` の Server Actions のみで、Jest からは呼ばれない）
