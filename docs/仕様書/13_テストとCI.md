## 2. Jest ユニットテスト

### 2.1 設定（`jest.config.js`）

```js
module.exports = {
  preset: 'ts-jest',
  testEnvironment: 'node',
  testMatch: ['**/*.test.ts'],
  setupFiles: ['<rootDir>/jest.setup.js'],
```

## 3. 重要事項: 「ユニット＝DB不要」レイヤ分離の実態と乖離

旧設計書・CI コメント（`.github/workflows/ci.yml` の「`src/tests/` の統合テストは実 DB が必要なため CI では除外」）はいずれも、**DBが必要なテストは `src/tests/` にのみ存在する**ことを前提にしている。しかし実装を `grep -rl "lib/prisma"` で棚卸しした結果、`src/tests/` の外にも実 DB（`prisma`）へ直接アクセスするテストファイルが 3 件存在する:

| ファイル | 配置 | DBアクセス |
|---|---|---|
| `src/logic/GameManager.test.ts` | `src/logic/`（ユニット扱い） | `prisma.character` / `prisma.monster` 等への実クエリ（`afterAll` の `cleanupUser` 含む） |
| `src/services/AuthService.test.ts` | `src/services/`（ユニット扱い） | `prisma.user.create` / `findUniqueOrThrow` 等 |
| `src/services/SessionSecurityService.test.ts` | `src/services/`（ユニット扱い） | `prisma.user.create` / `deleteMany` |

**検証方法と結果**: `.env` / `.env.local`（`DATABASE_URL` を含む）を一時的に退避し、CI のユニットテストコマンドと同一のコマンド（`npx jest --ci --testPathIgnorePatterns="<rootDir>/src/tests/"`）をローカルで再現したところ、以下の通り上記3ファイルのみが失敗した（他 84 ファイル・790 テストは影響なし）:

```
Test Suites: 3 failed, 84 passed, 87 total
Tests:       7 failed, 790 passed, 797 total
```

失敗理由は Prisma Neon アダプタの接続エラー（`No database host or connection string was set`）であり、`.github/workflows/ci.yml` には `secrets.DATABASE_URL` 相当の環境変数注入が存在しない（`grep -rn "DATABASE_URL|secrets\." .github/workflows/` でヒットなし）。

**結論**: `.github/workflows/ci.yml` の「Unit tests」ステップは、リポジトリ設定上 `DATABASE_URL` を supply する仕組みが一切ない前提では、この3ファイルで失敗するはずである。GitHub 側のリポジトリ/Organization シークレットで暗黙に `DATABASE_URL` が注入されている可能性は本書の権限では確認できない（`gh` CLI 未認証のため実際の Actions 実行ログは未確認）ため、**「未確認」**として扱うが、ワークフロー定義だけを見る限りこの3ファイルは `src/tests/` と同様に実DBを要求する統合テストであり、`testPathIgnorePatterns` の対象漏れである可能性が高い。第2章以降の技術的負債候補として §「先送り・未実装」に記載する。

### 5.3 E2Eの実行方式（`tests/helpers/e2e.ts`）

E2E は実DBを必要としない。`prepareE2EPage()` が以下を行う:

1. `page.route('**/api/auth/session', ...)` / `page.route('**/api/auth/**', ...)` で認証APIをインターセプトし、ゲストモードを強制（DB接続を発生させない）
2. `page.addInitScript()` で `localStorage` に既読ストーリーシーン（`necro-story-store-v2`）・完了チュートリアルフェーズ（`necro-tutorial-store-v2`）を事前投入し、初回チュートリアル/ストーリー演出をスキップ
3. `sessionStorage` に `necro-e2e-cleared-stages` / `necro-e2e-battle-boost=1` をセットし、クリア済みステージとバトル高速化（テスト用ブースト）を注入
4. `/` へ遷移し「拠点」表示を待機、スキップボタンが存在しないことを確認

このため `baseURL: http://localhost:3080` は Next.js フルサーバ（`docker compose` の `app` サービス）でも Vite（`npm run dev:ui`、ポート3000）でも動作しうる。`new-player-onboarding.spec.ts` は docstring で明示的に「Vite/ゲストモードで実行（Next.js DB不要）」と注記している。

### 5.4 docker-compose の `playwright` サービス

`docker-compose.yml` に E2E 専用サービスが定義されている:

```yaml
playwright:
  image: mcr.microsoft.com/playwright:v1.59.0-jammy
  environment:
    - PLAYWRIGHT_TEST_BASE_URL=http://app:3000
  depends_on: [app]
  entrypoint: /bin/sh -c "npm install && npx playwright test"
```

`app` サービスは `db`（Postgres 16）に依存する Next.js フルサーバ。ただし E2E 自体は §5.3 の通り DB を使わないモックで完結するため、この構成は「フルスタック環境での動作確認」の位置づけ。

## 8. マスターデータ非破壊規約

`CLAUDE.md` および `README.md` に明記された規約: **テストは `src/data/master/*.json`（10ファイル: `areas`, `demonForms`, `enemies`, `items`, `jobs`, `materials`, `monsters`, `necroConfig`, `skills`, `stages`）を変異させてはならない**。

- 強制方法: CI §6-7 の `git diff --exit-code --stat src/data/master`。ユニットテスト実行後にマスターデータJSONに差分があればビルド失敗
- `src/data/*.test.ts`（`stageRefs.test.ts`, `ch1Phase2NewEnemies.test.ts` 等）はマスターJSONを `import` して**読み取り専用**の整合性検証のみ行う（コード参照ステージIDの存在確認、新規エネミー/ステージのバランス検証）
- `src/lib/agent/*.test.ts` の決定論バリデータ群も同様に読み取り専用（実際にマスターデータを書き換えるのは `/admin` の Server Actions のみで、Jest からは呼ばれない）
