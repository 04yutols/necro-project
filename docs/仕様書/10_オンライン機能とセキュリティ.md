# 10 — オンライン機能とセキュリティ

> 最終更新: 2026-07-11 ｜ 生成方法: コードからのリバースエンジニアリング（コードが正） ｜ 主要ソース: `src/auth.ts`, `src/app/actions.ts`, `src/app/api/auth/*`, `src/app/api/ranking/route.ts`, `src/app/api/world-log/route.ts`, `src/services/AuthService.ts`, `src/services/SessionSecurityService.ts`, `src/services/RateLimitService.ts`, `src/services/RankingService.ts`, `src/services/WorldEventService.ts`, `src/hooks/useAuthFlow.ts`, `src/hooks/useWorldLog.ts`, `prisma/schema.prisma`

本書は Necromance Brave のオンライン機能（認証・クラウドセーブ入口・ランキング・世界ログ・第一発見者）とセキュリティ対策（Server Actions の認可、ステージ開始証跡、レート制限、JWT 失効）の**現行実装仕様**を記述する。認証は NextAuth v5 の Credentials プロバイダ + JWT 戦略のみで、OAuth は未実装。サーバー側の信頼境界は常に `auth()` が返す `session.user.id` であり、クライアントから渡る ID（characterId / monsterId / itemId 等）は所有権の証明として扱わない。

## 1. 全体アーキテクチャ

| 構成要素 | 実装 | 保存先 / 通信先 |
|---|---|---|
| 認証 | NextAuth v5（beta.31）Credentials + JWT | httpOnly Cookie（`src/auth.ts`） |
| ログインAPI | 手製 Route Handler（`next-auth/jwt` の `encode()` を直接使用） | `src/app/api/auth/login/route.ts` |
| セッション失効 | `User.sessionVersion` 照合 | PostgreSQL（`src/services/SessionSecurityService.ts`） |
| レート制限 | スライディングウィンドウ（Upstash Redis REST / メモリfallback） | `src/services/RateLimitService.ts` |
| ランキング | Prisma クエリ + Upstash Redis JSON キャッシュ（TTL 300秒） | `src/services/RankingService.ts` |
| 世界ログ | Prisma `WorldLog` 永続化 + Pusher Channels REST 配信 | `src/services/WorldEventService.ts` |
| ステージ開始証跡 | Prisma `StageAttempt`（短命・単回消費） | `src/app/actions.ts` |
| 管理画面保護 | development 限定（middleware + assertDev） | `src/middleware.ts`, `src/app/admin/adminGuard.ts` |

**SDK 非依存**: `package.json` に `pusher` / `pusher-js` / `@upstash/redis` / `@upstash/ratelimit` は存在しない。Upstash は REST API を素の `fetch` で、Pusher はサーバー側が REST + HMAC-SHA256 署名、クライアント側が素の `WebSocket` で直接叩く。認証関連の外部依存は `next-auth@^5.0.0-beta.31` と `bcryptjs@^3.0.3` のみ。

## 2. 認証システム

### 2.1 NextAuth v5 構成（`src/auth.ts`）

- プロバイダ: **Credentials のみ**（email / password）。`authorize()` は `prisma.user.findUnique({ where: { email } })` → `bcrypt.compare` で照合し、成功時に `{ id, name, email, sessionVersion }` を返す。
- セッション戦略: `{ strategy: 'jwt', maxAge: SESSION_MAX_AGE_SECONDS }`。`SESSION_MAX_AGE_SECONDS = 60 * 60 * 24`（24時間、`src/services/SessionSecurityService.ts`）。
- `trustHost: true`。
- `jwt` callback:
  - ログイン直後（`user.id` あり）: `user.sessionVersion`（なければ DB から `getUserSessionVersion()`）をトークンに埋め込む。取得不能なら `null` を返しセッション不成立。
  - 以降のセッション確認: `validateVersionedSessionToken(token)` で DB の現行 `sessionVersion` と照合。不一致・欠落は `null` → Cookie 破棄・未認証扱い。
- `session` callback: `session.user.id` と `session.user.sessionVersion` を公開（型拡張は `src/types/next-auth.d.ts`）。
- NextAuth Route Handler は `src/app/api/auth/[...nextauth]/route.ts`（`handlers` の GET/POST を re-export。`/api/auth/session` の確認などに使用）。

### 2.2 新規登録 — `POST /api/auth/signup`（`src/app/api/auth/signup/route.ts`）

処理順: レート制限チェック（scope `signup`）→ `createCredentialsUser()`（`src/services/AuthService.ts`）。

| 検証 | 内容 | エラーメッセージ |
|---|---|---|
| 必須入力 | email / password / displayName すべて必須 | 全ての項目を入力してください |
| email 形式 | `/^[^\s@]+@[^\s@]+\.[^\s@]+$/`（trim + 小文字化後） | メールアドレスの形式を確認してください |
| パスワードポリシー（SEC-7） | **12文字以上** または **英字と数字を含む8文字以上**（`/^(?=.*[a-zA-Z])(?=.*\d).{8,}$/`） | パスワードは12文字以上、または英数字を含む8文字以上にしてください |
| displayName | 2〜16文字（trim後） | プレイヤー名は2〜16文字にしてください |
| email 重複 | `prisma.user.findUnique` | このメールアドレスは既に登録されています |

- パスワードは `bcrypt.hash(password, 12)`（コスト12）で保存。`User.name` にも displayName を複製。
- レスポンス: 成功 200 `{ success: true }` / 検証失敗 400 / レート制限 429（`Retry-After` ヘッダ付き）。
- Server Action 経由の登録 `signUpAction(email, password, displayName)` も存在する（`src/app/actions.ts`）。こちらは同じ `createCredentialsUser()` を呼ぶが**レート制限を通らない**。

### 2.3 ログイン — `POST /api/auth/login`（手製、`src/app/api/auth/login/route.ts`）

NextAuth の signin エンドポイントではなく、専用 Route Handler が JWT を直接発行する。

1. email（trim + 小文字化）/ password の入力確認（欠落は 400）。
2. レート制限チェック（scope `login`）。超過は 429 + `Retry-After`。
3. `bcrypt.compare` 照合。ユーザー不在とパスワード不一致は**同一メッセージ**「メールアドレスまたはパスワードが違います」（401、存在推測防止）。
4. `next-auth/jwt` の `encode()` で JWT を発行: payload `{ sub, id, email, name, sessionVersion }`、`secret = AUTH_SECRET`、`maxAge = 86400`、`salt = COOKIE_NAME`。
5. Cookie 設定: `httpOnly, sameSite: 'lax', maxAge: 86400, path: '/', secure: isSecure`。

Cookie 名は `AUTH_URL` が `https://` で始まるかで切替: `__Secure-authjs.session-token`（本番）/ `authjs.session-token`（開発）。

クライアントの正規ログイン UI は `AuthGate.tsx` → `authClient.ts` の `signInWithCredentials()`（この API を fetch）。一方 `AuthPanel.tsx`（パスワード変更後の再ログイン等）は `next-auth/react` の `signIn('credentials')` を使い NextAuth の `authorize()` 経路を通る。**2つのログイン経路が併存**しており、どちらも `sessionVersion` を JWT に埋め込む。

### 2.4 ログアウト — `POST /api/auth/logout`（`src/app/api/auth/logout/route.ts`）

1. `auth()` でユーザー特定。ログイン中なら `invalidateAllUserSessions(userId)` で `User.sessionVersion` を +1（**全端末の旧 JWT を一括失効**）。
2. `authjs.session-token` と `__Secure-authjs.session-token` の両方を `maxAge: 0` で削除。
3. 未ログインでも Cookie 削除だけは行い `{ success: true, invalidated: false }` を返す。

### 2.5 パスワード変更 — `changePasswordAction`（`src/app/actions.ts` → `changePasswordForUser`）

- `auth()` 必須。検証: 新パスワードのポリシー（2.2と同一）→ 現在パスワードの `bcrypt.compare` → **現在と同一の新パスワードは拒否**。
- 更新はトランザクション内で `passwordHash` 差替えと `sessionVersion: { increment: 1 }` を同時に実行（変更後は他端末のセッションも失効）。

### 2.6 セッション失効機構 — sessionVersion（SEC-6、`src/services/SessionSecurityService.ts`）

| 関数 | 仕様 |
|---|---|
| `SESSION_MAX_AGE_SECONDS` | `86400`（24時間） |
| `resolveTokenUserId(token)` | `token.id` 優先、なければ `token.sub`。どちらも無効なら `null` |
| `normalizeSessionVersion(v)` | **1以上の整数**のみ有効。それ以外 `null` |
| `getUserSessionVersion(userId)` | DB の現行 version（ユーザー不在は `null`） |
| `isSessionVersionCurrent(userId, v)` | トークン version と DB version の厳密一致 |
| `invalidateAllUserSessions(userId)` | `sessionVersion increment 1`（失敗時 `null`、throw しない） |
| `validateVersionedSessionToken(token)` | 上記を合成した総合判定。`{ valid, userId, sessionVersion }` |

`sessionVersion` が increment されるタイミング: **ログアウト時**（2.4）と**パスワード変更時**（2.5）。DB スキーマは `User.sessionVersion Int @default(1)`（`prisma/schema.prisma`）。

### 2.7 クライアント起動フロー — `useAuthFlow`（`src/hooks/useAuthFlow.ts`）

状態機械: `checking → (guest | authRequired | loadingCharacter) → (characterRequired | ready | error | sessionExpired)`

- `/api/auth/session` を `cache: 'no-store'` で確認。レスポンスが JSON でない場合（= `npm run dev:ui` の Vite モードで NextAuth 不在）は **guest モード**でモックデータ `initialize()` 起動。
- セッションありなら `loadCharacterAction()` を**最大3回・1秒間隔**でリトライ（Neon コールドスタート対策）。
- `NO_CHARACTER` → `characterRequired`（キャラ作成画面）。`READY` → Zustand `loadFromServer(data)` → `ready`。
- カスタムイベント: `necro-auth-changed`（ログイン/登録成功時に再起動）、`necro-session-expired`（Server Action が `SESSION_EXPIRED` を返した時に `page.tsx` / `BattleCanvas.tsx` が dispatch → ReloginModal 表示。Zustand のゲームデータは保持）。
- ログイン/登録成功時に `switchStoryPersistenceScope` / `switchTutorialPersistenceScope` で localStorage の永続化スコープをユーザー ID 単位に切替。

### 2.8 キャラクター作成 — `createCharacterAction(jobId, name)`（`src/app/actions.ts`）

1. `auth()` 必須 → `getAuthorizedUser` で二重確認。
2. 名前は trim 後 **2〜16文字**。jobId はマスターデータ存在確認（不正なら「存在しない職業です」）。
3. **冪等**: 既に Character があれば新規作成せず既存データを返す。
4. トランザクションで初期武器 Item + Character を作成。初期セーブは `emptyPlayerSave()`（`PlayerSaveV1`、`saveVersion = PLAYER_SAVE_SCHEMA_VERSION`）に name / currentJobId / `jobs: [{ jobId, level: 1, exp: 0 }]` / 初期武器装備 / `INITIAL_WEAPON_MATERIALS` を設定。

初期武器テーブル（`STARTER_WEAPON_BY_JOB`、未知の職業は warrior にフォールバック）:

| 職業 | 初期武器 ID |
|---|---|
| warrior | `bone_cleaver` |
| mage | `apprentice_cinder_staff` |
| dark_priest | `mourning_bell_crozier` |
| rogue | `grave_thorn_dagger` |

進行データ（jobs / gold / clearedStages / party / 装備ID / necroStatus 等）は Character の**カラムではなく `Character.playerState`（JSON blob, PlayerSaveV1）**に格納される。詳細は `docs/仕様書/09_データベースと永続化.md` を参照。

## 3. Server Actions 全インベントリと認可（`src/app/actions.ts`）

### 3.1 共通認可パターン

すべての公開 Action は次の二段構えを取る:

```
xxxAction(...)            … 'use server' 公開境界。auth() でセッション取得、なければ即エラー
  └→ xxxForUser(user, ...) … getAuthorizedUser(user.id) で
                              「session.user.id === 引数の userId」を再検証（テスト経由の呼び出しも強制）
```

`getAuthorizedUser()`（actions.ts）は `auth()` を再実行し、セッションの user.id と引数の一致を確認する。所有権検証は常に Prisma の where 句に埋め込む（`Character: { id, userId }` / `Monster: { id, character: { userId } }` / `Item: { id, ownerId }` / `SoulShard: { id, characterId }` / `AbyssalResidue: { id, characterId }`）。所有していない ID は「存在しない」のと同じエラーを返し、存在推測を許さない。

### 3.2 アクション一覧

| Action | 引数 | 認証 | 所有者/整合性検証 | 備考 |
|---|---|---|---|---|
| `signUpAction` | email, password, displayName | 不要 | — | §2.2 と同一検証。レート制限なし |
| `changePasswordAction` | currentPassword, newPassword | 必須 | 本人のみ | sessionVersion increment |
| `startStageAction` | stageId | 必須 | Character 所有 + ステージ解放チェック | §4。StageAttempt 発行 |
| `processStageResultAction` | stageId, stageAttemptId, meta | 必須 | StageAttempt の userId/characterId/stageId 一致 + 単回消費 | §5 |
| `loadCharacterAction` / `loadGameStateAction` | なし | 必須 | userId で自キャラのみ取得 | `loadGameStateAction` はエイリアス |
| `createCharacterAction` | jobId, name | 必須 | userId 1:1、冪等 | §2.8 |
| `changeJobAction` | characterId, jobId | 必須 | Character 所有 | 解放条件は `changeJobInSave` 内で検証 |
| `fetchPlayerAction` | characterId | 必須 | `{ id: characterId, userId }`（SEC-2 IDOR対策） | CharacterData のみ返却 |
| `processGrowthAction` | characterId, type | 必須 | Character 所有 | **実質廃止**。`CHANGE_JOB` は changeJobAction へ誘導、RANK_UP 相当は「死霊術RankはLvから自動昇格します。」を返す |

| `equipItemAction` | characterId, slot, itemId | 必須 | Character 所有 + Item 所有 + スロット/type 一致 | slot は 8種（weapon/sub/head/body/arms/legs/acc1/acc2）、`ITEM_TYPE_BY_SLOT` で型検証 |
| `unequipItemAction` | characterId, slot | 必須 | Character 所有 + スロット妥当性 | |
| `equipResidueAction` | characterId, slotIndex, residueId | 必須 | Character 所有 + Residue 所有 + `slotIndex ∈ [0,5)` + `residue.itemId === RESIDUE_SLOT_ORDER[slotIndex]` + 残滓解放済み | 解放条件 = `area1_node3` クリア（`src/logic/AbyssalResidueUnlockSystem.ts`） |
| `enhanceResidueAction` | characterId, residueId, matIds | 必須 | Character 所有 + Residue を `SELECT ... FOR UPDATE` でロック + 素材消費検証 | 残滓解放済みが前提 |
| `rankUpWeaponAction` | characterId, weaponId | 必須 | Character 所有 + `Item{ ownerId, type: 'WEAPON' }` | 共鳴コスト検証、素材消費と rank+1 を同一 tx |
| `reforgeWeaponAction` | characterId, weaponId | 必須 | 同上 | ILv 上限検証 |
| `dismantleWeaponAction` | characterId, weaponId | 必須 | 同上 + **装備中の武器は分解不可** | Item 削除 + 素材還元 |

セーブ書込み系はすべて `prisma.$transaction` + `updatePlayerSaveSnapshot`（`src/services/PlayerSaveService.ts`）経由。ステージ結果と残滓強化は `SELECT ... FOR UPDATE` による行ロック（`lockCharacterForUpdate` / raw query）で並行更新を直列化する。セーブ JSON の破損は `PlayerSaveSchemaError` として検出し、固定文言「セーブデータの形式が不正です。サポートに連絡してください。」を返す。

### 3.3 管理系 Server Actions（`src/app/admin/actions.ts`, `src/app/admin/agents/actions.ts`）

- マスターデータ編集・AI エージェント（LangGraph + Gemini）系の Action は**セッション認証を持たない**代わりに、`assertDev()` / `withDevGuard()`（`src/app/admin/adminGuard.ts`）で `NODE_ENV !== 'development'` なら throw する。

## 4. ステージ開始証跡 — StageAttempt（SEC-8）

「バトルを開始した」証跡なしにステージ報酬を取得する攻撃（コンソールから `processStageResultAction` 直呼び）を防ぐ。旧設計（doc 68）の Redis トークン案とは異なり、**Prisma の `StageAttempt` テーブル**で実装されている。

### 4.1 発行 — `startStageAction(stageId)`

1. `auth()` + `getAuthorizedUser`。未認証は `SESSION_EXPIRED`。
2. stageId 正規化（`STAGE_ID_ALIASES`: `'1-1' → 'area1_node1'`）→ マスター存在確認（`STAGE_NOT_FOUND`）→ `nodeType === 'SAFE'` は `STAGE_NOT_PLAYABLE`。
3. **サーバー側解放チェック**: `getEffectiveClearedStages()`（Character カラムと playerState 内 clearedStages のマージ、`src/services/PlayerSaveService.ts`）に対し `isStageUnlocked()`（`unlockRequires` の全クリア判定、`src/logic/DungeonSystem.ts`）。未達は `STAGE_LOCKED`。
4. `StageAttempt` レコード作成: `{ userId, characterId, stageId, expiresAt = now + STAGE_ATTEMPT_TTL_MS }`。**TTL = 2時間**（`STAGE_ATTEMPT_TTL_MS = 2 * 60 * 60 * 1000`）。
5. 返却: `{ success: true, stageAttemptId, tokenId, expiresAt }`（tokenId は stageAttemptId の別名）。

### 4.2 消費 — `consumeStageAttempt()`（processStageResult の tx 内）

`updateMany({ where: { id, userId, characterId, stageId, consumedAt: null, expiresAt: { gt: now } }, data: { consumedAt: now } })` の**アトミックな条件付き更新**で単回消費を保証。count ≠ 1 の場合は原因を特定してエラーコードを返す。

| エラーコード | 条件 |
|---|---|
| `MISSING_STAGE_ATTEMPT` | stageAttemptId 未指定（**必須化済み** = 旧設計 Phase 2 到達） |
| `INVALID_STAGE_ATTEMPT` | レコード不存在 |
| `TOKEN_USER_MISMATCH` | 他ユーザーの証跡 |
| `TOKEN_CHARACTER_MISMATCH` | 別キャラクターの証跡 |
| `TOKEN_STAGE_MISMATCH` | 別ステージの証跡 |
| `STAGE_ATTEMPT_CONSUMED` | 二重送信（消費済み） |
| `STAGE_ATTEMPT_EXPIRED` | 2時間超過 |

## 5. ステージ結果のサーバー検証 — `processStageResultAction`

### 5.1 メトリクス正規化（ランキング改ざん耐性）

クライアント申告の `StageResultMeta { turnCount?, clearTimeSec?, totalDamage? }`（`src/types/online.ts`）は `normalizeStageClearMetrics()`（`src/services/RankingService.ts`）で検証・丸め・キャップされる:

- 非有限値 / `turnCount < 1` / `clearTimeSec < 1` / `totalDamage < 0` → `INVALID_STAGE_RESULT_META` で拒否。
- 既定値: turnCount = 10、clearTimeSec = turnCount × 5、totalDamage = 0。
- ステージ別キャップ（`getStageMetricCaps`, `src/app/actions.ts`）:
  - `maxTurnCount = max(30, waveCount × 30)`
  - `maxClearTimeSec = 3600`（1時間）
  - `maxTotalDamage = max(1000, ステージ全敵HP合計 × 4)` — REVIVE ギミック持ちは `floor(hp × reviveValue(既定0.5))` を HP 合計に加算。

### 5.2 トランザクション処理順序

1. `consumeStageAttempt`（§4.2。失敗は throw → 全ロールバック）。
2. `lockCharacterForUpdate`（`SELECT ... FOR UPDATE`）→ セーブ再読込。
3. EXP 計算（`RewardService.calculateExp`）、ドロップ抽選（`processStageDropTable` + `processStageNecromance` — **抽選は完全サーバー側**、クライアントは結果を受け取るのみ）。
4. ドロップ武器の DB 保存 + 第一発見者判定（§8.2）。消費アイテム / 残滓 / 魔物の保存。
5. セーブ更新: 職業EXP・死霊術EXP付与、gold 加算（`stage.rewards.baseGold`）、`clearedStages` 追記、素材加算。
6. `RankingService.recordStageClear`（§7.3）。
7. 世界イベント生成（tx 内は DB 保存のみ）: ボス**世界初**クリア → `BOSS_CLEARED`、黄泉10階刻み初回クリア → `YOMI_MILESTONE`（`getYomiMilestoneFloorForFirstClear`, `src/logic/YomiFloors.ts`）、残滓スコア世界1位更新 → `RANKING_UPDATED`。

コミット後に `RankingService.invalidate()`（キャッシュ削除）と `publishWorldEvents()`（Pusher 配信）を実行し、`loadCharacterForUser` で最新状態を返す。**Pusher 配信は必ずコミット後**（tx 内では `createWorldEvent` で DB 保存のみ）。

## 6. レート制限（`src/services/RateLimitService.ts`）

### 6.1 適用範囲と閾値（`AUTH_RATE_LIMITS`）

| scope | 識別子 | 上限 | ウィンドウ |
|---|---|---|---|
| `login:ip` | クライアントIP | 20回 | 10分 |
| `login:email` | email（正規化後） | 10回 | 10分 |
| `signup:ip` | クライアントIP | 5回 | 60分 |
| `signup:email` | email | 3回 | 60分 |

適用箇所は `/api/auth/login` と `/api/auth/signup` の**2エンドポイントのみ**。ゲーム系 Server Actions・ランキング/世界ログ API にはレート制限が存在しない（未実装）。IP 制限を先に評価し、超過ならその時点で 429。両方通過時の `remaining` は IP/email の小さい方。

### 6.2 アルゴリズム

- キー: `ratelimit:{scope}:{sha256(identifier)先頭32hex}`（識別子は trim + 小文字化。生の email/IP を Redis に残さない）。
- Upstash Redis が設定済み（`UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN`）なら REST pipeline 1回で `ZREMRANGEBYSCORE`（窓外削除）→ `ZADD`（now + randomUUID メンバー）→ `ZCARD`（件数判定）→ `EXPIRE` を実行するスライディングウィンドウ。
- Redis 未設定・エラー時は**プロセス内メモリの Map にフォールバック**（サーバーレスの複数インスタンス間では共有されない = ベストエフォート）。
- 超過時 `retryAfterSec`: メモリ版は最古エントリからの残時間、Redis 版はウィンドウ幅そのまま。

### 6.3 クライアントIPの解決（`getClientIp`）

優先順: `x-forwarded-for` の先頭 → `cf-connecting-ip` → `x-real-ip` → `'unknown'`。

## 7. ランキング（`src/services/RankingService.ts`, `GET /api/ranking`）

### 7.1 ランキング種別（`RankingType`, `src/types/online.ts`）

| type | 集計元 | ソート | value |
|---|---|---|---|
| `RESIDUE_SCORE` | `PlayerStats.bestResidueScore` | desc | 残滓スコア最高値 |
| `STAGE_TIME` | `StageRecord`（stageId 指定可） | `turnCount asc, clearTimeSec asc` | turnCount |
| `TOTAL_DAMAGE` | `PlayerStats.totalDamage`（BigInt） | desc | 累計ダメージ |
| `BOSS_KILLS` | `PlayerStats.bossKillCount` | desc | ボス撃破数 |
| `DUNGEON_FLOOR` | `PlayerStats.bestDungeonFloor` | desc | 黄泉最深階層 |

リセット周期は**全種別なし**（永続。月次リセットは未実装）。表示名は `displayName ?? name ?? email ?? '名もなき死霊術師'`。

### 7.2 API — `GET /api/ranking?type=&stageId=&limit=`（`src/app/api/ranking/route.ts`）

- **認証不要**（公開読み取り）。不正な type は `RESIDUE_SCORE` にフォールバック。limit は 1〜100 にクランプ（既定50）。
- キャッシュ: キー `ranking:{type}:{stageId ?? 'global'}:{limit}`、Upstash Redis に JSON 文字列で `EX=300`（5分）。Redis 不在・失敗時は素通しで DB クエリ（キャッシュは最適化としてのみ扱い、エラーは握り潰す）。

### 7.3 記録更新 — `recordStageClear(tx, input)`（processStageResult の tx 内）

- `StageRecord` は `@@unique([userId, stageId])` の1ユーザー1ステージ1レコード。更新条件（ベスト更新）: `turnCount` がより小さい、または同 turnCount で `clearTimeSec` がより小さい場合のみ上書き。
- `PlayerStats` は upsert: `totalDamage` は**加算**、`bossKillCount` は isBossStage（`nodeType === 'BOSS'` または `isAreaBoss`）時 +1、`bestResidueScore` / `bestDungeonFloor` は max 更新（階層は `getYomiFloorNumber(stageId)` から導出）。
- `becameTopResidue`: 今回の残滓スコアが更新前の全体トップを超えた場合 true → `RANKING_UPDATED` イベントの発火条件。

### 7.4 キャッシュ無効化 — `invalidate()`

limit ∈ {5, 10, 50, 100} について `RESIDUE_SCORE / TOTAL_DAMAGE / BOSS_KILLS / DUNGEON_FLOOR` の global キーと `STAGE_TIME:area1_boss` を削除する。**削除対象は固定リスト**であり、他の stageId 別 STAGE_TIME キャッシュや上記以外の limit 値は TTL 失効（最大5分）まで古い値が残る。

## 8. 世界ログと第一発見者

### 8.1 世界イベント（`WorldEventType`, `src/types/online.ts`）

| type | 発火条件（`src/app/actions.ts`） | 主な payload |
|---|---|---|
| `UR_DISCOVERED` | 世界初ドロップかつ isUnique / UR / UNIQUE / HIDDEN_UNIQUE | playerName, itemName, rarity, serialNo, isUnique |
| `SSR_DISCOVERED` | 世界初ドロップ（上記以外 = SSR / LR） | 同上 |
| `BOSS_CLEARED` | ボスステージの**世界初**クリア（StageRecord 不在判定） | playerName, stageId, stageName |
| `RANKING_UPDATED` | 残滓スコア世界1位更新（score > 0） | playerName, rankingName: '残滓スコア', value |
| `YOMI_MILESTONE` | 黄泉 `floor % 10 === 0` の階を**本人初**クリア | playerName, floor, stageId, stageName |

### 8.2 第一発見者システム

- 発見対象レアリティ: `DISCOVERY_RARITIES = { SSR, UR, LR, UNIQUE, HIDDEN_UNIQUE }` または `isUnique` 武器。
- 世界初判定: 同 `name` + `rarity` で `discovererId` 非 null の Item が存在しないこと（tx 内で判定 → `discovererId / discovererName / discoveredAt` を刻印）。
- シリアル No: `ItemSerialCounter`（itemName 単位）を `upsert + counter increment` で採番。**発見対象レアリティなら世界初でなくても** No が振られる（No.2 以降も付与）。

### 8.3 配信（`src/services/WorldEventService.ts`）

- 永続化: `WorldLog { type, payload(Json), authorId?, createdAt }`。tx 内は `createWorldEvent(tx, ...)` で DB 保存のみ、コミット後に `publishWorldEvents()` が Pusher へ送信（`emitWorldEvent()` は保存+配信を一括で行う単発用だが、現行のゲーム経路では未使用）。
- Pusher 送信: SDK を使わず `POST https://api-{cluster}.pusher.com/apps/{appId}/events` を直接叩く。認証は `auth_key / auth_timestamp / auth_version=1.0 / body_md5(MD5)` をソートした query string に対する **HMAC-SHA256（secret）署名**。channel は固定 `world-log`、event 名は WorldEventType。失敗は `console.warn` のみ（配信はベストエフォート、DB が正）。
- 環境変数が1つでも欠けると Pusher は無効化され、保存のみ行う。

### 8.4 取得 API とクライアント（`GET /api/world-log`, `src/hooks/useWorldLog.ts`）

- API: 認証不要。`WorldLog` を `createdAt desc` で取得、limit は 1〜100 にクランプ（既定50）。
- クライアント: **30秒間隔のポーリングが正**で、Pusher はライブ加速用。`pusher-js` を使わず素の WebSocket で `wss://ws-{cluster}.pusher.com/app/{key}?protocol=7...` に接続し、`pusher:connection_established` 受信後に `world-log` チャンネルを subscribe。受信イベントは最新50件に重複排除でマージ。
- 注意: ライブ受信のフィルタは `['UR_DISCOVERED', 'SSR_DISCOVERED', 'BOSS_CLEARED', 'RANKING_UPDATED']` で **`YOMI_MILESTONE` を含まない**（黄泉マイルストーンはポーリングでのみ反映される。意図か漏れかは未確認）。
